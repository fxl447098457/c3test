## 问题现象

vbman 中存在大量形如 `vb6_cXxx_FieldName` 的未声明标识符错误 (C2065)。原本以为是跨模块符号查找的问题, 直到采样 `vb6_cByteBuffer_Size` (27 处) 才定位到真正的根因。

### 典型样本

源码 `vbman\src\Socket\mdTlsThunks.bas` (UDT 与若干 Sub):

```vb
Private Type UcsBuffer
    Data()              As Byte
    Pos                 As Long
    Size                As Long
    Stack               As Collection
End Type

Private Sub pvTlsBuildClientHello(uCtx As UcsTlsContext, uOutput As UcsBuffer)
    ...
    lMessagePos = uOutput.Size                  ' <- 错误位置 1
    vb6_ToolsTlsThunks_pvTlsAppendHandshakeHash &uCtx, uOutput.Data, lMessagePos, uOutput.Size - lMessagePos
    ...
End Sub
```

注意:
- `uOutput As UcsBuffer` 是 ByRef UDT 参数 (VB6 默认 ByRef, UDT 在 C 中是 `UcsBuffer*`)
- `UcsBuffer.Size` 是 UDT 字段 `Size As Long`
- 项目里另一个类 `vbman\src\Websocket\cByteBuffer.cls` 又恰好定义了 `Property Get Size()` — 这就是冲突源头

修复前生成的 C 代码:

```c
/* ToolsTlsThunks.c line 700 (错误) */
lMessagePos = vb6_cByteBuffer_Size;          /* 应该是 (*uOutput).Size */

/* line 917 (同一函数内同一行错误) */
vb6_ToolsTlsThunks_pvTlsAppendHandshakeHash(&uCtx, (&(uint8_t*){(*uOutput).Data}),
    lMessagePos, (vb6_cByteBuffer_Size - lMessagePos));  /* 应该是 (*uOutput).Size */
```

注意第 917 行里 `(*uOutput).Data` 被正确生成 (struct 字段访问, 因为 "Data" 不与任何类成员冲突), 但 `uOutput.Size` 因为 "Size" 与 `cByteBuffer.Size` 撞名, 就被错误地以"跨模块函数"形式 `vb6_cByteBuffer_Size` 输出。

修复后生成的 C 代码:

```c
/* line 700 */
lMessagePos = (*uOutput).Size;

/* line 917 */
vb6_ToolsTlsThunks_pvTlsAppendHandshakeHash(&uCtx, (&(uint8_t*){(*uOutput).Data}),
    lMessagePos, ((*uOutput).Size - lMessagePos));
```

对 `(8B) vb6_cByteBuffer_Size - lMessagePos` 处的 ByRef UDT 字段, 正确生成 `(*uOutput).Size - lMessagePos`。

## 根因分析

### MemberAccessExpr 访问器流程 (cgen_expr.cpp:1089+)

`visit(MemberAccessExpr&)` 处理 `obj.member` 形式的成员访问。在 `node.object` 是 `IdentifierExpr` 的分支里 (line 1182+), 检查顺序是:

1. Err/Debug/App/Clipboard/Screen/Printer/Forms 等全局内置对象特殊处理
2. `knownFormControls_` — 窗体控件属性读取
3. `knownTypedComVars_` / `knownIfaceVars_` / `knownObjectVars_` / `knownVariantVars_` — 各类 COM 后期/前期绑定
4. `VB_GlobalNameSpace` promoted 函数
5. **`memSym = symTab_.lookupModule(node.memberName)` — 查找成员名符号 (问题所在)**
6. M22: 跨模块变量访问 `Module1.varName` → `vb6_Module1_varName`
7. 通用 fallback: `emitExpr(object); lastExpr_ += "." + member;`

第 5 步的 `memSym` 用 **成员名** (如 "Size") 去模块符号表里查, 一旦命中任何 Sub/Function/PropertyGet/Let/Set (无论是否是当前作用域内对象真正的方法/属性, 也无论来自哪个模块/类), 就会:

- 进入 `isVarName` 检查 (line ~1437)
- `uOutput` 是局部参数, 不在 `symTab_.lookup` (过程级) 命中, 也不在 `symTab_.lookupModule` (模块级 Variable/Parameter) 命中 (因为局部 Dim/过程级 Parameter 不存模块作用域, 而是用 cgen 层的 `knownUdtVars_`/`knownClassVars_` 等并行跟踪)
- `isVarName = false` → 进入 line ~1444 块, 把 `uOutput` 当成模块名, 用 `memSym->isExternal ? memSym->sourceModule : objIdent.name` 作为 `sourceMod` (对 `cByteBuffer.Size` 这就是 `"cByteBuffer"`), 通过 `cProcName(memberName, memSym->access, sourceMod)` 生成 `vb6_cByteBuffer_Size`

整段路径完全不知道 `uOutput` 其实是 UDT 变量, 只是因为 `sym` 表里 "Size" 这个名字命中了外类属性就把对象当成模块名, 产生错误的函数引用。

### 为什么"Data" 不受影响

测试 `uOutput.Data` 时, `memSym = symTab_.lookupModule("Data")` 在 vbman 符号表里查不到任何同名 Sub/Func/Property (没有 `cXxx.Data` 之类), `memSym == nullptr`, 整个块被跳过 → 到达 M22 → `knownUdtVars_.count("uoutput")` 命中 → `isVarName2=true` → 跳过 M22 → 到达通用 fallback (line ~1506) → 正确生成 `(*uOutput).Data`。所以"不撞名"的字段反而没问题, "撞名"的字段才会触发 bug。

### 影响:Pattern A

属于这个 bug 的所有错误 (Pattern A) 都具备三个特征:
1. 对象是 UDT 变量 (在 `knownUdtVars_` 中正确注册了, cgen_decl.cpp 注册逻辑没问题)
2. 对象是 IdentifierExpr 形式 (单层访问, 非链式)
3. 字段名 (成员名) 与项目中某个跨模块类的方法/属性名冲突

`vb6_cXxx_Yyy` 形式的 C2065 大约 96 个直接受益于此修复, 还连带消除了一批 C2440/C2198 (因为下游对 `vb6_cByteBuffer_Size` 的"未声明标识符当作 int 处理"产生的类型转换错误也消失了)。

## 修复方案

在 `cgen_expr.cpp` 的 `visit(MemberAccessExpr&)` 中, `node.object->kind == ASTNodeKind::IdentifierExpr` 分支内 (line ~1182+), 在 `// 查找成员名称的符号 \n auto* memSym = symTab_.lookupModule(node.memberName);` 之前, 新增 UDT 变量短路检查:

```cpp
// Fix 031: UDT 变量字段访问 — 必须在 memSym 查找之前拦截.
// 当 obj 是已知 UDT 变量 (knownUdtVars_) 时, obj.member 总是结构体字段访问
// (obj.member 或 (*obj).member 形式, 取决于 emitExpr 对该 UDT 变量的求值),
// 不应进入 memSym 路径把 obj 当作模块名 (或 uOutput 误当类实例).
// 现象: Private Sub pvTlsBuildClientHello(uCtx As UcsTlsContext, uOutput As UcsBuffer)
//       其中 UcsBuffer UDT 含 Size As Long 字段, 同时项目里又有 cByteBuffer.cls
//       声明了 Property Get Size, memSym 查找命中该跨模块属性 → 误生成
//       vb6_cByteBuffer_Size 函数引用 (而非 (*uOutput).Size 字段访问), 触发 C2065.
// 已知 UDT 变量与类实例 (knownClassVars_) / Object (knownObjectVars_) 在注册阶段
// 互斥, 此处不冲突.
if (knownUdtVars_.count(objLower)) {
    emitExpr(*node.object);
    std::string obj = std::move(lastExpr_);
    lastExpr_ = obj + "." + cIdent(node.memberName);
    return;
}
```

### 设计要点

1. **使用并集互斥保证**: cgen_decl.cpp 注册时, 变量按类型分到 `knownUdtVars_` (UDT) / `knownClassVars_` (类实例) / `knownTypedComVars_` (ComClass) / `knownObjectVars_` (As Object) / `knownVariantVars_` (Variant)。UDT 变量不可能同时是类实例或 Object, 这些集合互斥。
2. **emitExpr 求值负责解引用**: 局部 UDT 变量 emit 为 `uOutput`; ByRef UDT 参数 emit 为 `(*uOutput)` (cgen_expr.cpp:318-325 行 IdentifierExpr 处理 ByRef 时自动加解引用)。任一情况下 `.member` 都是合法的结构体字段访问, 与通用 fallback (line 1506+ → 1737) 行为完全一致, 只是把拦截位置前移到 memSym 查找之前。
3. **`cIdent` 保证 C 标识符合法化**: 同 fallback 路径一致。
4. **不影响类实例成员访问** (`knownClassVars_` 命中后走 `resolveClassMemberCall` 路径, 也不进 UDT 短路, 顺序保持不变)。

## 未覆盖的情况 (留给 Fix 032+)

### Pattern B: 隐式属性返回值变量 (Property Get body 内)

源码:

```vb
Public Property Get LocalHostName() As String
    pvSocket.GetLocalHost LocalHostName, vbNullString
End Property

Public Property Get ReadIntervalTimeout() As Long
    ReadIntervalTimeout = m_ReadIntervalTimeout
End Property
```

`LocalHostName` / `ReadIntervalTimeout` 在 Property Get body 内部是隐式返回值变量 (`vb6_ret_<PropName>` 临时变量, 在函数头部已声明)。但 IdentifierExpr 访问器 (不是 MemberAccessExpr) 不知道去查 `vb6_ret_<PropName>`, 转而走 memSym 路径把它当跨模块属性, 生成 `vb6_cTlsReMaster_LocalHostName` 之类的函数引用 (本应是 `vb6_ret_LocalHostName`), 触发 C2065 + C2064 级联。

涉及 ~30 个错误 (`vb6_cTlsReMaster_*` / `vb6_cSerialConfig_*` / `vb6_cAsyncSocket_*` / `vb6_cTlsSocket_*` 等若干)。该模式与本 Fix 031 不同, 因为对象不出现 (左值是裸符号), 需要 Fix 032 在 IdentifierExpr 访问器内做 Property Get body 上下文感知。注意 `ct` 前缀 (`vb6_ct_ReadIntervalTimeout`) 是 `cProcName` 在该 memSym 路径生成的某种本地字段缩写, 值得在 Fix 032 一并复核。

### C2064 级联 (UDT 数组字段索引)

样本:

```c
/* ToolsTlsThunks.c line 468 */
vb6_ToolsTlsThunks_pvArrayWriteBlob(&baPlainText, (*lPos),
    (int32_t)(intptr_t)&(_vb6_with_3.DecrBuffer.Data(0)), _vb6_with_3.DecrBuffer.Size);
/* line 1302 */
vb6_ToolsTlsThunks_pvBufferWriteBlob(&uVerify,
    (int32_t)(intptr_t)&((*uOutput).Data(lSignPos)), lSignSize);
```

`_vb6_with_3.DecrBuffer.Data` / `(*uOutput).Data` 现在被 Fix 031 正确生成成了结构体数组字段 (struct 内 `Byte()` 数组 = `vb6_SafeArray1D*`), 但 `Data(0)` / `Data(lSignPos)` 这种"UDT 数组字段 + 括号索引"的 IndexOrCallExpr 没有识别为 SafeArray 索引, 直接当函数调用输出 `(...)(0)` → C2064 (term does not evaluate to function)。

应在 `visit(IndexOrCallExpr&)` 检查: callee 是 `MemberAccessExpr` + 其结果对象是 UDT 变量时, 把 `(indx)` 转成 `VB6_SA_AT(fieldExpr, indx)` 或对内联元素数组 `fieldExpr[idx]`, 而不是当成函数调用。估算 ~14 个新错误都属这一类, 留给 Fix 033 解决 (与 Pattern B 同等级优先级, 顺序待定)。

### 链式 UDT 字段访问 (chained)

如 `uCtx.HandleSize.State` 三层访问 (UcsTlsContext UDT 内, HandleSize 又是某子 UDT, .State 是该子 UDT 字段) — 内层 `uCtx.HandleSize` 走 Fix 031 短路正确输出 `(*uCtx).HandleSize`, 但外层 `.State` 是 MemberAccessExpr (非 IdentifierExpr), 仍走 memSym 查找路径可能出错。如果 `.State` 名字与某个跨模块类成员撞名 → 同样 C2065。本项目 `vb6_cTlsReMaster_State` 等几个错误其实可能也属此类。Fix 032 时可在 memSym 查找前用 inferExprType 检查 node.object 是否返回 UDT 类型, 是的话也短路掉。
