# Fix 050: COM 枚举类型 + VB6 类型别名解析修复

## 日期
2026-07-23

## 问题描述

### 根因1: COM 枚举类型解析为 Variant (95 个 C2440 错误)

vbman 项目引用了 ADODB 等 COM 类型库，其中包含 `DataTypeEnum`、`CursorTypeEnum`、`LockTypeEnum` 等枚举类型。这些类型不在项目源码中定义，因此不在 C3 的符号表中。

在 `SemanticAnalyzer::resolveTypeRef()` (semantic_analyzer.cpp:552) 中，当 `typeSys_.resolveTypeName()` 返回 `Unknown` 时，会查找模块符号表。如果符号表中也没有找到（COM 枚举类型不在符号表中），则回退到 `Vb6Type::Variant`（第 600 行）。

然而，在代码生成器 `CCodeGen::mapTypeRef()` (cgen_base.cpp:1086-1091) 中，以 "Enum" 结尾的类型名被映射为 `int32_t`。

这导致**语义分析器认为参数类型是 Variant，但代码生成器生成 `int32_t`**，产生 `vb6_VARIANT → int32_t` 的 C2440 类型转换错误。

典型示例（cDataBase.cls）:
```vb
Public Function Param(Optional ByVal ParamType As DataTypeEnum = adVarChar) As ...
```
`DataTypeEnum` 来自 ADODB 类型库，语义分析器解析为 Variant，代码生成器生成 `int32_t`。

### 根因2: VB6 类型别名解析不一致 (additional C2440 errors)

类似的类型不一致问题也出现在 VB6 类型别名上:
- `LongPtr` — VB6 32 位下等于 Long，`mapTypeRef()` 映射为 `int32_t`，但 `resolveTypeName()` 返回 `Unknown`
- `OLE_COLOR` — DWORD 类型，`mapTypeRef()` 映射为 `int32_t`，但 `resolveTypeName()` 返回 `Unknown`
- `Vb*` 前缀枚举 (如 `VbCompareMethod`, `VbTriState`) — `mapTypeRef()` 映射为 `int32_t`，但 `resolveTypeName()` 返回 `Unknown`

这些类型在 `resolveTypeRef()` 中经过 `resolveTypeName()` 返回 `Unknown` 后，进入符号表查找分支，找不到后回退到 `Variant`，与代码生成器的 `int32_t` 不一致。

典型示例（mQRcodeGen.bas）:
```vb
Private Declare PtrSafe Function FillRect Lib "user32" (ByVal hDC As LongPtr, ...) As Long
Optional ByVal clrFore As OLE_COLOR = vbBlack
```

## 修复方案

### 修改1: `resolveTypeRef()` 添加 COM 枚举类型后缀检查

**文件**: `src/semantics/semantic_analyzer.cpp` (第 599 行附近)

在 `resolveTypeRef()` 中，当类型名未在符号表中找到时（即将回退到 `Variant` 之前），检查类型名是否以 "Enum" 结尾。如果是，返回 `Vb6Type::Long`。

```cpp
// Fix 050: COM 枚举类型 (如 DataTypeEnum, CursorTypeEnum, LockTypeEnum)
// 来自引用的 COM 类型库 (如 ADODB)，不在项目符号表中。
// VB6 中所有 Enum 类型都是 Long (32位整数)，因此以 "Enum" 结尾的
// 未识别类型名应返回 Long 而非 Variant，避免 vb6_VARIANT→int32_t C2440 错误。
{
    std::string lowerName = Symbol::toLower(simple.name);
    if (lowerName.size() > 4 &&
        lowerName.compare(lowerName.size() - 4, 4, "enum") == 0) {
        return Vb6Type::Long;
    }
}
// 未识别类型 → Variant (宽松策略)
return Vb6Type::Variant;
```

### 修改2: `resolveTypeName()` 添加 Enum 后缀 + VB6 类型别名支持

**文件**: `src/semantics/type_system.cpp` (第 42 行附近)

在 `resolveTypeName()` 中，在内置类型查找之后、返回 `Unknown` 之前，添加以下检查:

1. **Enum 后缀检查**: 以 "Enum" 结尾的类型名 → `Long`（与 `resolveTypeRef` 中的检查一致，但此处使所有 `resolveTypeName()` 调用方都受益，包括 `cgen_decl.cpp` 中的参数类型注册）
2. **LongPtr**: → `Long`（VB6 32 位下等于 Long）
3. **OLE_ 前缀**: `OLE_COLOR`, `OLE_HANDLE` 等 → `Long`（DWORD = Long）
4. **Vb 前缀枚举**: `VbCompareMethod`, `VbTriState` 等 → `Long`（VB6 内置枚举，底层是 Long）。排除 `boolean` 和 `byte` 以避免误匹配。

```cpp
// Fix 050: COM 枚举类型
if (lower.size() > 4 && lower.compare(lower.size() - 4, 4, "enum") == 0) {
    return Vb6Type::Long;
}
// Fix 050b: VB6 类型别名
if (lower == "longptr" || lower == "longptr") {
    return Vb6Type::Long;
}
if (lower.size() >= 4 && lower.compare(0, 4, "ole_") == 0) {
    return Vb6Type::Long;
}
if (lower.size() >= 2 && lower.compare(0, 2, "vb") == 0 &&
    lower != "boolean" && lower != "byte") {
    return Vb6Type::Long;
}
```

### 剩余 vb6_VARIANT → int32_t (40个) 根因分析

- mQRcodeGen.c (12个): UDT With 块的 COM 属性访问 (`vb6_VariantFromComResult(vb6_ComGetProp(...))` 返回 VARIANT，但 ByRef 参数期望 `int32_t*`)

- cZipArchive.c (4个): 类似的 Variant→数值参数问题
- 其他 (14个): 零散的 Variant 变量传给期望 int32_t 的函数
