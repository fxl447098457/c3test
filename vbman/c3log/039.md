# Fix 039 — Bitwise Operator Type Casting (And/Or/Xor/Eqv/Imp/Not)

## Date
2026-07-20

## Starting Point
After Fix 038b (commit `fa8c21c`): **1923 tracked errors**.

Targeted error codes (before fix):
- C2297: 46 — `'operator' : illegal, right operand has type 'function'`
- C2171: 27 — `'operator' : illegal for operand of type 'function'`
- C2296: 13 — `'operator' : illegal, left operand has type 'function'`
- C2088: 46 — `use of array/object/pointer requires []`
- C4804: 5 — `'==' : unsafe use of type 'bool' in arithmetic operations`

These errors were all caused by VB6 bitwise operators (`And`, `Or`, `Xor`, `Eqv`, `Imp`, `Not`) being emitted to C as raw `&`, `|`, `^`, `~` without operand type handling. When operands were `double` (from `vb6_Pow()`), `BSTR` (`wchar_t*`), `void*`, `SafeArray*`, or `vb6_VARIANT`, MSVC rejected the bitwise operation.

## Root Cause

In `src/backend/cgen_expr.cpp`, the `visit(BinaryExpr)` and `visit(UnaryExpr)` methods emitted VB6 bitwise operators as C bitwise operators directly:

- `And` → `(left & right)`
- `Or`  → `(left | right)`
- `Xor` → `(left ^ right)`
- `Eqv` → `(~(left ^ right))`
- `Imp` → `((~left) | right)`
- `Not` → `(~operand)`

VB6 semantics: bitwise operators convert operands to `Long` (int32) before the bitwise operation. The generated C code was passing non-integer types (doubles from `vb6_Pow`, BSTR pointers, `void*` class fields, `vb6_VARIANT`) directly to `&`, `|`, `^`, `~`, which MSVC rejects.

Examples of failure (from generated C code):
- `(~vb6_Pow(a, b))` — `~` on `double` (C2297)
- `(ptr & mask)` — `&` on `wchar_t*`/`void*` (C2296/C2297)
- `(~vb6_VariantFoo())` — `~` on `vb6_VARIANT` struct (C2088)
- `(x & flag) != 0` where `x` is `bool` — C4804

## Implementation

All changes in `src/backend/cgen_expr.cpp`. Three locations share the same `castBitwise` lambda pattern.

### Location 1: Eqv operator (~line 932)

```cpp
// Fix 039: VB6 Eqv → ~(a^b), cast to int32_t for non-integer operands
// (double from vb6_Pow, pointer from BSTR/void*/SafeArray*)
// Fix 039b: For Variant operands, use vb6_VariantToLong() instead of (int32_t)() cast.
if (node.op == BinaryOp::Eqv) {
    auto castBitwise = [&](const std::string& cExpr, const Expr* astExpr) -> std::string {
        if (cExprIsVariant(cExpr)) return "vb6_VariantToLong(" + cExpr + ")";
        if (astExpr && astExpr->kind == ASTNodeKind::IdentifierExpr) {
            auto& ident = static_cast<IdentifierExpr&>(const_cast<Expr&>(*astExpr));
            std::string lower = ident.name;
            std::transform(lower.begin(), lower.end(), lower.begin(), ::tolower);
            if (knownVariantVars_.count(lower)) return "vb6_VariantToLong(" + cExpr + ")";
        }
        return "(int32_t)(" + cExpr + ")";
    };
    lastExpr_ = "(~(" + castBitwise(left, node.left.get()) + " ^ " + castBitwise(right, node.right.get()) + "))";
    return;
}
```

### castBitwise Lambda Logic

The lambda (repeated in each location) applies the following rules in order:

1. If the C expression string starts with a known Variant-returning prefix (`cExprIsVariant()` — defined in Fix 038b), wrap with `vb6_VariantToLong(...)` to extract the Long value.
2. Otherwise if the AST node is an `IdentifierExpr` flagged as Variant in `knownVariantVars_`, also wrap with `vb6_VariantToLong(...)`.
3. Otherwise cast to `int32_t`.
   - This is safe for `double` (truncation matches VB6 Long semantics).
   - For `wchar_t*`/`void*`/`SafeArray*` (pointers), `(int32_t)ptr` extracts the low 32 bits — matches VB6's behavior of treating pointers as Long.
   - For `bool`, `(int32_t)bool` normalizes to 0/1 — fixes C4804.

## Fix 039b Refinement (Variant Regression)

The first version of Fix 039 (without the Variant check) applied `(int32_t)()` to all operands. This eliminated C2297/C2171/C2296/C4804 but caused C2440 to increase by 25 errors because `(int32_t)(vb6_VARIANT)` is not a valid cast in C.

Fix 039b added the `cExprIsVariant()` and `knownVariantVars_` checks BEFORE the `(int32_t)()` cast. When the operand is a Variant-typed expression, `vb6_VariantToLong()` is used instead — this is the correct API for extracting a Long from a `vb6_VARIANT`. This reduced the C2440 regression from +25 to +9.

The remaining +9 C2440 errors come from edge cases where `cExprIsVariant()` does not detect the Variant (e.g., function-returning-Variant whose prefix is not in the `cExprIsVariant` prefix list, or a class Property accessor registered as Variant in the symbol table). These will be absorbed by future C2440 fixes (Fix 040+).
