# Fix 011: C 代码生成修复（vbman 完整编译续，C2106 Patterns 多批修复）

## 背景

Fix 010（commit `128b018`）结束时，错误总数为 4064，主要瓶颈集中在 C2106（左值错误，166 个）与 With-block 类型系统。本批次继续以 C2106 sub-pattern 为切入点进行批量修复，五组子修复（010r-13 ~ 010r-16b）将错误从 **4064 降到 3938**（C2106 从 166 降到 35）。

## 错误趋势

| 阶段 | 总错误 | C2106 | 说明 |
|------|------|------|------|
| 010r-12c 之后（基线） | 4064 | 166 | 上一批次结束点 |

## 修改内容

### 主题 1：C2106 Pattern I — Windows API 宏冲突（010r-13）

**问题**：VB6 局部 `Const WHITE_BRUSH = 0` 会生成 `const int32_t WHITE_BRUSH = 0;`。但 `WHITE_BRUSH`、`MEM_COMMIT`、`MEM_RELEASE`、`CP_UTF8`、`SW_SHOWNORMAL`、`SW_SHOW` 等都是 `<windows.h>` 中的 `#define` 宏，宏在预处理阶段展开后变成 `const int32_t 0 = 0;`，触发 C2106。共 8 处。

**根因**：`cgen_stmt.cpp::visit(LocalDeclStmt)` 的 ConstDecl case 直接发出 `const int32_t NAME = VALUE;`，未考虑 NAME 可能被系统头文件中的宏占用。

**修改**（`src/backend/cgen_stmt.cpp::visit(LocalDeclStmt)`，ConstDecl 分支）：在 `const` 声明前追加一行 `#undef <cName>;`。`#undef` 对非宏名是 no-op，安全无副作用。

```cpp
c_.emitLine("#undef " + cName);   // 新增：清除可能的 windows.h 宏
c_.emitLine("const int32_t " + cName + " = " + valueExpr + ";");
```

**结果**：C2106 模式 I（8 处 Windows API 宏冲突）全部清除。

---

### 主题 2：C2106 Pattern B — Mid$ 语句被当作赋值目标（010r-14）

**问题**：VB6 的 `Mid$(Result, i*4+j+1, 1) = Mid$(BASE64_TABLE, ...)` 应生成对 `vb6_MidSet(...)` 之类的运行时调用，实际生成的是 `Mid_(Result, ...) = Mid_(...)`，左值是函数返回值，触发 C2106。共 32 处。

**根因**：词法器把 `Mid$` 合并为单个 Identifier token（不是 `TokenKind::Mid`），导致 `parser_stmt.cpp` 中 `TokenKind::Mid` 的 dispatch 永不触发，整条语句被当成普通 `AssignmentStmt` 解析，`target` 是 `IndexOrCallExpr`（callee 名为 "mid$" 或 "mid"）。

**修改**（`src/backend/cgen_stmt.cpp::visit(AssignmentStmt)`，新增 lines 141-175）：在赋值语句处理顶端追加检测，若 `target` 是 `IndexOrCallExpr`，且 callee 名匹配 `mid$`/`mid`（大小写不敏感），且参数数量为 2 或 3（positional），则重写为：

```c
vb6_MidSet(&TargetStr, StartPos, [Len], Value);
```

否则按原流程继续。

**结果**：C2106 模式 B（32 处 Mid$ 语句）全部清除。

### 主题 3：C2106 Pattern A — COM 字典 Item 赋值（010r-15）

**问题**：VB6 `dict("key") = value` 中 `dict` 是 COM 对象（如 `Scripting.Dictionary`），其默认成员 `Item` 通过 `vb6_ComCall(obj, L"Item", args, n)` 调用。该返回 `VARIANT*` 非 lvalue，被当左值即 C2106。共约 52 处（Pattern A 总数）。

**根因**：`visit(AssignmentStmt)` 的通用 fallback 路径对左值类型未加分类，直接 emit `target + " = " + value + ";"`，遇到 `vb6_ComCall(...)` 即出错。Set/Let 语句同样存在此问题（Pattern A1，约 6 处）。

**修改**（`src/backend/cgen_stmt.cpp::visit(AssignmentStmt)`，原 lines 673-690）：检测 `target.find("vb6_ComCall") == 0` 时，按 `vb6_ComSetPropArg(callArgs, packFn(value))` 重写。`packFn` 由表达式类型决定（`vb6_ComPackBSTR/Int/Bool/Double/Object/Variant`）。

**结果**：AssignmentStmt 路径下 Pattern A 全部修复；C2106 86→41（剩 41 为 A1/Patern A 在 Set/Let 路径 + Pattern C/D2/F 余项，由 010r-16 处理）。

### 主题 4：C2106 Patterns A1/F/C/D2 统一化 — tryRewriteCOMLvalue（010r-16）

**问题**：010r-15 只在 `visit(AssignmentStmt)` 处理了 Pattern A。但：
- **Pattern A1**：`Set obj.Item(k) = ref` 走 `visit(SetStmt)`，未走 AssignmentStmt
- **Pattern F**：`vb6_ComGetStringProp(obj, L"Name") = value`，COM Property Put
- **Pattern C/D2**：`vb6_X_prop_get_Y(args) = value`，Property Get 被当左值

三者共同点：左值是「COM 调用」或「Property Get 调用」的非 lvalue 返回。需要统一改写。

**修改** — 新增 helper `tryRewriteCOMLvalue()`：

声明位置：`src/backend/cgen.hpp`（`resolveComValue()` 之后）
实现位置：`src/backend/cgen_util.cpp`（lines 1007-1108，`resolveComMarkerForPack()` 之后）

逻辑（三段）：

1. **Pattern A**（`vb6_ComCall(...)` 任意位置）
   ```
   vb6_ComCall(obj, L"Item", args, n) = value
   → vb6_ComSetPropArg(obj, L"Item", args, n, comPackExpr(value))
   ```

2. **Pattern F**（任意 `vb6_ComGet*` 函数作为左值）
   ```
   vb6_ComGetStringProp(obj, L"Name") = value
   → vb6_ComSetProp(obj, L"Name", comPackExpr(value))
   ```
   匹配前缀 `vb6_ComGet`，把 `Get` 改 `Set`、丢弃方法名后多余参数。

3. **Pattern C/D2**（`vb6_<X>_prop_get_<Y>(args) = value`）
   ```
   vb6_cDictionary_prop_get_Item(_vb6_with_X, k) = v
   → vb6_cDictionary_prop_let_Item(_vb6_with_X, k, v)   // Let 语义
   → vb6_cDictionary_prop_set_Item(_vb6_with_X, k, v)   // Set 语义
   ```
   按 `Set`/`Let` 区分用 `prop_set_` 还是 `prop_let_`。

调用点：在三个语句 handler 的 fallback 之前依次插入：
- `visit(AssignmentStmt)`（line ~674，替换原 010r-15 内联检测）
- `visit(SetStmt)`（line ~941，`Set` 语义 → `prop_set_`）
- `visit(LetStmt)`（line ~1203，`Let` 语义 → `prop_let_`）

helper 返回 `true` 表示已 emit 重写语句；返回 `false` 由原流程继续。

**结果**：C2106 86→41（010r-15 之后）→ 35（010r-16 之后，-6 进一步消化的 A1 + F + C/D2）。

### 主题 5：C2106 Pattern J — 同模块函数名遮蔽（010r-16b）

**问题**：VB6 中 `Function Count() As Long` 函数体内 `Dim Count As Long` 后 `Count = 5` 应赋值给**局部变量**（局部遮蔽函数名）。原代码生成 `vb6_cCollection_Count = 5;` 把值赋给函数符号，触发 C2106（非 lvalue）。同类问题：
- `ToolsJs.NewArr`（`Public Function NewArr(...)` + 局部 `NewArr`）
- `Demo.Db`
- `cCryptoHMAC.Secret` 等

**根因**：`cgen_expr.cpp::visit(IdentifierExpr)` 中 `knownLocalVars_` 遮蔽检查带有条件 `(!foundSym || foundSym->isExternal)` — 即「仅当符号不存在或为外部符号时才让局部变量遮蔽」。对**同模块**符号（如 `Function Count` 本身就在当前模块符号表里），条件不满足，fall-through 后命中 Property Get 路径生成 `vb6_cX_Count = ...`。

**修改**（`src/backend/cgen_expr.cpp` line ~316）：去掉 `(!foundSym || foundSym->isExternal)` 条件，让 `knownLocalVars_` 无论符号来源都优先遮蔽。函数体内的自引用（如 `Count = Count + 1` 在 `Function Count` 中赋值给返回值）已由前面 lines 178-191 的 self-reference 处理覆盖，此修改不会破坏自引用语义。

代码改动：
```cpp
// 改前
if (knownLocalVars_.count(lower) && (!foundSym || foundSym->isExternal)) {
    return /* 局部变量名 */;
}
// 改后
if (knownLocalVars_.count(lower)) {
    return /* 局部变量名 */;
}
```

**结果**：C2106 41→35（-6，Pattern J 主要余项被清除，包括 `vb6_ToolsJs_NewArr` / `vb6_Left` 等自赋值案例）。
