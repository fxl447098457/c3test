# Fix 015 — Method chaining 解析 (跨模块 storageKey 冲突版本)

## 概要

错误数 3882 → 3873 (-9). C2039 (not a member) 89 → 81 (-8),
cCryptoHMAC 与 cCryptoHash 完全从 C2039 父类型列表中消失.

本修复解决多级链式调用 `obj.Method1(args).Method2(args).Method3(args)`
仅前两层被解析、后续层回退为点访问 (`.Method3(args)`) 触发 C2039 的问题.
典型案例: `HMAC.Secret(...).DataString(...).ReturnHex(...)` 三级链与
`HMAC.Mode(...).Secret(...).DataString(...).ReturnHex(...)` 四级链.

## 问题分析

### 现象

cCryptoHMAC 类提供 fluent (chain call) API, 方法返回自身类:

```vb
Public Function Mode(ByVal Algorithm As HMACAlgorithm) As cCryptoHMAC
Public Function Secret(...) As cCryptoHMAC
Public Function DataString(...) As cCryptoHMAC       ' 返回自身 → 链可继续
Public Function ReturnHex(...) As String             ' 终结方法
```

在 `Demo.bas` 中调用:

```vb
Debug.Print "SHA256: " & HMAC.Secret("secret").DataString(sText).ReturnHex()
```

未修复前生成的 C 代码:

```c
// 仅 Secret+DataString 被 Fix 015 解析; ReturnHex 退化为点访问
vb6_cCryptoHMAC_DataString(
    &((vb6_cls_cCryptoHMAC){ /*fix015chainDataString*/
        vb6_cCryptoHMAC_Secret(HMAC, vb6_BSTR_FromStr(L"secret"), 0,0,0,0)
    }), sText, 0, 0).ReturnHex(0, 0);   // ← C2039: ReturnHex 不是成员
```

### 根本原因: `getClassMethodReturnType` 受 storageKey 冲突影响

链式调用的核心由 `inferClassTypeOfExpr` 递归推断每一层返回类型:

```
inferClassTypeOfExpr(IndexOrCallExpr(DataString call))
  → recurse: inferClassTypeOfExpr(IndexOrCallExpr(Secret call))
      → recurse: inferClassTypeOfExpr(IdentifierExpr(HMAC)) → "cCryptoHMAC"
      → getClassMethodReturnType("cCryptoHMAC", "Secret") → ???
  → getClassMethodReturnType("cCryptoHMAC", "DataString") → ???
```

`getClassMethodReturnType` 遍历消费模块作用域,
查找 `lowerName == memberLower && sourceModule == className` 的 Function/PropertyGet 符号:

```cpp
for (const auto& [key, sym] : symTab_.moduleScope()->symbols()) {
    if (sym->lowerName != memberLower) continue;
    bool matches = false;
    if (sym->isExternal) {
        if (Symbol::toLower(sym->sourceModule) == classLower) matches = true;  // ← 这里
    }
    ...
}
```

问题: `driver.cpp` 的 `globalPublicSyms` 用 `storageKey` (= lowerName) 去重,
跨模块同名 Public 方法只保留首个注册者:

| Member | Declaring Classes (冲突) |
|--------|---------------------------|
| `Secret` | 仅 cCryptoHMAC (无冲突) |
| `DataString` | cCryptoHash, cCryptoHMAC |
| `Mode` | cCryptoHash, cCryptoHMAC, cDelay, cModbusTransportTCP, cNTPPacket, cSerialFrameParser (6 类) |
| `ReturnHex` | cCryptoHash, cCryptoHMAC, cToolsCrc, cFileEx, cFormater (5 类) |

`Demo.bas` 模块作用域中, `datastring` 外部符号的 `sourceModule` 是首个注册的类
(例如 cCryptoHash), `getClassMethodReturnType("cCryptoHMAC", "DataString")` 因
`sourceModule != "cCryptoHMAC"` 而 `matches = false`, 返回空 → 链式调用断链.

注意: 第一层 `Secret` 是同类内唯一, 无冲突, 故 `Secret(args).DataString(...)` 部分能解析.
但从 `DataString` 链到 `ReturnHex` 时, 需要推断 `DataString` 的返回类型,
而 `DataString` 因冲突无法被找到 → `.ReturnHex` 退化.

类似 Fix 014b 给 `resolveClassMemberCall` 加 Class symbol fallback,
本修复给 `getClassMethodReturnType` 加同等回退 — 但 Class 符号只有 `memberNames`
(字符串列表), 不含返回类型信息. 故需扩展 Class 符号结构.

## 修复方案

本 Fix 由 6 个递进修改组成 (前 5 个在之前会话完成, 第 6 个为本会话核心):

### Fix 015-1: `variableTypeName` 扩展到 Function/PropertyGet 符号

**文件**: `src/semantics/semantic_analyzer.cpp` (~621, ~701)

Pass 1 中, `visit(FunctionDecl)` 和 `visit(PropertyDecl)` 在创建 Function/PropertyGet
符号时, 若返回类型为 `SimpleTypeRef`, 把类型名记入 `sym->variableTypeName`.
此前 `variableTypeName` 仅用于 Variable 符号 (跨模块类实例变量识别);
扩展到 Function/PropertyGet 后用于跟踪方法的返回类类型, 供链式调用解析使用.

### Fix 015-2: `driver.cpp` 外部符号复制 `variableTypeName`

**文件**: `src/driver/driver.cpp` (~1122-1132)

外部符号创建时, `variableTypeName` 此前仅在 `if (srcSym->kind == Variable)` 分支内复制,
导致 Function/PropertyGet 外部符号丢失返回类型名 (尽管 Fix 015-1 已在源端写入).
将赋值语句移出 `if (Variable)` 块, 对所有 Symbol 类型统一复制. 无副作用
(`variableTypeName` 在非 Variable/Function/PropertyGet 符号上始终为空).

### Fix 015-3: 新辅助函数 `canonicalClassName` / `getClassMethodReturnType` / `inferClassTypeOfExpr`

**文件**: `src/backend/cgen_util.cpp` (~1227-1301), `src/backend/cgen.hpp` (~610)

- `canonicalClassName(typeName)`: 在模块作用域查找 Class 符号规范化大小写
  (用户源码可能写 "cWinsock" 但 struct 定义用 "cWinSock"). 找不到则原样返回.
- `getClassMethodReturnType(className, memberName)`: 遍历模块作用域 Function/PropertyGet
  符号, 若 `type == Vb6Type::Object && !variableTypeName.empty()` 则返回规范化的返回类名.
  **本会话添加 storageKey 冲突回退** (Fix 015-6).
- `inferClassTypeOfExpr(expr)`: 递归推断表达式返回的类类型.
  - `IdentifierExpr` → 查 `knownClassVars_` (变量名小写 → 类名)
  - `IndexOrCallExpr` → 进 `callee` (MemberAccessExpr)
    → `inferClassTypeOfExpr(ma.object)` 拿到对象类名
    → `getClassMethodReturnType(objClass, ma.memberName)` 返回方法返回类名

### Fix 015-4: `visit(MemberAccessExpr)` 的链检测

**文件**: `src/backend/cgen_expr.cpp` (~1482)

当 MemberAccessExpr 的 obj 是 `IndexOrCallExpr` (即 `obj.Method(args).Member` 模式),
调用 `inferClassTypeOfExpr(obj)` 推断 obj 的返回类名. 非空则:

- 用 `resolveClassMemberCall(retClassName, memberName)` 解析外部成员函数名
- 将 obj 包装为复合字面量 `&((vb6_cls_X){ /*fix015chainMember*/ <obj_C_expr> })`
- 调用上下文 (`asCallCallee_ == true`): 仅发出裸函数名, 把 wrapped obj 存入
  `pendingChainObj_` 字段, 让调用方在参数处理完成后将其作为第一个 this 参数前置
- 值上下文 (`asCallCallee_ == false`): 直接发出 `func(wrappedObj)` (无默认参数)

### Fix 015-5: `asCallCallee_` 保存/恢复 + `pendingChainObj_` 通信

**文件**: `src/backend/cgen.hpp`, `src/backend/cgen_expr.cpp`, `src/backend/cgen_stmt.cpp`

`visit(IndexOrCallExpr)` 和 `visit(CallStmt)` 中设置 `asCallCallee_=true` 后调用
`emitExpr(callee)` 之前要保存原值, callee 处理完成后恢复 — 否则嵌套 callee
(链中的内部 IndexOrCallExpr) 会把外层 `asCallCallee_=true` 误重置为 false,
导致外层 Fix 015 路径走错分支.

`pendingChainObj_` 是新加的通信通道: 当 `asCallCallee_=true` 时由
`visit(MemberAccessExpr)` 设置, 让 `visit(IndexOrCallExpr)` / `visit(CallStmt)`
在参数处理完成后将其作为 this 指针前置, 而非像往常通过 callee 字符串拆分.
这确保链式调用经过完整的参数签名查找和默认参数填充 (Fix 015-4 直接发
`func(wrappedObj)` 时会跳过默认参数, 导致 `C2198 参数过少`).

### Fix 015-6: **Class 符号 `memberReturnTypes` 表 + 冲突回退** (本会话核心)

**问题**: `getClassMethodReturnType` 的模块作用域迭代在 storageKey 冲突时找不到
目标类的 Function 符号, 返回空 → 链式调用从第二级 (`DataString`) 开始断链.
此问题与 Fix 014b 给 `resolveClassMemberCall` 加的 Class symbol fallback 同源,
但 Class 符号只有 `memberNames` (字符串列表), 不含返回类型信息.

**修复**: 给 Class 符号加 `memberReturnTypes` 字段, 记录每个 Function/PropertyGet
的返回类型名. 该表以 className 为索引, 不受 storageKey 冲突影响.

#### 改动 1: `src/semantics/symbol_table.hpp` (~113)

Symbol 结构体类相关字段中, 在 `memberNames` 后新增:

```cpp
// Fix 015: 成员返回类型表 — 仅记录 Function/PropertyGet 返回类型名为命名类型
// (即 returnType 是 SimpleTypeRef 的成员) 的方法. key=成员名小写, value=返回类型名.
// 用于 method chaining storageKey 冲突场景下的返回类型推断.
std::unordered_map<std::string, std::string> memberReturnTypes;
```

#### 改动 2: `src/semantics/semantic_analyzer.cpp` (~124, ~141)

`analyze()` 中创建 Class 符号的循环 (与 `memberNames` 同时填充):

- **FunctionDecl**: 若 `returnType->kind == SimpleTypeRef`,
  `classSym->memberReturnTypes[lower(name)] = returnType->name`.
- **PropertyDecl**: 仅 `propKind == PropertyGet` 时记录 (Let/Set 无返回值).
  通过前判 `propKind == PropertyGet` 避免后续 Let/Set 覆盖 Get 的返回类型.

#### 改动 3: `src/driver/driver.cpp` (~1115)

外部 Class 符号创建时复制 `memberReturnTypes`:

```cpp
if (srcSym->kind == SymbolKind::Class) {
    extSym->instancing = srcSym->instancing;
    extSym->memberNames = srcSym->memberNames;
    extSym->memberReturnTypes = srcSym->memberReturnTypes;  // Fix 015: 链式返回类型
    extSym->isInterface = srcSym->isInterface;
    ...
}
```

#### 改动 4: `src/backend/cgen_util.cpp` (~1273-1314) `getClassMethodReturnType`

模块作用域迭代失败 (返回 `""`) 之前, 加 Class symbol fallback:

```cpp
// Fix 015: storageKey 冲突回退
const Symbol* classSym = nullptr;
for (const auto& [ckey, csym] : symTab_.moduleScope()->symbols()) {
    if (csym->kind != SymbolKind::Class) continue;
    if (csym->isExternal) {
        if (Symbol::toLower(csym->sourceModule) == classLower) { classSym = csym.get(); break; }
    } else if (isClassModule_ && Symbol::toLower(moduleName_) == classLower) {
        classSym = csym.get(); break;
    }
}
if (classSym) {
    auto it = classSym->memberReturnTypes.find(memberLower);
    if (it != classSym->memberReturnTypes.end()) {
        const std::string& rawRetName = it->second;
        // 校验: 返回类型必须是当前作用域中真实存在的 Class 符号
        // (避免 UDT/Enum/String 误当作可链类)
        for (const auto& [k2, s2] : symTab_.moduleScope()->symbols()) {
            if (s2->kind != SymbolKind::Class) continue;
            if (s2->isExternal) {
                if (Symbol::toLower(s2->sourceModule) == Symbol::toLower(rawRetName))
                    return s2->sourceModule;
            } else if (Symbol::toLower(s2->name) == Symbol::toLower(rawRetName)) {
                return s2->name;
            }
        }
        // 返回类型不是类 (UDT/Enum/String/接口) → 链终止
        return "";
    }
}
return "";
```

注意: `memberReturnTypes` 存储返回类型对应的 SimpleTypeRef 名 (源码原样大写),
所以这里要做 Class 符号存在性校验 + 规范化 — 不直接用 `canonicalClassName`
是因为后者在找不到 Class 时返回原值, 无法区分 "找不到" 与 "名字就是源码原样".

### C2197 (-36) 与 C2198 (+13) 解释

C2197 (参数过多) 大幅减少是因为链式调用此前通过通用 fallback 路径生成代码,
会把 wrapped obj 作为参数 (复合字面量), 此 obj 又被 IndexOrCallExpr 当成函数
额外插入参数 → 整体多了 1-2 个参数 → C2197. Fix 015 后通过 `pendingChainObj_`
正确传递, 参数数量与签名一致, C2197 减少.

C2198 (参数过少) 增加是因为 MSVC 现在能更深入编译更多文件 (cCryptoHMAC 和
cCryptoHash 链成功后不再阻挡后续代码), 暴露原本被 100 错误上限遮挡的预存问题
(如 `vb6_cCsv_prop_get_Value` 调用少传索引参数). 这些是非链式调用的预存 bug,
不在本 Fix 范围内.

## 已知限制

1. **`prop_get_` 前缀启发式可能误判** (Fix 014b 遗留问题在链场景下暴露).
   `vb6_cCryptoHMAC_prop_get_Mode` 是错的 — `cCryptoHMAC.cls` 中 `Mode` 是
   `Function`, 不是 `PropertyGet`, 实际 C 函数应为 `vb6_cCryptoHMAC_Mode`.
   原因: `resolveClassMemberCall` 的 Fix 014b fallback 用 "作用域中是否存在
   `mode$pg` 外部符号" 启发式判断前缀, 但当 6 个类中某个用 PropertyGet 声明
   Mode (它的 `mode$pg` 外部符号被消费模块保留), 该启发式就误判所有类的 Mode
   都是 Property Get. 此问题不会触发 C2039 (函数名前缀错也能过编译), 但会在
   最终链接阶段 `LNK2019: 未解析的外部符号 vb6_cCryptoHMAC_prop_get_Mode` 失败.
   修复方案: 给 Class 符号加 `memberProcKinds` 映射 (lowerName → ProcKind),
   Fix 014b 改用 classSym->memberProcKinds 判断 Function vs PropertyGet,
   而非查作用域中的 `$pg` 外部符号.

2. **`memberReturnTypes` 仅记录命名返回类型**, 不处理 As Variant 返回对象的
   运行时分发场景 (Variant.member 模式). 这是 VB6 动态分发, 需独立 Fix 处理.

3. **目前 `memberReturnTypes` 复制策略完整**, 但若未来 `globalPublicSyms`
   改为 (className, methodName) 复合键去重 (即不再有 storageKey 冲突),
   `getClassMethodReturnType` 的常规迭代路径就能直接命中, 本回退可考虑移除.
   保留作为兜底无副作用, 但代码会更复杂.
