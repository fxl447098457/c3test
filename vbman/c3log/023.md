## 调查

### 根因分层

C2224 在 C3 编译器中来自**5 种独立的类型未解析场景**, 都是同一类后果 (void* 上做 .member 访问):

#### 场景 A: 外部 COM 类字段映射为 void* (166 错误中最大来源)

VB6 中 `Dim Rs As New ADODB.Recordset` 等外部 COM 类. C3 的 `mapTypeRef()` (cgen_base.cpp:983-1102) 由于不知道这些类型在 vtable 层的精确结构, 一律映射为 `void*`. 类结构体里该字段也是 `void* Rs;`:
```c
// cHttpServerSession.h
struct vb6_cls_cDataBase {
    void* Rs;   /* As New ADODB.Recordset */
    ...
};
```

当 VB6 写 `Db.Rs.EOF` 时, MemberAccessExpr 走 fallback 路径 emit 为 `Db->Rs.EOF` — 而在 C 中 `Db->Rs` 是 `void*`, 不可 `.EOF` → C2224.

#### 场景 B: void* 函数参数未注册到 COM dispatch

VB6 中 `Sub Foo(Data As Collection)` 等接口参数. C3 生成参数声明:
```c
void vb6_cX_Foo(vb6_cls_cX* me, void* Data)   /* As Collection */
```

但 `Data.Count` 这类成员访问仍依赖 `knownObjectVars_` 集合判定 — 而被外部 COM 接口/Collection 类型参数填充的 `void*` 没有被注册到这个集合, 所以不走 COM dispatch, 直接 emit `Data.Count` → C2224.

#### 场景 C: Form-instance 被识别为 void*

每个窗体的全局句柄是 `static void* vb6_hwnd_<FormName> = NULL;` (cgen_form.cpp:193). VB6 中 `Me.Height`, `Me.ScaleWidth`, `Me.Move(...)` 等成员访问:

1. **`Me.Height` 模式**: `node.object` 是 `MeExpr` (不是 `IdentifierExpr`). visit(MemberAccessExpr) 主分支 `if (node.object->kind == IdentifierExpr)` 跳过, 触发 fallback emit `vb6_hwnd_<FormName>.Height` → C2224.
2. **`FLogs.ScaleWidth` 模式** (显式窗体名引用): 走 IdentifierExpr 分支命中 `knownFormControls_`, 但 `getControlPropReadFn(Form, "ScaleWidth")` 返回空 (Form case 只覆盖 Caption/Visible/Enabled), warn-and-fall-through 后又掉到 fallback → C2224.

Form-instance 占 C2224 总量 ~50 处, 是单一大类.

#### 场景 D: WithMemberExpr ClassInstance-empty-className fallback

VB6 中 `With foo.Bar: .Count: End With` 模式, 当 `foo.Bar` 的类名未解析时, WithMemberExpr 的 ClassInstance-empty-className 分支原 emit `vb6_ComGetStringProp(tempVar, L"Member")`. 但外层 MemberAccessExpr 的链式 COM 检测2 只匹配 `vb6_ComCallObject`/`ComGetObjectProp` 等特定前缀, 不匹配 `ComGetStringProp`. 导致链式访问无法继续 COM 分派.

#### 场景 E: 类 void* 字段返回值做 callee

VB6 中 `With Session.Remove(...): .Count: End With` 等. `.Remove` 是类方法返回 void* (Collection 类型) 的 COM 对象, 链式 .Count 应走 COM 分派 — 但 Fix 023 之前, IndexOrCallExpr 返回的 `vb6_cClassName_Remove(args)` 字符串不被链式 COM 检测2 匹配, 也不被 Fix 015 类链路 (`inferClassTypeOfExpr`) 解析 (因为返回 void*, inferClassType 返回空) → 落到 fallback emit `vb6_cClassName_Remove(args).Count` → C2224.

### 类 void* 字段的产生 (mapTypeRef)

C3 的 `cgen_base.cpp:mapTypeRef()` 路径 (line 983-1102) 把以下 VB6 类型映射为 C `void*`:
- `Any` → `void*` (line 991-992)
- VB6 内置对象类型 (Object/Collection/StdPicture/etc.) → `void*` (line 1003-1005 `vb6BuiltinObjTypes`)
- ADODB / Scripting / 等已知 COM 对象类型 → `void*` (line 1077-1085 `comObjTypes`)
- 所有未识别类型 (兜底) → `void*` (line 1097+)

类结构体生成 (cgen_base.cpp:290-313) 直接用 `mapTypeRef()` 给字段定型, 所以这些 COM 字段全是 void*.

### knownObjectVars_ 等运行时跟踪集合

C3 codegen 用一组 `set<string>` 在 codegen 过程中跟踪变量类型:
- `knownObjectVars_`: 小写 void* / Object / Collection 变量名 — 走 COM 后期绑定
- `knownTypedComVars_`: 小写前期绑定 COM 变量名 (有 ComClass 符号)
- `knownIfaceVars_`: 小写接口变量名
- `knownVariantVars_`: 小写 Variant 变量
- `knownClassVars_`: 小写 → 类名 (用 `resolveClassMemberCall` 分派)
- `classVoidFieldMap_` (Fix 023 新增): 类名 → 该类的 void* 字段集合

MemberAccessExpr 的 IdentifierExpr 主分支按优先级顺序查这些集合分发 (cgen_expr.cpp:1216-1348).

## 方案

### Fix 023 base: classVoidFieldMap + voidptr 注释标记

在 driver.cpp 的 `runCodeGeneration` 入口处预扫所有模块 AST, 构建 `classVoidFieldMap` (className → set<string> 该类的 void* 字段小写名). void* 判定规则与 `mapTypeRef` 完全一致.

codegen 时:
- 内层 MemberAccessExpr 的 `knownClassVars_` fallback 路径 (cgen_expr.cpp:1627-1663) 在检测到字段是 void* 时, 在 emit 注释中加入 `voidptr` 标记:
  ```c
  Db->Rs  /* class var .Rs field voidptr */
  ```
- 外层 MemberAccessExpr 的链式 COM 检测2 之后 (cgen_expr.cpp:1500-1517) 新增 voidptr 检测块, 识别该注释把访问切换为 COM dispatch.

### Fix 023c: void* 函数参数注册到 knownObjectVars_

在 cgen_decl.cpp 的 3 处参数注册循环 (SubDecl, PropertyDecl, Event/第三处) 添加新代码: 当参数未被前面分支精确注册为 Class/ComClass/Interface/UDT 时, 调用 `mapTypeRef` 查 C 类型, 若是 `void*` 则注册到 `knownObjectVars_`. 让 `As Object` / `As Collection` / `As ADODB.Recordset` 等参数都在 MemberAccessExpr 主路径的 IdentifierExpr 分支 (line 1307 `knownObjectVars_.count(objLower)`) 命中 COM 后期绑定.

### Fix 023d: WithMemberExpr ClassInstance-empty-className fallback 改用 COM marker

修改 `visit(WithMemberExpr)` 的 ClassInstance-empty-className fallback (line 3413-3424), 从直接 emit `vb6_ComGetStringProp` 改为设置 COM marker (`comObjExpr_ = tempVar` 等), 让 `resolveComValue` 在上层消费时根据 unpackType 选择正确的 `vb6_ComGetObjectProp` / `vb6_ComCall` 函数.

### Fix 023e: Form-instance (Me.X 和 FormName.X) 路由 COM dispatch

两部分改动:

1. **新增 MeExpr+Form 早期分支** (cgen_expr.cpp:1138-1177, 在 IdentifierExpr 主分支之前): 当 `node.object->kind == MeExpr` 且 `isFormModule_` 且 `!knownFormName_.empty()` 时:
   - 优先用 `getControlPropReadFn(FrmControlType::Form, node.memberName)` 查已知 Form 控件属性 (Height/Width/Left/Top/Hwnd/Caption/Visible/Enabled/Font*/Color*/etc.) — 若命中则 emit `readFn(vb6_hwnd_<FormName>)` 形式.
   - 未知的 Form 成员 (ScaleHeight/ScaleWidth/Move/Refresh/Show/Print/Cls/Line/...) 设置 COM marker, 让上层 IndexOrCallExpr / AssignmentStmt 通过 `vb6_ComCall/ComGet*Prop` 分派.

2. **修改已知控件分支 Form case** (cgen_expr.cpp:1312-1326): 当 `itCtrl->second == FrmControlType::Form` 且 `readFn` 为空时, 不再 warn-and-fall-through, 而是同样设置 COM marker on form HWND 直接 return.

#### 关于 form HWND 作 IDispatch* 的说明

Form 的 `vb6_hwnd_<FormName>` 在 C3 中是 **Win32 HWND** (`void*` 指向窗口), 而非 IDispatch 指针. 把它当 IDispatch* 通过 `vb6_ComCall` 走 COM dispatch **运行时会 crash** — 这只是**编译 stub** (让 MSVC 接受代码). 真正的运行时正确性需要:
- 方案 A: 为 Form 实现专门的 IDispatch 接口 (查询 QueryInterface 拿到 IDispatch)
- 方案 B: 在 RTL 中添加专用 Form-属性辅助函数 (`vb6_GetFormScaleWidth`, `vb6_MoveForm(hwnd, x, y, w, h)` 等)

考虑到当前 vbman 编译测试目标是**让 DLL link 通过**, 运行时正确性留待后续 fix.

1. **C2440 (1842)** — 占所有错误 55%, 是 vbman 编译瓶颈最大目标. 典型模式:
   - int → VARIANT (整数赋值给 Variant 变量不需显式包装? 检查)
   - SafeArray1D → VARIANT (数组参数传递)
   - UDT 值 → UDT* (ByRef 参数传递)
   - 类实例值 → 类指针 (方法链返回值赋给左值)
   每类都有大量重复模式, 单次 fix 可能减少数百错误.

2. **C2198 + C2197 (528)** — 占 16%, Fix 015 链式调用残留. 与 C2440 部分重叠 (类型转换失败导致参数推断错误).

3. **C2065 (345)** — Top 标识符:
   - `vb6_hwnd_Timer1` (14): Timer 控件 HWND 命名问题
   - `Tstr` (14): 拼写错误或作用域
   - `vb6_cByteBuffer_Size` (11): 类内方法调用前缀问题
   - `vb6_uRect_Left` (8): UDT 字段访问前缀
   - 各类需独立排查.

剩余 C2224 (40) 拆为 6 个独立模式:
- Fix 024: ToolsTlsThunks With-block UDT void* 字段 (10)
- Fix 025: cCsv 链式 vb6_cClass_Method 返回 void* (6)
- Fix 026: cJson TypeOf 返回 void* (5)
- Fix 027: default-prop + .Member 链式 (FLogs + FToastDrawer + FLayer = 7)
- Fix 028: 类字段 As New 另一类成员访问 (cHttpServer + cTimer + cDelay + cTimers + cTlsReMaster + dHttpSvr + ToolsIDE = 12)

建议优先做 C2440 的整体分析, 因为它一项就占 vbman 总错误 55%. 拆完 C2440 几个大模式后, 总数有望降到 1500-2000 区间, 此时再回头收尾 C2224 残留.
