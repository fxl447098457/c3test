# Fix 016: prop_get_ 前缀启发式误判修复 (跨类同名混合 Function/Property 场景)

## 背景

Fix 014b 为 `resolveClassMemberCall` 的 Class 符号 fallback 引入了一个 "$pg 外部符号启发式":
当常规 scope 迭代找不到目标方法时, 检查作用域中是否存在 `<memberLower>$pg` 外部符号,
若存在则判定为 PropertyGet, 发出 `prop_get_` 前缀.

该启发式在跨类同名混合 Function/Property 场景下误判, 同时 dll_entry.c 的 COM 分派表生成
存在同类的跨类名称泄漏问题.

## 问题

### 现象

VB6 中有 13 个方法名在多个类中既是 Function 又是某 Property 变体:

```
async, backcolor, count, data, isvalid, item, items, mode, path, state, tag, timeout, webroot
```

典型冲突: `Mode` 在 6 个类中定义:
- cCryptoHMAC / cCryptoHash: `Public Function Mode(...) As cCryptoHMAC/cCryptoHash` (链式调用, 返回自身类型)
- cDelay / cModbusTransportTCP / cNTPPacket / cSerialFrameParser: `Property Get Mode` / `Property Let Mode`

对 Function 类, 生成代码错误发出 `vb6_cCryptoHMAC_prop_get_Mode(...)` 而非
`vb6_cCryptoHMAC_Mode(...)`. 这不触发编译错误 (MSVC 假设函数存在), 但会在最终链接阶段
产生 LNK2019 (未解析的外部符号 `vb6_cCryptoHMAC_prop_get_Mode`).

### 误判影响范围 (Fix 016 前)

**resolveClassMemberCall 路径** (cgen_expr.cpp MemberAccessExpr 调用):
- `cCryptoHMAC::Mode` — 18 处 (Function 误判为 PropertyGet) [Demo.bas 链式调用]
- `cCryptoHash::Mode` — 8 处 (同上)
- `cCollection::count` — 11 处 (Function 误判)
- `cDataBase::count` — 2 处 (Function 误判)

**dll_entry.c COM 分派表** (cgen_util.cpp generateDllEntry 生成):
- `vb6_cCryptoHMAC_prop_get_Mode` — 2 处 (extern 声明 + 调用, 符号实为 cDelay 的 PropertyGet)
- `vb6_cCryptoHMAC_prop_let_Mode` — 2 处 (extern 声明 + 调用, 符号实为 cDelay 的 PropertyLet)
- `vb6_cCryptoHash_prop_get_Mode` — 2 处 (同上)
- `vb6_cCryptoHash_prop_let_Mode` — 2 处 (同上)

## 根因分析

### 路径 A: resolveClassMemberCall 的 $pg 启发式

`resolveClassMemberCall(className, memberName)` 在常规 scope 迭代找不到符号时
(`chosen == null`) 走 Fix 014b fallback. 该 fallback 查找 className 对应的 Class 符号,
验证 memberName 在 memberNames 中, 然后用 "$pg 启发式" 判断前缀:

```cpp
// 旧代码 (Fix 014b)
std::string pgKey = memberLower + "$pg";
if (symTab_.moduleScope()->symbols().find(pgKey) != ...) {
    prefix = "prop_get_";
}
```

问题: `globalPublicSyms` (driver.cpp:1054-1068) 以 storageKey 去重, 只保留每个
storageKey 的首个注册者. 对 "mode$pg" (PropertyGet), 6 个 PropertyGet 类中只有一个
的 "mode$pg" 外部符号被注入消费模块. 启发式不区分该符号属于哪个类, 对所有类的 Mode
一律判为 PropertyGet.

调试输出确认: `resolveClassMemberCall("cCryptoHMAC", "Mode")` 返回 `chosen=null`,
`foundGet=null`, `foundSubFn=null` — 常规路径完全空手, 走 fallback, 被启发式误判.

### 路径 B: dll_entry.c COM 分派表的跨类名称泄漏

`generateDllEntry()` (cgen_util.cpp) 收集每个协同类 (coClass) 的 Public 方法时,
对每个 `memberName` 遍历 `allSymTabs` 搜索匹配符号:

```cpp
// 旧代码
memSym = symTab_.lookupModule(memberName);       // 当前 symTab_ (最后一个模块)
if (!memSym) {
    for (auto* st : allSymTabs) {                 // 所有模块符号表
        memSym = st->lookupModule(memberName);
        if (memSym) break;
    }
}
// Property Get/Let/Set 同样遍历 allSymTabs
```

问题: 搜索不验证符号归属. 对 cCryptoHMAC 的 Mode:
1. Sub/Function 搜索 "mode" (storageKey) — 因 globalPublicSyms 去重, 可能找到其他类的
   Function "mode", 或找不到 cCryptoHMAC 自己的.
2. PropertyGet 搜索 "mode$pg" — 在 allSymTabs 中找到 cDelay 的 PropertyGet "mode$pg"
   (sourceModule="cDelay"), 不加验证地加入 cCryptoHMAC 的 publicMethodSyms.
3. PropertyLet 搜索 "mode$pl" — 同样泄漏 cDelay/cModbusTransportTCP 的 PropertyLet.

生成时用 `cc.moduleName="cCryptoHMAC"` 拼出 `vb6_cCryptoHMAC_prop_get_Mode` /
`vb6_cCryptoHMAC_prop_let_Mode` — 调用了不存在的函数 (cCryptoHMAC 根本没有
PropertyGet/Let Mode). 同时 cCryptoHMAC 自己的 Function "mode" 因搜索去重而丢失,
dll_entry.c 中完全缺失 `vb6_cCryptoHMAC_Mode`.

## 修复

### Fix 016a: resolveClassMemberCall fallback 改用 memberProcKinds

**symbol_table.hpp** (~125): Class 符号新增 `memberProcKinds` 字段
(`unordered_map<string, ProcKind>`), key=成员名小写, value=过程类型.

**semantic_analyzer.cpp** (~119-170): Pass 1 创建 Class 符号时填充 memberProcKinds,
按读上下文优先级 (Get > Function > Sub > Let > Set) 覆盖:
- SubDecl → PropertyGet 优先保留; 否则写入 Sub
- FunctionDecl → PropertyGet 优先保留; 否则写入 Function
- PropertyDecl Get → 总是写入 PropertyGet (最高优先级)
- PropertyDecl Let → 仅在键不存在或现有是 Let/Set 时写入
- PropertyDecl Set → 仅在键不存在或现有是 Set 时写入

**driver.cpp** (~1117): 外部 Class 符号创建时复制 `memberProcKinds`.

**cgen_util.cpp** resolveClassMemberCall fallback (~1213): 改用 `classSym->memberProcKinds`
判断前缀, 替代 `$pg` 启发式. 保留原启发式作为 memberProcKinds 缺失时的回退 (旧符号兼容).

memberProcKinds 按 className 索引 (每个 Class 符号独立), 互不影响, 彻底消除跨类碰撞.

### Fix 016b: dll_entry.c COM 分派表收集加归属验证

**cgen_util.cpp** generateDllEntry (~73-89): 收集前先构建 `classOwningSymTab` 映射
(className lower → 定义该类的 SymbolTable*), 遍历 allSymTabs 找非外部的 Class 符号.

**cgen_util.cpp** generateDllEntry (~101-160): 成员收集改为:
1. 优先搜索 `ownTab` (类自身符号表) — 本地方法无碰撞.
2. 若 ownTab 未命中, 回退到 symTab_ / allSymTabs 搜索 (兼容路径).
3. 对找到的符号验证归属:
   - 外部符号 (isExternal=true): 检查 `sourceModule == className`
   - 本地符号 (isExternal=false): 检查 `ownTab->lookupModule == memSym`
4. 仅归属当前类的符号才加入 publicMethodSyms.

搜索 ownTab 是关键: 每个类的本地方法符号只存在于定义该类的模块符号表中.
cCryptoHMAC 的 symtab 有 cCryptoHMAC 的本地 Function "mode", 没有 cDelay 的
PropertyGet "mode$pg" (那是外部符号, 注入到消费模块, 不在定义模块).
