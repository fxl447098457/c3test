# C3 静态链接指南

> 本文是 C3 的扩展能力文档（VB6 本身没有静态链接 `Declare` 的语义）。
> 语法参考见《[Declare 语句](vb6-manual/02-语句/Declare%20语句.md)》；
> 命令行参数总表见《[C3 编译选项](../ai/C3_COMPILE_OPTIONS.md)》。
> 实施细节与验收数据见《024-静态库链接计划书》§十二。

## 概述

`Declare` 的 `Lib` 子句除了传统的 DLL 名，还接受**静态库 / 目标文件**形式的取值。
C3 按扩展名分类：

| `Lib` 取值 | 分类 | 行为 |
|---|---|---|
| 裸名 或 `xxx.dll` | 动态 | 沿用 VB6 旧行为（运行期导入 / 导入库） |
| `xxx.lib` | MSVC 静态库 | **本版支持**，编译期寻址 + 链接期真链接 |
| `xxx.obj` | 目标文件 | **本版支持**，同上 |
| `xxx.a` / `xxx.o` | MinGW 归档 | 本版**不支持**（T06 另案），会被诊断 `VB5005` 拒收 |

静态路下 `Declare` 不再生成 `vb6_di_*` 转发桩与 `#pragma comment`，
而是直接声明真实导出符号、把归档作为 `link.exe` 的显式输入。

## 寻址规则（四层）

对每一个静态 `Lib` 引用（以及 `ExtraLib`），C3 依次尝试：

1. **绝对路径** → 直接使用；
2. **带路径分隔符的相对路径** → 相对**工程目录**（`.vbp` 所在目录）解析；
3. **裸文件名** → 在**搜索根**列表里逐个查找；命中即用**第一个**；
4. 全都找不到 → 报错 `VB5004` 并**列出已搜索的全部根**（便于定位）。

搜索根的来源与顺序：

1. `.vbp` 里的 `LibDir=`（可多行、可 `;` 分隔，按书写顺序）；
2. 命令行 `--libdir`（可重复）；
3. 默认根 `<工程目录>\Lib`（存在才参与）。

## 引用方式

### 声明（Declare）

```bas
Declare Function SlAdd Lib "mylib.lib" Alias "sl_add" (ByVal a As Long, ByVal b As Long) As Long
```

### 工程级（.vbp）

```ini
LibDir=third_party;extra_deps
LibDir=more\libs
ExtraLib=helper.lib
ExtraLib=zlib.lib
```

- `LibDir=` 与 `ExtraLib=` 均支持**多行、`;` 分隔的多个值**。
- `ExtraLib` 用于**没有对应 Declare** 的静态库（静态库之间的依赖）。

### 命令行

```
C3 --libdir third_party --libdir extra_deps --extra-lib helper.lib --output-dir out proj.vbp
```

`--libdir` / `--extra-lib` 均可重复出现，与 `.vbp` 键按上述顺序合并。

## 引用了"用不上"的库会怎样

**MSVC 归档是按需拉取的**：链接器只为尚未解析的符号去归档里取成员。
所以——

- 声明了静态库但一次都不调用 → **完全无害**，不报错、不拉成员、其依赖也不会被要求；
- `ExtraLib` 写了**存在的**文件 → 无害（哪怕用不上）；
- `ExtraLib` 写了**哪儿都找不到的**裸名 `.lib` → 链接期 `LNK1181`（见"已知限制"）。

归档成员是 **`.obj` 粒度**的：同一次 `cl /c` 编出的多个函数在同一个成员里，
只调用其中一个也会把整个成员拉进来，**连同它的外部依赖**。
建议一个功能一个 `.obj`，依赖的库用 `ExtraLib` 显式给出。

## C 侧签名怎么对齐（重要）

VB6 声明与库的 C 原型必须**逐参精确一致**：

| VB6 | C（x64 / x86 皆同） |
|---|---|
| `ByVal x As Long` | `intptr_t` / `long long` |
| `ByRef x As Long` | `intptr_t*` |
| `ByVal x As String` | `const char*`（C3 自动做 BSTR→ANSI 临时量并释放） |
| `ByVal x As Integer` | `int16_t` |

- 返回 `As String` 仍是 VB6 语义（`BSTR`），与参数口径不同；
  C 函数返回 `char*` 时请声明为 `As Long`（指针）再自行转换。
- 需要宽字符串参数时用 `DeclareWide`（C3/TwinBASIC 扩展），
  `ByVal x As String` 将直接传 BSTR，不做 ANSI 转换：

  ```bas
  DeclareWide Function SlLenW Lib "mylib.lib" Alias "sl_lenw" (ByVal s As String) As Long
  ' C 侧: long sl_lenw(BSTR s);   // VB6 字符串即 BSTR
  ```

## 调用约定

- C3 的 `Declare` **默认 `__stdcall`**，与 VB6 一致（要 cdecl 得显式写 `Declare ... CDecl`）。
- 但 **MSVC 编译 C 源码的默认是 `__cdecl`**，不是 stdcall。给 VB6 用的静态库请**显式**写
  `__stdcall`（或整库加 `/Gz`），否则归档里的符号是 `_name`，而 C3 声明要的是 `_name@N` →
  **x86 下链接期报 `LNK2019: 无法解析的外部符号 _name@16`**。
  这是刻意的安全失败：名字里带参数字节数，签名对不上就解析不了。
- 库确实是 `__cdecl` 时，声明写成 `Declare Function F Lib "x.lib" Alias "name" CDecl (...) As ...`。
- **x64 下 `__cdecl` 与 `__stdcall` 是同一套 ABI**（只有一个约定），
  所以上面这条只在 `--arch x86` 时产生后果。

## 逃生舱：`Alias` 字面写完整修饰名（含 `@N`）

C3 默认按声明自动算 x86 stdcall 修饰名。名字对不上时也可以**字面**指定链接符号，
`@` 是合法的（C3 用 `/alternatename` 把内部标识符桥到真实符号，已实测 link.exe 14.29）：

```bas
' C 侧: intptr_t __stdcall sl_mul3(intptr_t, intptr_t, intptr_t);  → x86 符号 _sl_mul3@12
Declare Function Mul3 Lib "mylib.lib" Alias "_sl_mul3@12" (ByVal a As Long, ByVal b As Long, ByVal c As Long) As Long
```

- 写了 `Alias "_xxx@N"` 就**完全按字面**：C3 不再自动加前缀/算 `@N`，并把该字面值
  当引用名做归档符号比对 —— 归档里只有差个 `@N` 的近似形态（如 `_sl_mul3@8`）时，
  编译期直接报 `VB5008` 指出库里实际的名字。
- 该逃生舱对 `__cdecl` 库同样可用（`Alias "_name"`），也是从工具链不认识的
  修饰名恢复的兜底写法。
- **x64 注意**：x64 符号没有 `_` 前缀和 `@N`。x64 构建时 `Alias "_foo@12"` 会按字面
  交给链接器，除非归档里真有人字面导出了这个串，否则 `LNK2019`。x64 下请写
  `Alias "foo"` 或干脆省略 `Alias`。

### ⚠️ 声明宽度写错，编译器不会替你发现 —— 请逐参精确对齐上表

x86 的 `@N` 只挡得住**元数**变化和**栈槽字节数**变化（如 `Long`↔`Double`）；它挡不住
**同一槽位类型内部的宽度差**（`Integer` 与 `Long` 在 x86 上都只占 4 字节栈槽 → `@N` 相同 →
链接器眼里是同一个符号）。x64 则**完全没有**这层保护。实测同一条错误声明
（`ByVal a As Long` 误写成 `ByVal a As Integer`，C 侧是 `long`）：

| | x86 | x64 |
|---|---|---|
| 链接诊断 | 无 | 无 |
| 运行结果 | 恰好正确（**巧合**，别依赖） | **每次运行都不同的垃圾值** |

想要一个**会报错**的安全网，只有一条：把参数写错成**不同个数**（→ `LNK2019`）。
结论：静态库这条路，**VB6 声明的每个参数类型都必须和库的 C 原型严格一致**，这靠人，不靠工具。

## 编译库

x64（默认）：

```bat
cl /c /nologo mylib.c
lib /nologo /OUT:mylib.lib mylib.obj
```

x86（库必须与目标架构一致，混用只会有链接器警告 `LNK4272`）：

```bat
cl /c /Gz /nologo mylib.c   &rem /Gz = 默认 __stdcall，符号变成 _name@N
lib /nologo /OUT:mylib.lib mylib.obj
```

`/Gz` 把未标约定的 C 函数默认成 `__stdcall`，可整库替代逐个写 `__stdcall`。

### 编库时加 `/Gy /Gw`：让 exe 只带走真正用到的函数

链接器从归档"引用即拉入"的单位是 `.obj` 成员——但**拉进来 ≠ 留下**：编译时开了
函数级拆分的成员，链接器能把没被引用的函数/数据逐个丢弃。前提是**编库的一方**开了：

- MSVC：`/Gy`（每函数独立 COMDAT 节）+ `/Gw`（全局数据也 COMDAT）；
  链接时 `/OPT:REF`（默认开）扔未引用节，`/OPT:ICF` 合并相同节；
- GCC/Clang 等价物：`-ffunction-sections -fdata-sections` + 链接 `--gc-sections`。

```bat
cl /c /Gz /Gy /Gw /nologo mylib.c
lib /nologo /OUT:mylib.lib mylib.obj
```

不加的话，调用库里任何一个函数都会把**整个 .obj 成员**（该编译单元的全部函数，
连同其外部依赖）连进最终 exe。库越大，这条越重要。仍无法消除的残留：静态初始化
等有副作用的节链接器不敢扔，这是各语言/工具链共同的硬限制，不是 C3 特有。

## 已知限制（本版）

1. **MinGW 的 `.a` / `.o` 不支持**（T06 另案）—— 会得到 `VB5005` 诊断而不是错误链接。
2. `ExtraLib` 写了不存在的裸名 `.lib` 时，错误只有裸的
   `LNK1181: 无法打开输入文件"nope.lib"`，没有 C3 上下文提示（不提示"是否忘了 `LibDir=`"）。
3. 架构混用（x64 归档喂给 `--arch x86`）目前只有链接器 `LNK4272` 警告，
   C3 编译期尚不读归档架构。
4. x64 下签名宽度错误无任何诊断（见上文告警框）。
