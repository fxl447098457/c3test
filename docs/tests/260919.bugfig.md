## B1：BSTR 拼接上下文里的标量返回函数漏转换

### 现象

`&` 拼接的右（或左）操作数若是"返回整型/浮点的内建函数"，生成的 C 代码**不做取字符串转换**，直接把标量塞进 `vb6_BSTR_Concat`：

```c
// Err.Number 为 5 时 → 按地址 5 解引用 → 0xC0000005
vb6_BSTR_Concat(vb6_BSTR_FromStr(L"a="), vb6_ErrNumber())
```

### 证据：`--emit-c` 逐形态对照 **【实测】**

样本 `tmp/errnum_repro.bas`（本次分析用，未入库），执行：

```bat
.build\C3.exe tmp\errnum_repro.bas --emit-c --output-dir tmp\out
```

| 源码形态 | 生成的 C | RTL 返回类型 | 结果 |
| --- | --- | --- | --- |
| `"a=" & Err.Number` | `vb6_BSTR_Concat(..., vb6_ErrNumber())` | `int32_t` | **漏转换** |
| `"b=" & e1`（`e1 As Long`） | `vb6_BSTR_Concat(..., vb6_CStrLong(e1))` | — | 正确 |
| `"c=" & CStr(e1)` | `vb6_BSTR_Concat(..., vb6_CStrLong(e1))` | — | 正确 |
| `"d=" & Now` | `vb6_BSTR_Concat(..., vb6_CStrDate(vb6_Now()))` | `double` | 正确 |
| `"e=" & UBound(Array(1, 2))` | `vb6_BSTR_Concat(..., vb6_UBound(_arr_0, 1))` | `int32_t` | **漏转换** |
| `"j=" & App.Path` | `vb6_BSTR_Concat(..., vb6_App_Path())` | `BSTR` | 正确 |
| `"k=" & Screen.Width` | `vb6_BSTR_Concat(..., vb6_Screen_Width())` | `int32_t` | **漏转换** |

关键对照：**同样一个 `Err.Number`，先赋值给 Long 变量再拼接就正确**（第 2 行）。转换与否取决于操作数能否被判定出具体类型，而不是取决于语义需要。

### 原因（三层）

**第一层 —— 判定是白名单，不是类型。**
`wrapToBSTR` 早期的显式分支（`:29-36`）只认 `vb6_ComGetIntProp` / `vb6_ComGetDoubleProp` 等少数几个名字，随后 `:72-92` 有一份"数值函数 → `vb6_CStrLong`"的手工清单，只列了 19 个函数名：`vb6_CLng` / `vb6_CInt` / `vb6_Len` / `vb6_InStr` / `vb6_Abs` / `vb6_VarType` …… `vb6_ErrNumber`、`vb6_UBound`、`vb6_Screen_Width`、`vb6_Asc`、`vb6_Day` 均不在其中。

缺口规模 **【实测】**（`tmp/check_gap.py`）：RTL 中声明为 `int32_t` / `int16_t` / `uint8_t` / `double` / `float` / `intptr_t` 且未出现在该清单的 `vb6_*` 函数共 **263 个**。清单式判定不可能覆盖。

**第二层 —— 兜底直接假定为 BSTR。**
未命中清单后落到 `cgen_expr_binary_util.cpp:105`：

```cpp
return expr;  // 其他vb6_函数假定为BSTR
```

这个兜底是"默认安全"的反面 —— 对绝大多数返回值不是 BSTR 的 `vb6_*` 函数，它给出的是错误答案。

**第三层 —— 两个"提前返回"把判定挡在了后面。**
`wrapToBSTR` 的判定顺序是"先匹配一串字符串、命中即返回"，缺陷来自其中**两处**不同的提前返回。它们各自漏掉一类输入：

**机制 ①（前缀兜底）**：`cgen_expr_binary_util.cpp:63` 的 `if (expr.find("vb6_") == 0)` 块在 `:105` 无条件 `return expr`。**只要表达式以 `vb6_` 开头且不含字符串实参，就永远走不到后面基于 `node` 的类型推断。**

**机制 ②（子串未锚定）**：`:37` 的 `if (expr.find("vb6_BSTR") != std::string::npos) return expr;` —— **`find(...) != npos` 不锚定开头，实参里出现 `vb6_BSTR` 就会命中。** 于是任何"带字符串字面量实参的标量函数"都在这里被当成 BSTR 直通：

```c
vb6_BSTR_Concat(vb6_BSTR_FromStr(L"b="), vb6_Len(vb6_BSTR_FromStr(L"abc")))
//                                       ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 实参含 vb6_BSTR，整体被判为"已是 BSTR"
```

**实测证据【实测】**（样本 `"x=" & <fn>`，逐条 `--emit-c`）：

| 表达式 | 生成的右操作数 | RTL 返回 | 机制 | 结果 |
| --- | --- | --- | --- | --- |
| `Err.Number` | `vb6_ErrNumber()` | `int32_t` | ① | **漏转换** |
| `UBound(Array(1,2))` | `vb6_UBound(_arr_0, 1)` | `int32_t` | ① | **漏转换** |
| `Screen.Width` | `vb6_Screen_Width()` | `int32_t` | ① | **漏转换** |
| `Len("abc")` | `vb6_Len(vb6_BSTR_FromStr(L"abc"))` | `int32_t` | ② | **漏转换**（注：`vb6_Len` **在**数值清单 `:79` 里，仍被 ② 挡掉） |
| `InStr("abc","b")` | `vb6_InStr(1, ...)` | `int32_t` | ② | **漏转换**（`vb6_InStr` 在清单 `:81` 里） |
| `Val("1.5")` | `vb6_Val(vb6_BSTR_FromStr(L"1.5"))` | `double` | ② | **漏转换** |
| `Asc("A")` | `vb6_Asc(vb6_BSTR_FromStr(L"A"))` | `int32_t` | ② | **漏转换** |
| `Abs(-1.5)` | `vb6_CStrLong(vb6_Abs((-1.5)))` | `double` | — | 命中清单（且无字符串实参） |
| `Sqr(2)` | `vb6_CStrLong(vb6_Sqr(2))` | `double` | — | 命中清单 |
| `UCase("x")` / `Left("a",1)` | 裸调用 | `BSTR` | ② | 正确（返回值本就是 BSTR） |

**这张表暴露的关键点：数值清单（`:72-92`）对带字符串实参的函数形同虚设** —— `vb6_Len` / `vb6_InStr` 明明写在清单里，却因为 `:37` 的未锚定子串检查在更前面返回而永不生效。

**这不是新问题，项目已经修过同族缺陷。** `ai/C3_FIX_HANDOFF.md` 记录的 **092a** 正是同一模式：

> BSTR 形参提取跳过条件：子串 → 顶层。`paramBase == String` 分支原用 `argVal.find("vb6_BSTR")` 子串判定"已是 BSTR" → …… 改为 4 项**顶层前缀**白名单

092a 修的是**实参路径**的未锚定子串判断，而 `wrapToBSTR` 里的同一模式从未修 —— `:37` 至今仍是 `find != npos`。

**后果分三档 —— 取决于漏传的标量是什么类型 【实测】**（一次编译 `Sqr`/`Abs`/`Val`/`Len`/`UBound` 五形态，取全量诊断）：

| 漏传类型 | MSVC 诊断 | 后果 |
| --- | --- | --- |
| `int32_t` → `BSTR` 形参 | `warning C4047`（"BSTR" 与 "int32_t" 间接级别不同）+ `C4024` | **仅警告，编译通过** → 运行期把整数当指针 → `0xC0000005` |
| `double` → `BSTR` 形参 | **`error C2440`**（无法从 "double" 转换为 "BSTR"） | **编译直接失败** |

即：**整数型漏转换是"静默误编"（编译过、运行崩），浮点型漏转换是"编译报错"**。前者危险得多 —— 它绕过了"不支持的语法必然报错，绝不静默误编"这条信条。

实测诊断原文（`output/c3-error.log`，对应的生成行为 `m.c`）：

```text
m.c(14): error C2440: 无法从 "double" 转换为 "BSTR"          ← vb6_Val(...)
m.c(15): warning C4047: "BSTR" 与 "int32_t" 的间接级别不同    ← vb6_Len(...)
m.c(19): warning C4047: "BSTR" 与 "int32_t" 的间接级别不同    ← vb6_UBound(...)
```

**是否所有漏转换都会崩：** 不一定。C4047 只是警告，实际后果取决于调用约定 —— 64 位下整数走 `rcx`/`rdx`，指针也在同一寄存器，行为与"把整数当指针"一致；但若该函数返回 0（如 `Err.Number` 在无错误时），解引用 NULL 同样崩。**这属于典型 UB，不能依赖任何"有时能跑"的观察。**

### 修复方案

#### 方案 A（推荐）：两处提前返回都改为"精确判定才返回"

**必须两处一起改**，只改一处则另一类输入仍漏（见上文机制 ①②）。

**A-1 修 `:37` 的未锚定子串检查（影响面更大，建议先做）**

```cpp
// 现状：实参含 vb6_BSTR 即整体直通 → Len("abc") / InStr(...) / Val(...) / Asc(...) 全漏
if (expr.find("vb6_BSTR") != std::string::npos) return expr;
```

参照 092a 的做法改为**顶层前缀**判定（表达式本身就是某个 BSTR 返回函数调用），而不是"内部含有"。可复用的判据是 `:19-27` 已有的 `expr.find(...) == 0` 模式 —— 把"以 BSTR 返回函数开头"逐个列出，或在调用 `wrapToBSTR` 之前先用 `inferExprType(node)` 判出具体类型来做主判据。

**A-2 修 `:63` 的前缀块兜底**

`:105` 的 `return expr; // 其他vb6_函数假定为BSTR` 改为落到块外，交给 `:110` 起的 `inferExprType(node)` 判定：

```cpp
if (expr.find("vb6_") == 0) {
    // Date 类 / 数值函数清单 —— 命中即返回（保持现状）
    ...
    // 兜底不再 return expr；落到块外走 node 类型推断
}
```

**为什么落到 `inferExprType(node)` 是安全的**：两种结果都是正确的 BSTR ——
- 识别出具体类型（如 `Long` / `Double`）→ 生成对应 `vb6_CStrXxx(...)`。`Err.Number` 正是这条：`cgen_util_type.cpp:109` **已经**把它判成 `Vb6Type::Long`；
- 识别不出 → 回退 `Vb6Type::Variant`（`:189`）→ `vb6_CStr(vb6_VariantFromValue(x))`。`_Generic`（`vb6rtl_variant.h:134-152`）按实参 C 类型分派，`int` → `vb6_VariantLong`、`double` → `vb6_VariantDouble`、`wchar_t*` → `vb6_VariantString`、`vb6_VARIANT` → identity 直通 —— 对 BSTR 返回也安全。

即：**不再存在"静默传标量"，风险从"猜错就 UB"变成"多套一层转换"。**

**改动面**：前置的 21 条 BSTR 直通（`:39-60`，A-1 若改为顶层判定则这些正是保留项）与数值清单（`:65-92`，A-2 后**首次真正生效**）行为不变或由错转对；只有"清单外 + 无字符串实参"这一类改变生成形态。

- **必须防的回归**：`wrapToBSTR` 是 `&` 与 `+` 两条拼接路径共用的热点函数。历史上同族改动翻过车 —— `092h` 曾因泛用实参包装把 bisect 基线从 30 打到 81 后回退。**要求**：改完先跑 `--emit-c` 逐字节对照（改前/改后各跑一遍，采样面覆盖 `tests/*.bas` 全量 + 代表 `.frm`），再做一次生成 C 的 grep 抽查，最后才跑全量回归（基线 `PASS=82 / FAIL=0 / SKIP=1 / TOTAL=83`）。
- **预期的 diff 形态**：上表"漏转换"各行从裸调用（或"实参含 BSTR"的误判）变成带包装；**返回值本就是 BSTR 的函数（`UCase` / `Left` / `App.Path` / `vb6_BSTR_*`）与字符串字面量必须零变化**。若 `--emit-c` 对照里出现后者变化，说明 A-1 收窄过头，应回退重做。
- **建议分两次提交**：A-1、A-2 各自独立跑一轮 `--emit-c` 对照。合并提交会让 diff 混在一起，回归时无法归因到具体哪一处。

#### 方案 B（更稳但更大）：在 `inferExprType` 内部补内建函数的返回类型

在 `cgen_util_type.cpp:83-98` 的 `IndexOrCallExpr` 分支加一条：先查 `getRuntimeParamCType` 同族的 RTL 签名表（`cgen_util_type.cpp:388-492`），用函数的 RTL 返回类型映射到 `Vb6Type`。

- 优点：修的是类型推断本身，`wrapToBSTR` 之外的其他消费者（`isDefinitelyVariantExpr`、算术提升、Debug.Print 分支）一并受益。
- 缺点：那张表**只有参数类型，没有返回类型**（`getRuntimeParamCType` 的语义就是"参数索引 → C 类型"），要新增 `getRuntimeReturnCType` 与第二张表；表规模约 100 项，需要逐项核对 RTL 头文件，工作量大且容易表头与 RTL 脱节。
- 结论：**不建议本次做**。方案 A 已能消除崩溃，B 留作技术债。

#### 方案 C（收尾）：`Err` 家族在语义层推断为具体类型

`Err.Number` → Long、`Err.Description` / `Err.Source` → String。改动点是语义层的内建对象成员类型登记。

- **现状比预想好** **【实测】**：`inferExprType` 的 `MemberAccessExpr` 分支（`cgen_util_type.cpp:106-113`）**已经**把 `Err.Number` 判成 `Vb6Type::Long`、`Err.Description` / `Err.Source` 判成 `String`。语义层不需要新建登记。
- 生成点有 3 处，且都只吐字符串、不吐类型：`cgen_expr_with.cpp:196`、`cgen_expr_member_precheck.inc:35`、`cgen_expr_ident_dispatch.inc:35`。
- **结论**：方案 A-2 落地后，`Err.Number` 会自然走上正确的 `Long` 分支（因为 `node` 推断已就绪）。方案 C 因此**没有独立工作量**，降级为"方案 A 的验收点之一"：改完后 `--emit-c` 必须看到 `vb6_CStrLong(vb6_ErrNumber())`。
- **一处偏差另行处理**：`Err.HelpFile` 生成 `(BSTR)0`、`Err.HelpContext` 生成 `0`（`cgen_expr_with.cpp:199-200`），但 `cgen_util_type.cpp:111` 把两者都判成 `String`。`HelpContext` 生成整数 `0` 而类型被告知是 String → 若落进"String 分支返回裸 expr"就会直通。当前无崩溃报告，建议单独核实后另行处理，不并入本次修复。

### 建议实施顺序

1. **B2**（退出码）—— 独立于生成器，改动最小，可单独验证。
2. **A-1**（`:37` 未锚定子串检查）→ `--emit-c` 逐字节对照 → 全量回归。
   - 覆盖面最大（`Len` / `InStr` / `Val` / `Asc` 等带字符串实参的标量函数全在这一类），且与 `092a` 的既有修法同族、有先例可参照。
3. **A-2**（`:63` 前缀块兜底）→ 同样跑 `--emit-c` 对照 → 全量回归。
   - 覆盖 `Err.Number` / `UBound` / `Screen.Width` 这类无字符串实参的。
4. **B3**（数值清单浮点截断，见附一）→ 用诊断档位验收（`C4244` 归零）。
5. 方案 B（`inferExprType` 补内建返回类型）登记为技术债，不排期。

方案 C 无独立步骤 —— 它是 A-2 的验收点（见上）。

### 验证用例建议

新增 `tests/test_bstr_concat_scalar.bas`（命名与内容按仓库用例风格），断言写文件（不依赖 stdout，遵守差分硬规则）：

| 用例 | 期望 | 覆盖机制 |
| --- | --- | --- |
| `On Error Resume Next` + `"x=" & Err.Number`（无错，值为 0） | 输出 `x=0`，退出码 0 | ① |
| 触发错误后 `"x=" & Err.Number`（值为非 0，如 5 / 53） | 输出对应数字，**不崩** | ① |
| `"x=" & UBound(Array(1,2))` | `x=1` | ① |
| `"x=" & Len("abc")` | `x=3` | **②**（`vb6_Len` 在清单内却被 ② 挡掉） |
| `"x=" & InStr("abc","b")` | `x=2` | **②** |
| `"x=" & Val("1.5")` | 与 VB6 原生一致 | ② + B3（**当前编译就报 C2440**） |
| `"x=" & Asc("A")` | `x=65` | ② |
| `"x=" & Abs(-1.5)` / `& Sqr(2)` | 与 VB6 原生一致 | B3（当前被截断成整数） |
| `"x=" & "str"` / `& UCase("a")` / `& Left("abc",1)` / `& App.Path` | 保持现值 | 回归护栏（BSTR 返回，不得改变） |

**三个必须满足的要求：**
1. **至少要有一个让 `Err.Number` 取到非零值** —— 只有非零才能区分"正确转换"与"传了 NULL 恰好没崩"。
2. **必须同时含"带字符串实参"与"不带字符串实参"两类** —— 前者验机制 ②，后者验机制 ①。只测一类会漏掉另一处。
3. **必须同时含整数型与浮点型** —— 整数型是"编译过、运行崩"，浮点型是"编译报 C2440"。两者用 `--syntax-only` 或编译退出码都验不到整数型那一类，**整数型必须实跑进程看退出码**。

**验收断言建议按诊断档位分两层：**
- **编译期**：改完后 `scripts\compile.bat` 对该用例的 `c3-error.log` 中，`C4047` / `C4024` / `C2440` / `C4244` **全部为 0**。这一层能立刻抓到 B1 与 B3 是否真修好，不需要运行。
- **运行期**：产物写出的文件内容与 VB6 原生对照一致，退出码 0。

## B2：`-h` / `--help` / `--version` 退出码为 1

### 现象 **【实测】**

| 命令 | 退出码 | 期望 |
| --- | --- | --- |
| `C3.exe --version` | 1 | 0 |
| `C3.exe -V` | 1 | 0 |
| `C3.exe -h` | 1 | 0 |
| `C3.exe --help` | 1 | 0 |
| `C3.exe`（无参数，等同 `-h`） | 1 | 0 |
| `C3.exe --nosuchopt`（未知选项） | 1 | 1 ✓ |
| `C3.exe -O 2`（无源文件） | 1 | 1 ✓ |

"打印帮助并主动退出"被当成失败返回。脚本/CI 里 `c3 --version` 会被判为失败。

### 代码位置

```
src/driver/driver_args.cpp:24    return {opts, 0};   // 无参数 → 显示帮助
src/driver/driver_args.cpp:32    return {opts, 0};   // -h/--help
src/driver/driver_args.cpp:36    return {opts, 0};   // -V/--version
src/driver/driver_args.cpp:141   resultCode = 1;     // 未知选项
src/driver/driver_args.cpp:150   resultCode = 1;     // 未指定源文件
src/driver/driver_args.cpp:154   return {opts, resultCode};
src/driver/driver_compile.cpp:22-28
```

```cpp
CompileResult Driver::compile(int argc, char* argv[]) {
    auto [opts, code] = parseArgs(argc, argv);
    if (code != 0 || opts.sourceFiles.empty()) {
        return {false, "", 1, 0};   // ← 一律 errorCount=1，main 据此返回 1
    }
    return compile(opts);
}
```

### 原因

`parseArgs` **已经**用 `code` 区分了三种情况 —— 显示帮助后退出（`0`）、未知选项（`1`）、无源文件（`1`）。但 `compile()` 把 `code != 0 || sourceFiles.empty()` 合并成一个条件，统一返回 `errorCount = 1`。`main.cpp:114-119` 于是只看得到 `errorCount == 0`，返回 1。

`driver_args.cpp:32` 的注释 `// 0 = 显示帮助后退出` 说明原意就是返回 0 —— 是 `compile()` 这一层把区分丢掉了，不是 `parseArgs` 的错。

### 修复方案

**方案 B（推荐）**：在 `compile()` 里保留 `parseArgs` 的 `code`，只在"确实有源文件但编译失败"时算错误。

```cpp
CompileResult Driver::compile(int argc, char* argv[]) {
    auto [opts, code] = parseArgs(argc, argv);
    if (code != 0) {
        return {false, "", 1, 0};          // 参数错误（未知选项 / 无源文件）
    }
    if (opts.sourceFiles.empty()) {
        return {false, "", 0, 0};          // 已显示帮助，正常退出
    }
    return compile(opts);
}
```

改动 3 行，`CompileResult.success` 语义不变（帮助/版本本来就不是成功编译）。

**方案 A（替代）**：给 `parseArgs` 的返回加第三种码（如 `2` = 已显示帮助正常退出），`compile()` 判 `code == 2` 时返回 `errorCount = 0`。改动更大，且 `pair<CompileOptions,int>` 的 int 语义会变得隐晦 —— 不如方案 B 直观。

### 风险评估

- **无脚本依赖** **【实测】**：`grep -rn --version tests/*.ps1` 无命中；`scripts/release.bat:40-51` 里的 `--version` 是 `release.bat` **自己的**参数（`set "VER=%~2"`），不是调 C3。改退出码不会破坏现有自动化。
- **无测试依赖** **【实测】**：`tests/run_tests.ps1` 未对 `-h` / `--version` 的退出码做断言。
- **潜在影响面**：如果将来有人在 CI 里用 `C3.exe --version` 做"工具链可用性探测"，改之前判失败、改之后判成功 —— 这是修复方向，不是回归。
- **验收**：`C3.exe --version; echo %ERRORLEVEL%` 与 `-h` / `--help` / `-V` / 无参数 五项均为 0；`--nosuchopt` 与"无源文件"仍为 1。

## 附一：数值清单里 `CStrLong` 与 RTL 返回类型不一致 **【实测，已确认】**

`cgen_expr_binary_util.cpp:72-92` 的数值清单把**全部命中项**都归到 `vb6_CStrLong`，但其中多项的 RTL 返回类型是 `double` / `float`：

| 函数 | RTL 声明 | 清单归到 | 影响 |
| --- | --- | --- | --- |
| `vb6_Sqr` | `double` | `vb6_CStrLong` | 小数被截断 |
| `vb6_Abs` | `double` | `vb6_CStrLong` | 小数被截断 |
| `vb6_CDbl` | `double` | `vb6_CStrLong` | 小数被截断 |
| `vb6_CSng` | `float` | `vb6_CStrLong` | 小数被截断 |
| `vb6_Timer` | `double` | `vb6_CStrLong` | 小数被截断 |
| `vb6_Rnd` | `float` | `vb6_CStrLong` | 小数被截断 |
| `vb6_Fix` | `double` | `vb6_CStrLong` | 语义本身即取整，影响小 |
| `vb6_Int` | `double` | `vb6_CStrLong` | 语义本身即取整，影响小 |

**已确认，不只是理论推断**：编译 `s = "sqr=" & Sqr(2)` / `& Abs(-1.5)`，MSVC 对该行报出两个警告 ——

```text
m.c(12): warning C4244: 从 "double" 转换到 "int32_t"，可能丢失数据   ← vb6_CStrLong(vb6_Sqr(2))
m.c(13): warning C4244: 从 "double" 转换到 "int32_t"，可能丢失数据   ← vb6_CStrLong(vb6_Abs((-1.5)))
```

即 `double` 在调用边界被隐式截断为 `int32_t`。`Sqr(2)` 会输出 `1` 而非 `1.4142135623731`；`Abs(-1.5)` 会输出 `2`（四舍五入）而非 `1.5`。

（注：`vb6_CStrLong` / `vb6_CStrDbl` 最终都走同一个 `vb6_Format`，差异在 VARIANT 类型标记 `VT_I4` vs `VT_R8` —— **而截断发生在进入函数之前**，所以无论 `vb6_Format` 如何实现，值已经丢了。）

**与 B1 的关系**：这是同一个函数的另一个独立缺陷。B1 是"该转换的漏转换"（两处提前返回），本条是"转换的目标类型选错"（清单一律 `CStrLong`）。两者都源于同一段手工清单。

**建议**：不并入 B1 一起改。B1 落地验证通过后单独修 —— 修法是按 RTL 返回类型把清单拆成 `CStrLong` / `CStrDbl` 两组。**验收**：上述两个 `C4244` 警告消失，且 `"x=" & Sqr(2)` 的输出与 VB6 原生一致。

## 附二：本次分析的可复现步骤

```bat
REM 1) 生成 C 代码，直接读拼接形态
.build\C3.exe <样本>.bas --emit-c --output-dir <临时目录>

REM 2) 在生成的 C 里定位拼接行，逐条核对操作数形态
findstr /C:"vb6_BSTR_Concat" <临时目录>\*.c

REM 3) 想同时拿到 MSVC 诊断（C2440/C4047/C4244 分档）就完整编译一次，
REM    诊断落在 output\c3-error.log（与 C3.exe 自己的 run.log 是两个文件）
scripts\compile.bat <样本>.bas

REM 4) 退出码
.build\C3.exe --version & echo %ERRORLEVEL%
.build\C3.exe --nosuchopt & echo %ERRORLEVEL%

REM 5) 核对某个 vb6_* 函数的真实返回类型
findstr /R /C:"vb6_ErrNumber" src\rtl\core\vb6rtl\*.h
```

**判定要点**：凡是 `vb6_BSTR_Concat` 的实参不是 `vb6_BSTR_*` / `vb6_CStr*` / 字符串字面量形态，就是本缺陷的候选；再查该函数的 RTL 声明确认返回值是否非 BSTR。

**只跑 `--emit-c` 拿到的是代码形态，不是后果** —— 后果要靠第 3 步的 MSVC 诊断（或实际运行）才能分档。本次分析中"整数漏转换仅警告"这一关键结论就来自这一步，只看生成的 C 是得不出来的。
