# Fix 033 — 跨模块 storageKey 冲突导致类成员调用参数签名错误 (C2197/C2198)

## 错误现象

### 问题：C2197 "too many arguments" 234 例 + C2198 "parameter not enough" 部分例

在类模块中调用另一类实例的方法时，C3 使用错误的参数签名匹配，导致生成的 C 调用实参数量与形参不匹配。

典型场景（`vbman/src/Winsock/cWinSock.cls`）：

```vb6
Private m_oSocket As cTlsSocket
' ...
m_oSocket.Create 0, eSocketType, , , , , , , , 1
```

`m_oSocket` 声明为 `cTlsSocket` 类型，`cTlsSocket.Create` 有 4 个 Optional 参数（第 1062-1066 行）。但 C3 生成的 C 调用传了 11 个实参（5 个参数值 + 5 个 `_has_` 标志 + `me`）：

```c
// 错误: 使用 cAsyncSocket.Create 的签名 (5 Optional) 填充 cTlsSocket.Create (4 Optional)
vb6_cTlsSocket_Create(me->m_oSocket, 0, eSocketType, 0, vb6_BSTR_Empty(), 0, 1, 1, 1, 1, 1);
//                                                                                            ^^^^^^^^^^ 多余的 _has_ 标志
```

## 根本原因

### storageKey 冲突导致类成员签名查找失败

C3 的 `Symbol::storageKey()` 规则：
- Sub/Function/Variable/Constant = `lowerName`
- Property Get/Let/Set = `lowerName + "$pg"/"$pl"/"$ps"`

`driver.cpp` 的 `globalPublicSyms` 按此 key 对 Public 方法去重。当多个类都有 `Public Function Create(...)` 时，只有**第一个注册**的类的 `Create` 外部符号存活下来，其余被去重丢弃。

`visit(IndexOrCallExpr&)` 在 cgen_expr.cpp:2516-2527 处对 MemberAccessExpr callee 使用 `symTab_.lookupModule(memberName)` 查找 `calleeParams`。由于 storageKey 冲突，此查找总是返回**第一个注册类**的同名方法符号 —— 无论实际对象属于哪个类。

**具体影响**：
- `cWinSock.m_oSocket` 的类型是 `cTlsSocket`，但 `lookupModule("create")` 返回 `cAsyncSocket.Create`（先注册）
- `cAsyncSocket.Create` 有 5 个 Optional 参数 → C3 为每个 Optional 填充 `_has_` 标志
- `cTlsSocket.Create` 只有 4 个 Optional 参数 → 多生出 1 个 `_has_` 标志 → C2197

## 修复方案（三部分）

### Part 1: Symbol 新增 memberParams 映射（symbol_table.hpp）

在 `Symbol` 结构体中新增字段，与 `memberProcKinds` 平行：

```cpp
std::unordered_map<std::string, std::vector<ParameterInfo>> memberParams;
```

按成员名（lower）存储该成员的参数列表。优先级规则与 `memberProcKinds` 一致：Get > Function > Sub > Let > Set（读上下文优先）。

**关键设计**：Class 符号本身不受 storageKey 去重影响（每类一个），所以 `memberParams` 存储在 Class 符号上是可靠的。

### Part 2: Pass1 填充 memberParams（semantic_analyzer.cpp）

**第一版错误**：在 class init 阶段（line 112-268）填充 `memberParams`。该阶段在所有声明注册**之前**运行，`resolveTypeOrDefault()` 无法解析 EnumType/UserDefinedType 等命名类型 → 所有参数默认为 `Variant` → C2440 类型转换错误 +37 例（regression）。

**正确版本**：将 `memberParams` 填充移到 **Pass1**（SubDecl/FunctionDecl/PropertyDecl visitor 的 `pass_ == 1` 分支），此时所有声明已注册，`resolveTypeOrDefault()` 可正确解析类型。

三处填充点（均在 `symTab_.define(std::move(sym))` 之前，`sym->params` 已构建完毕）：

1. **SubDecl Pass1**（~line 626）：Sub 覆盖写入（与 memberProcKinds Sub 行为一致）

2. **FunctionDecl Pass1**（~line 711）：Function 覆盖写入（与 memberProcKinds Function 行为一致）

3. **PropertyDecl Pass1**（~line 797）：按 wins 逻辑写入。Pass1 时 `memberProcKinds` 已在 class init 阶段确定最终胜出者，据此判定当前 Property 是否为胜出者：
   - PropertyGet：总是胜出（`wins = true`）
   - PropertyLet：仅当 `memberProcKinds[lower] == PropertyLet` 时胜出
   - PropertySet：仅当 `memberProcKinds[lower] == PropertySet` 时胜出

   此判定逻辑正确 —— 因为 `memberProcKinds` 反映的是最终结果，只有与最终结果匹配的 Property 才应贡献 `memberParams`。

### Part 3: findClassMemberCallParams 辅助函数（cgen_util.cpp + cgen.hpp）

新增函数声明（cgen.hpp ~line 627）：

```cpp
bool findClassMemberCallParams(const std::string& className,
                                const std::string& memberName,
                                std::vector<ParameterInfo>& outParams,
                                bool& outIsBuiltin);
```

实现（cgen_util.cpp ~line 1387）—— 两阶段查找：

**Phase A**：遍历 `moduleScope` 符号，查找 `sourceModule == className` 且名为 `memberName` 的方法符号。若找到，从该符号的 `params` 获取参数列表。适用于本模块或正常外部注册的场景。

**Phase B**（storageKey 冲突 fallback）：若 Phase A 未找到（storageKey 冲突导致外部方法符号的 `sourceModule` 不匹配），查找 Class 符号本身（`symTab_.lookupModule(className_lower)`，Class 符号唯一不受去重影响），从其 `memberParams[memberLower]` 获取参数列表。

### Part 4: IndexOrCallExpr calleeParams 查找改用类感知解析（cgen_expr.cpp ~line 2516-2570）

对 MemberAccessExpr callee，当 `maExpr.object` 是 IdentifierExpr 时：
1. 确定 className：从 `knownClassVars_` 查找变量名；若是 "me" 则用 `moduleName_`
2. 调用 `findClassMemberCallParams(className, memberName, ...)`
3. 成功则使用返回的 params 填充 `calleeParams`
4. 失败则回退到原有 `lookupModule` 逻辑

### Part 5: driver.cpp extSym 传播（~line 1154）

在外部符号复制时同步传播 `memberParams`：

```cpp
extSym->memberParams = srcSym->memberParams;
```

## 验证结果

### 错误数对比

| 类别 | Fix 032 基线 | Fix 033 第一版(buggy) | Fix 033 修正版 |
| --- | --- | --- | --- |
| **总计** | 2508 | 2433 | **2403 (-105)** |
| C2197 | 234 | 162 | **163 (-71)** |
| C2198 | 219 | 180 | **187 (-32)** |
| C2440 | 1254 | 1291 (+37 regression) | **1247 (-7, 优于基线)** |
| C2065 | 211 | 211 | 211 |
| C2106 | 24 | — | 30 (+6, 自然暴露) |

### C2197 目标达成

C2197 从 234 降至 163（-71，-30%），核心目标 "too many arguments" 大幅减少。

### C2198 附带收益

C2198 "parameter not enough" 从 219 降至 187（-32），因为类感知的 params 解析同样修正了参数不足的场景。

### C2440 regression 修复

第一版在 class init 阶段填充 memberParams 导致 C2440 +37（类型解析不完整，EnumType 参数被记录为 Variant）。修正版移到 Pass1 后，C2440 不仅恢复到基线，还额外减少 7 例（1247 vs 1254）—— 说明 Pass1 的正确类型信息也修正了部分基线已有的 C2440。

### C2106 自然增加 (+6)

C2106 "+6" 是自然的错误层暴露：部分此前被 C2197（参数过多）掩盖的代码现在通过了参数检查，暴露出底层的左值赋值问题（如 `vb6_VariantArrayGet(...) = value`、`vb6_cTimers_Item(...) = 123`）。这些是 Property Let/默认成员赋值的 codegen 问题，将在后续 fix 中处理。
