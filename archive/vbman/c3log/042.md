# Fix 042 — Declare Function _has_ Flags + Method Chain calleeParams

## Starting Point
- After Fix 041 (commit 7bba89e): 1682 tracked errors
- C2198=141 (too few arguments), C2197=79 (too many arguments)

## Root Cause Analysis

### Problem 1: Declare Function _has_ Flag Mismatch
VB6 Declare functions (external DLL imports) can be declared with Optional parameters in multiple modules. The C3 codegen generates `_has_<paramName>` flags for Optional params in both:
1. **C header declarations** (`cgen_decl.cpp` `makeParamList()` lines 444-450) — appends `int _has_<name>` for each Optional param
2. **Call sites** (`cgen_expr.cpp` ~line 3960) — appends `_has_<name>` values when calling functions with Optional params

The `#ifndef` guard on Declare function headers means only ONE module's declaration wins. Different modules may declare the same Declare function with different numbers of Optional params:

- `cAsyncSocket.cls`: `CallWindowProcW` with 0 Optional params → 5 C params
- `cZipArchive.cls`: `CallWindowProcW` with 3 Optional params → 5+3=8 C params (with `_has_`)

If cAsyncSocket's header wins (5 params), calls from cZipArchive that pass 8 args → C2197 (too many).
If cZipArchive's header wins (8 params), calls from cAsyncSocket that pass 5 args → C2198 (too few).

**Key insight**: Declare functions are `__declspec(dllimport)` — they're imported from external DLLs and do NOT use the `_has_` convention. The `_has_` flags are only meaningful for C3-generated user functions. All modules should agree on the same signature WITHOUT `_has_` flags.

### Problem 2: Method Chain calleeParams Lookup
Complex method chains like `db.Table("t").OrderByDesc("id").Limit(10).Offset(20)` involve `MemberAccessExpr` where the object is NOT a simple `IdentifierExpr` but another `MemberAccessExpr` or `IndexOrCallExpr`. The existing calleeParams lookup only handled `IdentifierExpr` objects, leaving `calleeParams` empty for method chains. This caused argument truncation to fail — when args > params, the extra args weren't truncated.

## Fix 042a — Skip _has_ Flags at Call Site for Declare Functions

**File**: `src/backend/cgen_expr.cpp`

1. Added `calleeIsDeclare` bool flag (~line 2992) to track whether the callee is a Declare function.
2. Set `calleeIsDeclare = true` in both IdentifierExpr and MemberAccessExpr calleeParams lookup paths when `funcSym->kind == DeclareSub || funcSym->kind == DeclareFunc`.
3. Changed `_has_` flag generation condition (~line 3960): `!calleeIsBuiltin && !calleeIsDeclare` (was just `!calleeIsBuiltin`).

**Result**: C2197 79→41 (-38). CallWindowProcW 33→0.

## Fix 042b — Method Chain calleeParams Lookup Using inferClassTypeOfExpr

**File**: `src/backend/cgen_expr.cpp`

Added new block (~line 3057) before the fallback `lookupModule` in MemberAccessExpr handling:
- When `maExpr.object` is NOT an `IdentifierExpr` (i.e., it's a complex expression like a method chain), calls `inferClassTypeOfExpr(*maExpr.object)` to determine the class type.
- Then calls `findClassMemberCallParams(className, maExpr.memberName, ...)` to resolve the callee's parameters.
- If found, sets `calleeParams` + `calleeParamsFound`.

**Result**: This caused a +12 C2198 regression (GdipDrawImageRectRectI=10, GdiplusStartup=2) because the calleeParams lookup now found Declare function params (which still had `_has_` flags in headers), and the arg truncation logic reduced the call args to match — but the call site (with Fix 042a) already wasn't passing `_has_` flags, so 14 args < 17 params → C2198.

## Fix 042c — Remove _has_ Flags from Declare Function Header Declarations

**Files**: `src/backend/cgen.hpp`, `src/backend/cgen_decl.cpp`

**Root cause of regression**: Declare function C header declarations in `makeParamList()` still generated `_has_` flags for Optional params, but call sites (with Fix 042a) no longer passed them. This mismatch caused C2198 "too few arguments".

**Fix**:
1. Added `bool isDeclare = false` parameter to `makeParamList()` declaration in `cgen.hpp` (line 533).
2. Added `bool isDeclare` parameter to `makeParamList()` definition in `cgen_decl.cpp` (line 403).
3. Wrapped the `_has_` flag generation loop (lines 444-455) in `if (!isDeclare)` — skips `_has_` flags for Declare functions.
4. Updated `visit(DeclareDecl)` call site (line 843): `makeParamList(node.params, true)` — passes `isDeclare=true`.

**Result**: C2198 153→141 (-12). Regression fully fixed. GdipDrawImageRectRectI 10→0, GdiplusStartup 2→0 (errors only, warnings remain).

### Key Design Decisions

- **Why `isDeclare` parameter instead of separate function**: `makeParamList()` is called from 6 places. Adding a default parameter (`false`) means only the Declare call site needs to change. All other call sites (user functions, class methods, properties) remain unchanged and continue to generate `_has_` flags as before.

- **Why Declare functions don't need `_has_` flags**: Declare functions are `__declspec(dllimport)` — their C signatures must match the actual DLL export signatures. The `_has_` convention is a C3-internal mechanism for IsMissing support in user-defined functions. External DLLs don't have this concept. By removing `_has_` from both headers and call sites, all modules agree on the same signature.

- **Why the regression was caused by Fix 042a+042b interaction**: Fix 042a removed `_has_` from call sites. Fix 042b enabled calleeParams lookup for method chains, which found Declare function params (still with `_has_` in headers). The arg truncation logic then reduced args to match the "expected" param count (including `_has_`), but the call site wasn't passing `_has_` → mismatch. Fix 042c resolved this by removing `_has_` from headers too.
