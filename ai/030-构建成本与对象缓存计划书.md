## 一、为什么开这一篇

三条追问逼出来的读数，印象答不了：

1. 「把 RTL 预编成静态库（.lib）收益大么？C3.exe 体积也能小些吧？」

第三问把我原本的结论问翻了（见 §五），所以这篇的价值不只在读数，还在**把"跨工具链到底安不安全"这条判清楚**。

## 二、读数（本机 x64，同一个 .build/C3.exe，未改任何码）

测量手法：同一输出目录里交替编两个项目（tests/hello.bas、tests/test_compat.bas），用 -v 读命中分数。
**单次计时不可信** —— 这条链路的墙钟受 OS 文件缓存支配，同一支命令测出过 14.3 s 与 0.9 s，所以下面只给区间。

| 面 | 读数 |
|---|---|
| --syntax-only（只到语法） | 0.39 s |
| --emit-c（语义 + TypeLib + RTL 解包 + 发码，**完全不碰 MSVC**） | 0.57 s |
| --emit-c --no-auto-typelib | 0.18 s ⇒ **那 8 个 ProgID 的注册表查询 ≈ 0.2–0.4 s / 每次编译** |
| 冷 obj 缓存（0 命中，67 个 RTL .c 全重编） | 16.7 – 29.4 s |
| 暖缓存（66–67/67 命中），MSVC env 未预灌 | 2.2 – 5.4 s |
| 暖缓存 + **MSVC env 预灌**（跳过 vcvarsall） | **0.9 – 1.4 s** |
| cmd /c echo ok | 0.02 s |
| cmd /c call vcvarsall.bat x64 | 5.2 – 6.6 s（冷；机器热了之后 1 s 级） |
| cl /c 两个生成 .c ＋ link 68 个 obj ＋ rc（env 已就位时） | 合计 ≈ 0.35 s |

对照今天套件里一个用例的 23–41 s：**能挤到 1 s 级，且不需要任何新机制**（§六 三格）。

## 三、成本现在落在哪（按可读性排序）

1. **RTL 全量重编 ≈ 13–15 s**：每次编译都重编 67 个 RTL .c（RTL 是 .c/.h 源码嵌在 exe 里当 RCDATA，见 src/driver/c3rtl.rc 的 P10 口径）。这是冷缓存里最大的一格。
2. **vcvarsall 每次构建调两遍**：cl 前缀一次（src/backend/msvc_driver.cpp 编译路径）、link 前缀一次（msvc_driver_incremental.cpp:296）。P24-05 早就留了跳过通道（见 §四最后一格），但只在调用方环境里已经有 VCINSTALLDIR 时生效。
3. **前端 0.57 s**，其中 auto-typelib 0.2–0.4 s 是纯注册表查询。
4. cl/link/rc 本体 ≈ 0.35 s —— **不是瓶颈，别在这上面动手**。

## 四、机制现状（读码定位，全部是行号级事实）

> **本节记的是 T30-A 落地之前的样子**（行号仍对得上旧代码的地方已少了几处：
cache.txt、optsFp、"cacheDir = <outputDir>/.c3obj" 那三条已被 §九 的实现取代）。留在篇里是因为
它就是量出那 20–40 s 的成因，也是判据的靶子。

- 缓存目录：msvcOpts.incrementalCacheDir = outputDir + "/.c3obj"（src/driver/driver_link.cpp:494）⇒ **每个输出目录各一份，天然不跨项目共享**（实测能共享，见下条，但机制上没打算）。
- 开关默认：driver.hpp:88 bool incremental = false；套件与 .github/workflows 里 **0 处** 传 --incremental ⇒ 这条机制今天完全没在用。
- 键：optsFp = hash(arch | isDll | isGui | optimizationLevel | debugInfo)（msvc_driver_incremental.cpp:107-112）⇒ 不含 /I 集、不含 CRT 档、不含工具串。
- 记录：record = srcHash + " " + hash(本地 include 内容拼接) + " " + optsFp（:163）⇒ **系统头（&lt;&gt; include）不进哈希**；§五 论证这条可接受。
- obj 身份 = **basename**（:153 sp.stem() + ".obj"）⇒ 共享目录里两个项目的同名 .c 会互踩（hello 与 test_compat 的 com_entry.c 就是同名，只是内容哈希救了正确性）。
- **cache.txt 每次只写本进程的 newCache 且 trunc**（:244-248）⇒ 交替编两个项目会互相抹记录。实测读数：共享目录里 objs 68 个、cache.txt 只剩 67 条。
- include 解析偏向工程：/I 同时给 rtlDir 与 srcDir（:130-131），且 collectLocalIncludes **先查 srcDir 再查 rtlDir**（:72-75）⇒ 工程里放一个同名 vb6rtl.h 就能抢位，而且依赖哈希跟着抢错对象。**这是最该关的洞，比工具串版本大得多。**
- 发布不原子、无锁：新 obj 用 copy_file(overwrite_existing) 进缓存（:232 附近），cache.txt trunc 重写，全程无目录锁 ⇒ 两个 C3.exe 并发共写同一 cache 能读到半写 obj。
- /OPT:REF **只出现在注释里**（msvc_driver.cpp:178、msvc_driver_incremental.cpp:141），两条链接路的命令行都没写 ⇒ 依赖 link.exe 的默认（非 /INCREMENTAL 时默认开）。**增量与非增量两条路的链接输入因此必须逐字对齐**，这条要进判据。
- vcvars 跳过通道已存在：buildVcvarsPrefix（msvc_driver_discovery.cpp:167-184）—— VCINSTALLDIR 已设且 VSCMD_ARG_TGT_ARCH 与目标架构一致时**返回空前缀**。⇒ "调用方先把 MSVC env 灌好"是零改码的加速；实测预灌之后同一工程同一暖缓存 2.2–5.4 s → 0.9–1.4 s，产物真建出来且跑起来输出与对照臂逐字相同。
- 注意 --arch x86 那条通道：VSCMD_ARG_TGT_ARCH=x64 与目标不符 ⇒ 仍要重跑 vcvarsall x86（:175 明写）。按架构分格缓存 env 才能两边都吃到。

## 五、「obj 挑不挑 VS 版本」—— 我先说重了，订正如下

我最初的论证是：「67 个 obj 里 45 个 include windows.h ⇒ 它们烙的是发布机那套 SDK 头的结构体布局 ⇒ 必须按 cl/SDK 版本分格，否则跨机静默错」。用户反驳「lib 好像不挑 VS 版本」，复核之后**用户是对的**：

- 真挑版本的是 **LTCG（/GL）**，不是 COFF obj 容器。全仓只有 msvc_driver.cpp:183 一句注释提到 /GL 并明写「本项目未使用」（/MP 能正是因为它没用）；优化档只有 /Od /O1 /O2 /Ox（:159-164）。⇒ 这条约束不存在。
- **跨 obj 边界的结构体只有我们自己的**：grep RTL 对外头，SDK 结构体名仅命中一处 —— src/rtl/core/vb6forms/vb6forms_axsite_internal.h:52 的 RECT，而 _internal.h 只在 RTL 自己的 TU 之间共享，这些 TU 是整包同机产的、内部自洽；对外入口一律 void* + 基本类型。⇒ 「发布机的 windows.h 布局」没有出口去和用户机的头打架。
- 所以键里**承重**的只有三条：架构、/I 路径集、RTL 源与其本地 include 的内容哈希（vb6_VARIANT 那套布局真跨边界，但它是我们的头，内容哈希精确盖住）。
- **cl.exe 文件版本 / SDK include 版本目录**从「正确性闸门」降级为「廉价保险 + 可诊断」：不带它，最坏是老 link.exe 遇到新 obj 报一个**响亮**的链接错，不是静默错；带它的代价最多是换工具集时本地多编一次 15 s。仍然带，但别当承重墙。

**推论：发布随包带预产 obj 没有静默错路径。** RTL 一改，内容哈希就 mismatch ⇒ 自动回退源码编。当年 P11.3 的 .lib 回退（f99436c → 6 个存档进仓库 → 78df0b3 撤）反对的是「把二进制当发布契约入库」，不反对「带一份可丢弃的缓存」。ai/024 §"RTL 绝不入包 / 不引预编译 RTL 回潮" 那条边界仍然有效，T30-D 要碰它，得单独拍。

### 5.1 用户接着指出的第二条（2026-09-26 复核成立，且把 T30-D 改判成主力）

用户口径：「只有我们改编译器的人才动 RTL，写 VB 的人不动 RTL；改了 RTL 肯定要发新版本。」—— 这条把我上面那个"跨机错配"的顾虑基本消掉，并且顺带纠正了我对键的判断。核到的证据：

- **MsvcDriverOptions 里没有 defines 字段**（src/backend/msvc_driver.hpp 的字段清单：rtlDir / isDll / isGui / srcDir / arch …），用户的 -d NAME=V 不下到 cl 命令行 ⇒ **把 RTL 的编译 flag 与用户 flag 解耦不改变语义**。
- 于是 RTL 那一族的 obj 实际只由「架构 + RTL 源内容」决定。今天的实现却让它看起来跟别的东西相关：
  - **optsFp 含 isDll | isGui（:107-112），而这两个不进 cl 命令行**（common 串只有 /I、/O、/Zi、/std:c11、/D UNICODE 那组、/W3、/Gy、x86 才有的 /MT）⇒ 同一工程的 console / GUI / DLL 三个变体各重编一遍 67 个 .c，13–15 s × 3，**产出的 obj 逐字相同**。
  - 反向也浪费：-O 2 会让 RTL 整套失效（实测 0/67），而 RTL 没必要跟用户码的优化档走。
- 所以设计落到一句话：**RTL 用独立且固定的一套 flag 编（只 /I rtlDir、固定优化档、不喂 srcDir），obj 改成内容寻址命名**（文件名 = hash(架构 + flag 串 + RTL 源与其本地 include 的内容)）。这一改同时买到四件：
  1. 键塌成「架构 + RTL 内容」一格，全局一份缓存服务所有项目、所有产物形态、所有用户 flag；
  2. 工程里放同名 vb6rtl.h 抢位那个真洞被堵（因为不再喂 srcDir，见 §四 collectLocalIncludes :72-75 那条）；
  3. cache.txt 这个索引文件可以整个去掉 ⇒ §四 列的「交替项目互相抹记录（实测 68 obj / 67 条）」「basename 同名互踩」「trunc 非原子重写」三件事一起消失；
  4. **随包带 obj 变纯赚**：查不到就自己编，过期/错配的最坏后果是那 1.4 MB 白占地方，永远不会用错；发布版本号进 flag 串 ⇒ 跨版本整格自然失效。

唯一要标出来的真风险：RTL 从今天的 /Od 改成固定 /O2 是一次**代码生成变化**，浮点结果理论上不该变（MSVC 不默认 /fp:fast），但这属于「数值类用例真跑一遍才算过」那类改动（test_ndarray / test_compat 那批 + x86 侧单独验）。不担这点风险的退路：固定档就写 /Od，缓存收益一分不少，只是 RTL 慢一点。

顺带两条被这次测量否掉的想当然：

- 「.build 里已经有静态库可用」—— 那三个 vb6c3-cgen/core/ir.lib 是**编译器自己的 C++ 库**（名字修饰、C++ 运行时、CRT 配置都对不上），与 RTL 无关。RTL 的 67 个 .obj 在 .c3obj 里，那才是「编一次反复用」的现成形态。
- 「.lib 比 obj 强」—— 恰恰相反：obj 是单文件失效粒度，归成 .lib 后任一处改动都要重归档整包；且当年长成 console/dll/gui × x86/x64 六格是**可以不必**的（CRT 只有 x86=/MT、x64=/MD 两格，P24-09 钉死在 msvc_driver_incremental.cpp:143）。体积也不省：exe 里 RTL 源负载 1.18 MB（.c 0.96 + .h 0.16 + .inc 0.07），那 6 个 .lib 合计 1.46 MB。

twinBASIC 那条（第 2 问）与本篇无关，记在案以免重复讨论：D:\tools\twinBASIC_IDE_BETA_983\bin 里 29 KB 的 exe 唯一 import 就是 6.6 MB 的 twinBASIC_win64.dll，那个 dll 里有 LanguageServer / workspace / .twinproj 串 ⇒ 它是**编译核 + 语言服务**，不是运行时。它买的是「核常驻」（边打字边重编、LSP 秒响应），买不到「编译更快 / 产物更小」。对 C3 而言对应的那一格是 ai/009 缺口表里「LSP/DAP 零实现」，不属本篇。

## 六、提案（每格独立过门，顺序按"每次构建都受益 vs 只受益一次"）

| 格 | 内容 | 深度 | 收益 |
|---|---|---|---|
| **T30-A** | **RTL 独立 flag + 内容寻址 + 全局一格**（§5.1 的读法）：RTL 那一族 .c 用固定的一套 flag 编（只 /I rtlDir、不喂 srcDir、优化档固定），obj 文件名 = hash(架构 + flag 串 + RTL 源与其本地 include 的内容)，**cache.txt 整个去掉**；发布版本号与 cl.exe 文件版本进 flag 串（后者是廉价保险不是闸门 —— §五）；原子发布（写临时名 + MoveFileEx 替换） | 中（集中在 msvc_driver_incremental.cpp + driver_link.cpp） | 跨项目 / 跨 console-GUI-DLL / 跨用户 flag 全复用；顺带关掉同名头抢位与并发那三件 | **〔已实施 2026-09-26，读数见 §九〕**
| **T30-C** | vcvarsall **每进程只调一次**：按架构捕获 env 并复用（复用 P24-05 那同一套判据），cl 与 link 两遍并一遍；x86/x64 分开缓存 | 很浅（driver 一处） | 每次构建省 1.3–4.5 s，冷机器上一次省到 5–6 s |
| **T30-D** | 发布随包带 rtl-obj/（build.bat 顺手产 x64 + x86 两份，exe 里继续嵌 .c 当回退） | 打包侧 | 新机器/新 job 的第一次也跳过那 13–15 s；**内容寻址 ⇒ 错配只是查不到，永远不会是查错**（§5.1） |
| T30-E | auto-typelib 的 8 个 ProgID 结果落盘 / 改按需加载 | 很浅 | 0.2–0.4 s / 每次编译 |
| CI 侧 | 那份缓存目录做成 Actions cache，键 = 架构 + 工具串 + RTL 源哈希 | 配置 | 一轮 55–61 分钟能砍掉大半；**属他人工作流，只报数不动**（同 tests_github 那条约定） |

**顺序（§5.1 之后改判）**：A → C → D。原稿里排在 A 后面的那格「全局分格 cacheDir」被 A 吸收了 —— 内容寻址之后没有"分格目录"这个概念，只有一个 store 目录，键就是文件名。

补记一个零风险等价方案：`C3 --prewarm`（用户机自己的工具链产自己那份 obj，15–20 s 一次）。有了 D 之后它只剩一个用途：我们选择让 cl 版本进串，那么用户机版本不同就 miss —— prewarm 把这笔钱从"第一次构建"挪到"安装时"，顺带让 -O / -g 之类固定档之外的差异也一并预热掉。

## 七、判据（**"产物逐字节相同"这条作废**）

作废理由（实测）：同一份 hello.bas 冷编两次，md5 就不同 —— 临时会话目录 %TEMP%\C3C\&lt;id&gt; 烙进了产物。逐字节在这条链路上不可执行，别拿它当门。

1. **跑起来输出相同**：同工程「冷编产物」与「暖命中产物」各跑一遍，stdout 逐字相同（hello.bas 的 Count: 1..N 已验，102 字节三臂一致）。
2. **命中计数进断言**：-v 的「N/M 个源文件命中缓存」—— 首编 0/M、次编 (M-1)/M、新项目进共享缓存 ≥66/67。这条同时证明「跨项目共享真在发生」。
3. **三条失效负控必红**：改任一头文件 / 改 /I 集 / 换架构。（-O 档那条已实测通：一换 -O 2 就 0/67 全失效。）
4. **并发共写**：两个 C3.exe 同时用同一 cacheDir，两边产物都正确（今天做不到 —— 无锁 + 非原子，这正是 T30-A 的内容）。
5. **增量路与非增量的链接输入逐字对齐**（/OPT:REF 只在注释里那条警告）：同一工程分别走 --incremental 与不带，比较 link 命令行（-v 读 rsp 内容或 rc/cl/link 三段），除 obj 路径外应无差。
6. **零回归护栏**：默认仍关时，30 工程 --emit-c 逐字节护栏 0 diff + 语法 129/0 + 门（全量回归零新增失败）。
7. **x86 真编真跑**：门只测默认架构是老规矩，CRT 档与 /MACHINE 这格改动必须 x86 侧单独验。

## 八、不做什么

- 不把 RTL 发成 .lib **入库**（ai/024 的永久边界，P11.3 是同族教训）。T30-D 带的是可丢弃缓存 + 永远存在的源码回退，不是发布契约；要碰也得单独拍。
- 不在没影子跑过之前默认开 --incremental。共享树里有并发（3 个写入者 + Documents 一份全树副本在跑套件），默认开等于给并发加一条未知路径。
- 不动 tests_github/** 与 T 系列工作流（他人在修清单/预算漂移）。CI 那条 cache 建议以「报数 + 一行提案」交付，不自己改。
- 本篇不碰控件线。ai/029 的下一批（C29-9b：CommonDialog 起窗自关探针 → 真模态框 + 取消→32755）排队中，本篇 §六 落完就回 029。

## 九、T30-A 落地读数（2026-09-26，改完后的 .build/C3.exe）

手法：把 %LOCALAPPDATA% 指向临时目录 ⇒ 每轮跑在自己的空 store 上，不受本机历史缓存摆布。
工程 = tests/hello.bas（67 个源 = 65 个 RTL + hello.c + com_entry.c）。

| 臂 | 命中 (rtl · user) | 墙钟 |
|---|---|---|
| 空 store 首编 x64 | 0/65 · 0/2 | 22.0 s |
| 再编 x64 | 65/65 · 2/2 | 2.80 s |
| 三编 x64 | 65/65 · 2/2 | 2.65 s |
| 换 -O 2 | 65/65 · 0/2 | 5.70 s |
| 空档首编 x86 | 0/65 · 0/2 | 25.8 s |
| 再编 x86 | 65/65 · 2/2 | 3.15 s |

⇒ 命中之后一次构建 22 s → 2.8 s（**7.9 倍**）。`-O 2` 那臂 RTL 仍全命中（**RTL 与用户优化档
解耦成立**），用户码另占一格；六轮之后 store = 136 个 obj / 2.21 MB。三臂产物跑起来 stdout 逐字相同。

实现要点（都落在 src/backend/msvc_driver_incremental.cpp）：

- objStoreDir() 取 %LOCALAPPDATA%\C3\objcache（宽字符 API，不走 CRT 的 ANSI 转换），拿不到才退回
  调用方给的 <outputDir>/.c3obj；
- 键 = hash(flagsKey + toolsetTag + srcHash + 依赖头内容哈希 + 源名)，文件名 = <stem>_<key>.obj，
  **cache.txt 整个删除**（顺带：isDll/isGui 退出键 —— 核过它们只影响 link 行，不进 cl 命令行）；
- RTL 组与用户码组**分两次 cl 调用**（编译档不同不能共用一条命令），/Fo 分别落 objDir/rtl 与 objDir/usr，
  同名 .c 从此不会互踩；
- RTL 组的 /I 只给 rtlDir、依赖也只在 rtlDir 里解析 ⇒ 工程里放同名 vb6rtl.h 抢不动（§四 那条洞）；
- 进 store 走"拷临时名 + 同目录 rename"，且**只在目标不存在时写**（键即内容 ⇒ 并发写同格是同样字节）。

判据已进回归：tests/run_tests.ps1 新增 `Test-ObjCache`（注册在 `all|run|vbp` 组，用例名 `objcache`），
五条一起断 —— 空 store 首编必 0 命中、次编必全命中、换 -O 2 后 RTL 命中数不变、store 里用户码 .c
恰好 2 格而每个 RTL 源恰好 1 格、三臂产物输出相同。助手本身用"注入假读数"验过**能红**
（红读数：`第二次没全命中: 3/65`）。

两条踩到的（已写进用例注释）：

1. PS 里 `@(@(), @(), @('-O','2'))` 会把空数组压平，三臂悄悄变成 `-O` / `2` / 无 —— 一度把正确实现判成 FAIL。
2. 断言不能依赖全局 store 的历史：不隔离时，上一轮探针留下的 `/O2` 那格会把"用户码必须 miss"翻成
   "命中"，假红假绿都出得来。

**默认开之前仍欠三件**：① store 无淘汰策略（工程每改一次多一格，只增不减）；② "改 RTL 内容 / 改头文件
⇒ 必失效"两条负控在实现上是通的（键含内容哈希），但还没做成能跑的用例；③ 并发明证（两个 C3.exe
同时喂空 store）。今天 `--incremental` 仍默认关 —— 不碰它就零影响，这是本批可以先进门再补欠账的理由。

### 10.7 GA 第一次真跑就抓到一个洞：增量那条链接路没配 CRT（门 #94 红 → 修 → 冷/暖双验）

把 `-Incremental` 接进 ci.yml 推上去之后，门 **#94** 唯一失败的是 `Tests (bas #2)`：
`test_delegate_x86: compile FAIL`。本地最小复现同一条：`--arch x86 --incremental` ⇒ `rc=1`。

错误面（`c3-error.log`）：

```
LINK : warning LNK4098: 默认库"msvcrt.lib"与其他库的使用冲突；使用 /NODEFAULTLIB:library
msvcrt.lib(chandler4gs.obj) : error LNK2019: 无法解析的外部符号 __except_handler4_common，
                                     函数 __except_handler4 引用了该符号
fatal error LNK1120: 1 个无法解析的外部命令
```

根因（`dumpbin /directives` 定的位，不是猜的）：

- P24-09 把 **x86 全部按 `/MT` 编**，65 个 RTL obj 一律带 `/DEFAULTLIB:LIBCMT`、**没有一个**带 msvcrt；
- 只有 `usr/test_delegate.obj` 同时带 `LIBCMT` 和 `msvcrt.lib` —— 那个 `msvcrt.lib` 是**用例自己**在
  `.bas` 里写的 `#pragma comment(lib, "msvcrt.lib")`（生成进 C 第 7 行），不是 cgen 发的；
- 增量那条路的链接是**直接叫 `link.exe`**（编译与链接被拆成两步，`cl /link` 用不了，见代码里 D8003 那条
  注释），而 `link.exe` 不带指示时按默认的 `/MD` 档去配 `msvcrt.lib` ⇒ 与 obj 的 `LIBCMT` 打架，
  x86 独有的 SEH4 助手 `__except_handler4_common` 就落空。默认路径经 `cl /link`，cl 会替我们配平，
  所以这个洞从来没露过面 —— `--incremental` 在 T30-B 之前**从没进过任何回归**。

修法（一行，镜像编译侧那个 `/MT` 判据）：`msvc_driver_incremental.cpp` 里
`if (options.arch == "x86") linkCmd << " /NODEFAULTLIB:msvcrt.lib";`。
手工三组对照（拿留下的 obj 直接 relink）：asis ⇒ 同样 LNK1120；只加 `/NODEFAULTLIB:msvcrt.lib` ⇒
`rc=0` 出 exe 且跑出自检 8 行（末行 `DELEGATE-DONE`）；再补 `/DEFAULTLIB:libvcruntime.lib` ⇒ 冗余。

修后本地双验（新 binary，`C3.exe` 11:53:33，且验过 binary 里真含新串）：
x86 **空 store 冷编 29 s → rc=0 + DELEGATE-DONE**；x86 暖 3 s（`rtl=65/65 user=2/2`）；
x64 空 store 冷编 31 s 正常。x64 不受影响（`__except_handler4` 是 x86 独有，所以 GA 只有 x86 那两条红）。

**这条给自己的教训（写死）**：我先前一次"重建"用的是 `MSYS_NO_PATHCONV=1 cmd //c build.bat` ——
`//c` 在关掉路径转换后**不再是 `/c`**，cmd 于是开了个交互式 shell 直接退出，`exit=0` 看着像成功，
日志里只有版本横幅。我拿 08:21 的旧 binary 验了新代码，得出过一条错误结论。以后：改完必须先证
"产物 mtime 变了 + 产物里含新增的串"，再谈验证结果；`build.bat` 的正确调用是
`MSYS_NO_PATHCONV=1 cmd /c build.bat`。
