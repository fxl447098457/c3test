# 023-VB6 包与工程引用计划书

> 日期：2026-09-23
> 状态：**提案，待拍板**（本文所有代码锚点为本轮实测；开工前须复核是否漂移）
> 一句话结论：VB6 缺的不是"静态库"，是**工程引用**；先把机制命名为"引用"，包只是它带版本与哈希的那个子类。**只走源码级 + 自包含目录**：不引压缩库、不冻 ABI、不做二进制引用（这是永久边界，非过渡方案，见 D2 与八-6）。

---

## 一、问题定义

VB6 没有工程间引用与包管理。今天的唯一复用手段是**把别人的源码拷进自己 vbp 列成模块**，实证见 `tests/VBFlexGridDemo/VBFlexGridDemo.vbp:5-18`：

```
Module=VTableHandle; Builds\VTableHandle.bas
Module=VBFlexGridBase; Builds\VBFlexGrid\VBFlexGridBase.bas
UserControl=Builds\VBFlexGrid\VBFlexGrid.ctl
Class=IVBFlexDataSource; Builds\VBFlexGrid\IVBFlexDataSource.cls
```

后果：每次构建全量重编（连 RTL 的 40 余个 `.c` 一起，见 `src/driver/driver_link.cpp:137-189`）；库的私有成员对宿主全可见（无边界）；换机器要靠手改路径（同一 vbp 里 `:2-3` 是绝对路径 `\\?\C:\Windows\...`，`:4` 是被手改成 `..\..\..\..\Windows\...` 的相对路径）。

## 二、术语与分层（先钉死，后文一律按此用词）

| 名词 | 是什么 | 解决什么 | 本项目现状 |
|---|---|---|---|
| `.vbg` 工程组 | 构建图（哪些 vbp + 启动工程 + 依赖序） | 多工程构建顺序 | 零支持（全仓无 `.vbg`） |
| **工程引用** | 编译期可见性：宿主看见被引工程的 Public 成员 | 复用代码 | 零支持（`vbp_parser.cpp:55-62` 无 `Project=` 键） |
| **包 (Package)** | 工程引用 + 版本 + 逐文件哈希 + 可分发 | 复用 + 分发 + 校验 | 本计划要做 |
| **静态库 (`.lib`/`.a`)** | 链接器的一个输入产物，只有符号地址、没有签名 | 链第三方 C 代码 | **不做**（D2 永久边界；试过又回退的 P11.3 是同族教训） |

两条撞名警示：

1. **不要叫 manifest**。Windows 应用清单已占用该词与 `RT_MANIFEST` 资源（本仓实例：`tests/BalloonTooltips/BalloonTooltips.exe.manifest`）。包侧文件本文一律称**清单 (list/desc)**，文件名建议 `package.c3d`。
2. 与 `ai/讨论记录/008-IDE生态架构分析与库优先设计决策.md` 的"**库优先**"无关——那篇讲的是编译器内部把核心逻辑下沉成 C++ 可复用库，不是用户侧复用单元。引用本文时须点名区分。

## 四、核心决策

- **D1 命名与范围**：特性叫 **引用**；"包"= 外来 + 带版本/哈希的引用。先做仓库内工程引用（VBFlexGrid 这类共享代码立刻受益），再长出分发。
- **D2 只走源码级（永久边界，不是过渡方案）**：包里是 `.bas/.cls` + 清单。不产 `.lib`/`.a`、不冻 ABI。
  **边界范围**：本条只约束"包**发成**二进制"（此时 ABI 契约由我们承担）。"**消费**别人编好的静态库"是另一件事、另一份契约模型（用户与库提供者之间，同今天 `Declare` 写错就崩），已单独立项 → `ai/024-静态库链接计划书.md`。别把两者混为一谈而误删本条或误扩本条。
  三条理由，按分量排：
  1. **不可诊断**：源码级包出错，编译器给的是行号与签名；二进制包出错是链接期"未解析/重复符号"或运行期字段错位，用户拿到 `.a` 后**没有还原手段**——归档里少一个成员、CRC 过但内容被改、跨工具链混用，全都是静默腐坏，坏一处整包作废且无法局部修复。封闭性只是表象，**不可修复性**才是决定性理由。
  2. **被双后端放大成四倍成本**：`ai/讨论记录/014-…MinGW-COM兼容性分析.md` 已把 `--backend=msvc|mingw`（默认 MinGW）定成发布策略。该篇的"二进制互通"讲的是 **COM 接口层**（vtable + x64 统一调用约定）；私有对象之间互通还要额外钉名字修饰、结构体布局、CRT 初始化、libgcc 的 `__emutls_*`。一个包要覆盖 2 后端 × 2 架构 = **4 份产物 + 4 份 ABI 验证**。这是 P11.3 预编译 RTL `.lib` 回退（`driver_link.cpp:137-138`、`rtl_embedded.cpp:3`）的放大版。
  3. **时机也不对**：022 的 B04/B05 刚往类结构体加了 `__iv_<I>`/`__refcount`（紧跟 `__comObj`），B13/P6 还要继续动对象布局，`vb6_VARIANT` 布局也仍在被各 Fix 触碰。布局一动，已发布二进制包集体静默错位。
- **D3 vbp 里不写路径**：只写名字 + 版本，寻址规则唯一（六节）。把"布局即契约"从每个工程收敛进编译器一处。
- **D4 清单不引入外部格式**：自研 `Key=Value` + 小节式（与 vbp 同族，有现成解析先例），**不用 JSON**（无解析器）、**不用 zip**（无依赖）。内容纯 ASCII。
- **D5 编译器只认目录，永不直接读容器**：单文件容器是纯分发外壳（九节 S06），因此可晚做、可替换（将来换 zip 或直接用 git 仓库地址）而编译器零改动。
- **D6 校验而非生成**：路径/清单由作者写一次，工具负责规范化与报警，不做"自动改 vbp"。C3 是编译器不是包管理器——安装动作 v1 就是"把目录放进 `packages/`"。
- **D7 校验报警不拒收**：就地改包内源码调试是真实工作流，拒收等于废掉它。
- **D8 与 022 自动化任务解耦**：本特性不得进入 022 的批次表（那是继承/接口/CoClass 的唯一状态源），进度另立表或并入本文九节的勾选列。

## 五、清单格式草案 `package.c3d`

```
[C3Package]
Format=1
Name=VBFlexGrid
Version=1.2.0
Desc=tB-style grid control package

[Files]
VBFlexGridBase.bas=<sha1>,<size>
VBFlexGrid.cls=<sha1>,<size>

[Export]
Module=VBFlexGridBase; Public
Class=IVBFlexDataSource; Public
Friend=False

[Needs]
Comctl6=True
```

要点：
- 所有文件路径**相对清单自身所在目录**（唯一基准，与 `resolvePath()` 一致）。
- `Format=1` 是版本号，**不可解析的新字段一律报错**，不许静默忽略——清单格式演进的唯一保险。
- 逐文件哈希是强制项：目录形态没有单一产物哈希，缓存失效判定与"有人手改过包"只能靠它。
- 禁止出现只有 C3 认得的宏。若确有需求，只允许两个语义明确的：`$(ProjectDir)` / `$(PackageRoot)`，且须写进文档。

## 六、寻址与解析

```
宿主 vbp 里一行：   Package=VBFlexGrid; 1.2
解析为：            <搜索根>/VBFlexGrid-1.2/package.c3d
```

- 搜索根 = 默认 `packages/`（相对 vbp），可被命令行 `--package-root` 追加。
- 目录名用 `-` 分隔版本（`Foo-1.2`），**不用 `@`**（URL/脚本里要转义，无收益）。
- **不允许引用仓库/搜索根之外的任意目录**。需要调试外部源码时，在 `packages/` 里放一个目录 junction 即可，比在格式里开绝对路径后门干净。
- 构建期三条硬校验：解析结果跳出搜索根 → 报错；清单缺文件/哈希不符 → 警告（D7）；包名与宿主工程名或已加载模块名冲突 → 报错。

## 七、可见性与符号注入语义

- 注入时机：stage 3 之后、3.5 之前（与 `ai/022` 的 D15-1 结论同族：可见性只需工程级表 + 本模块成员表，不必再往跨模块解析里塞新阶段）。
- 导出边界：包内 `Friend`/`Private` 对宿主不可见；宿主不得实例化包内私有类。**这是拷源码进 vbp 那条路给不了的唯一实质能力**，也是本特性存在的理由。
- 包的模块**不参与**宿主的 `Startup=` 与窗体集合；包不得含 `Sub Main` 作为入口候选。
- 开放项 O1（限定名口径）见十一节。

## 八、硬边界（v1 明写不做）

1. **包不得携带任何最终二进制级资源**：`.rc/.res/.manifest/icon/.tlb` 一律禁。一个 exe 只容得下一份 `CREATEPROCESS_MANIFEST_RESOURCE_ID`，而 C3 已有两条塞资源的路（三节末两行）；包再塞就是同 ID 重定义，且错状取决于链接顺序。
2. C3 **今天不生成应用清单**。若将来包需要表达 manifest 诉求，只允许声明**需求布尔位**（如 `[Needs] Comctl6=True`），由宿主合并生成，绝不允许包直接给产物。
3. **RTL 绝不入包**——重演 P11.3 回退的直接风险。包只装用户代码，RTL 继续与生成的 C 源码同批编译。
4. 包不接入系统 activation context / `assemblyIdentity` 语义，避免长出第二套"名字+版本"体系（八-3 与 `ComLib=` 旁路的分界）。
5. v1 包内**只允许标准模块与类模块**：禁 `.frm`/`.ctl`/`.pag`、禁 `Event` 声明。理由：控件宿主与事件接收器牵动 `.frm` 生成路径，成本与本体无关。禁 `.frm` 顺带消掉 `.frx` 与属性页需求。
6. **二进制引用（`.lib`/`.a`/`.obj` 进包）明确不做**，理由见 D2。也不在清单里为它预留字段（`[Bin]`/`AbiHash` 一概不加）——预留就等于给这条路留门，将来会有人以"字段已经有了"为由把它捡回来。`Format=` 保持 1。*（例外：宿主工程直接消费第三方静态库不属于包格式，见 `ai/024`。）*
7. 但被这条边界挡在门外的两个真实诉求必须有**出口**，否则它们会反复回流成"包再加点二进制"的提案：
   - **闭源分发** → 走 C3 已有的 COM/ActiveX DLL 路线（P6 全链：`src/rtl/core/vb6comserver/` + `DllGetClassObject` 导出层 + 类型库引用 `Reference=`）。那是 VB6 世界现成、且语义正确的商业分发形式：接口即契约、类型库给签名、损坏能被 `regsvr32`/版本目录诊断。包系统不承担闭源。
   - **构建太慢** → 立**独立特性：本地对象缓存**（同一 RTL 版本指纹下复用包/模块的 `.obj`）。它安全的原因正是"缓存只在本机同版本内有效、永不跨机器分发"，所以不需要给第三方冻 ABI。性能诉求从这里解决，不从包格式解决。

## 十一、待拍板的开放决策

- **O1 限定名口径**：宿主调用包成员写成 `Pkg.Mod.Func(...)`、`Mod.Func(...)`、还是"无冲突时允许裸名"？倾向前者中的**包名限定**（冲突面最小、可读、与 typelib 引用的 `Lib.Cls` 先例同形）；代价是与同工程模块的调用写法不一致。
- **O2 一个宿主能否引多个包 / 包能否引包**：v1 建议"多包可以，包不引包"（传递依赖要版本求解器，是另一整个特性）。
- **O3 版本求解**：v1 精确匹配目录名（`Foo-1.2`），不做范围语法。确认接受"要新符号就加一个版本目录"。
- **O4 ActiveX DLL 工程能否被引用**：v1 只允许被引方是 EXE/DLL 的**源码工程**，不引入"引已注册 DLL"的旁路。
- **O5 构建图（`.vbg`）**：确认推迟。多工程顺序属于 workspace 特性，不塞进本计划。

## 十五、S03 实装记录（2026-09-24）

- **导出过滤机制**：包内符号对包外消费者（宿主/另一包）的可见性在 stage 3.5 注入处过滤
  （`driver_crossmod.cpp`）——注入是跨模块符号可见的唯一通道，与 Private 的
  "不导出即不可见"完全同构。规则：
  - 导出模块（清单 `[Export]` 列名）的 Public 成员 → 可见；
  - Friend 成员 → 仅当清单 `Friend=True` 可见（默认包内可见、宿主不可见）；
  - 非导出模块 → 整模块不可见；Private → 永不可见；
  - 同包模块之间 / 包消费宿主 → 不受限。
- **诊断 VB7006**（`VbpPackageNotExported`）：屏蔽表【预计算】——S02 读包源码时用
  `extractProcDecls`（轻量行扫描）提取过程声明 + 清单导出状态算出被屏蔽名字，
  `runSemanticAnalysis` 按消费者包归属下发各分析器。为什么预计算：无实参裸调用
  （`Hidden1`）不走 deferredXmodCalls_（那里只记带实参的调用点），stage 3 之后才下发
  屏蔽表会漏掉它，只能漏到 cgen 裸调 → LNK2019。visit 期查无此名时命中屏蔽表即报错
  （`visit(IdentifierExpr)` / `visit(IndexOrCallExpr)` / 延后点三处挂钩）。
- **改动面**：`ast_decl.hpp` Module 加 `packageName`（frontend 按 文件→包 映射回填，

## 十六、S04 实装记录（2026-09-24）

**R1 实测结论（本批第一任务）**：包内**导出类**的 `vb6_cls_<C>` 结构体在宿主 TU
**完全可见**，无需 S04 预案里那条 `#include "<Cls>.h"` 补丁。实测证据（`--emit-c` 宿主段）：
`Dim t As PkgThing` + `Set t = New PkgThing` + `t.Setup 21` + `t.Value` 全链产出
**静态绑定**：`vb6_cls_PkgThing* t` / `t = (vb6_cls_PkgThing_New())` /
`vb6_PkgThing_Setup(t, 21)` / `vb6_PkgThing_prop_get_Value(t)`，运行得 `PKG-C1:42`。
R1 关闭：类跨模块走的是"类符号注入 + 头文件依赖"，与过程同一套。

**但 R1 的正面结论掩盖了一个更坏的洞（S04 真正堵的）**：类**不走** S03 的注入过滤 ——
它由消费方 codegen 的 `lookupTypeSymbol` 解析，查不到就**静默退化成后期绑定 COM**：

- 非导出类 `Dim h As HiddenCls` → 类型退化成 `void*`；
- `Set h = New HiddenCls` → `h = vb6_NewObject(L"HiddenCls")`，方法调用 →
  `vb6_ComCall(h, L"Poke", NULL, 0)`；
- **构建成功、退出码 0、产物照出**，只有运行期才失败。

比 S03 的 `LNK2019` 更坏一档：链接错误至少会报，这个是"编译通过 + 语义悄悄变了"。

**做法**：把非导出包类的**类名**纳入屏蔽表（新增 `Driver::packageBlockedClasses_`，
`driver_compile` 在 S02 读包源码时对 `.cls` 且 `modExported == false` 的模块登记），
由 `driver_semantics` 按消费者包归属下发（排除自己的包），语义层两处报 VB7006：
- `visit(NewExpr)`（`semantic_analyzer_expr.cpp`）—— 拦实例化；
- `resolveTypeRef` 的 `SimpleTypeRef` 分支（`semantic_analyzer_typeref.cpp`）—— 拦
  `Dim x As Cls` / 参数 / 返回值，否则类型静默退化 Object。
同一类名多处引用由 `reportedBlockedClasses_` 去重只报一次。
诊断文本：`'X' is a class of a package that does not export it (add 'Class=X; Public'
to the package manifest)`。

**四条边界实测（`tests/pkg_cls/`）**：

| 场景 | 用例 | 结果 |
|---|---|---|
| 导出类被宿主使用（New+方法+属性） | `pkg_s04_cls_ok` | ✅ 静态绑定 `PKG-C1:42` |
| 非导出类被宿主 `New` | `pkg_s04_cls_blocked` | ✅ VB7006、退出码 1、无产物 |
| 非导出类仅作声明类型 `Dim x As Cls` | `pkg_s04_cls_dim_only` | ✅ VB7006 |
| **同包内**模块使用该非导出类 | `pkg_s04_cls_same_package` | ✅ 不拦（包内可见） |

**逐字节护栏**：本批**不触及发码路径**（改动全部在 `driver_*`/`semantics/*`，
`blockedPkgClasses_` 为空时 `reportIfPackageClassBlocked` 直接返回），
故无 `--emit-c` 基线的可比对象 —— 护栏口径按"无发码路径改动即免跑"记录，
与十二节"S02/S04 必做"的差异在此明写：S02 改了加载集，S04 只加诊断路径。

**v1 已知边界（补记，与十五节一致）**：导出类的 **Friend 成员**经 `obj.` 调用仍可见
（成员级屏蔽属 084a `memberAccessLevels` 的后续工作）；本批只解决**类型级/实例化**边界。

  （否则 S05 生效后全是警告噪音）。**教训：`io.open` 文本模式会把 CRLF 翻译成
  LF，改 CRLF 文件必须 `newline=''`** —— 本批脚本第一次跑 `total 0` 就是这个。

### S06 `--pack/--unpack` 分发外壳

- 新文件 `src/driver/driver_pack.{hpp,cpp}`；`main.cpp` 的 `runCompile` 在进编译
  管线前截获这两个选项（编译器本体**永不读容器**，D5）。
- 容器格式（零压缩零依赖）：`"C3PKG"` 魔数 + 顺序成员区（u16 名长 + 名 +
  u64 尺寸 + 原始字节）+ 尾部中央目录（每成员 名/offset/size）+ 19 字节尾部
  （cdOffset + cdCount + `"C3PKEOF"`）。成员 = `package.c3d` + 清单 `[Files]`
  逐项（按清单顺序，路径基准 = 清单目录）。
- `--unpack` 按**中央目录**随机访问释放，逐成员校验顺序区头（名/offset/size
  三重一致），成员名防逃逸（禁绝对路径/`..`/反斜杠）。缺省释放到
  `<容器目录>/<Name>-<Version>/`（Name/Version 取自容器内的 package.c3d）。
- 负向实测：截断容器（缺尾部）→ 退出 1；坏魔数 → 退出 1；`--pack` 指到 vbp
  → 退出 1（找不到 package.c3d）。
- 测试 helper：`Test-VbpWarn`（构建成功 + 警告在场，防"成功路径吞警告"回归）、
  `Test-CliOk`（通用 exit 0 + 文案）、`Test-PackRoundtrip`（复制夹具到临时目录
  → pack → unpack → 逐文件 SHA1 比对，不污染源夹具）。
