## 0. 本轮目标

交接文档把「窗体 Release 崩溃」列为**阻塞项**，并建议「Debug 构建 + cdb 抓 FLayer 崩溃栈」。本轮先验证该阻塞项是否仍然存在。

## 1. 阻塞项其实是陈旧对象，不是 UB

- **复现**：给 `scripts/_tmp_bisect.ps1` 加 `-Forms` 开关（纳入 `VBMAN.vbp` 的 `Form=` 条目），`-N 38 -Forms`（末条 = `Form=Layer\FLayer.frm`）→ `.build\C3.exe` 启动后即退出，**0xC0000005**，`c3-error.log` 不生成；`-N 37 -Forms`（不含窗体）正常 → 窗体模块是触发条件。
- **反证（逐条排除 UB）**：
  - `--dump-frm FLayer.frm` 单独跑正常（exit 0）→ 窗体**解析**阶段无问题，崩点在之后；
  - `.build-rwdi`（RelWithDebInfo，`/O2 /Ob1`）**不崩**（完整跑到 cl 阶段）；
  - `.build-rel2`（`CMAKE_BUILD_TYPE=Release` + `/O2 /Ob2 /DNDEBUG /Zi`，即 release 代码生成 + PDB）**不崩**；
  - `cmake --build .build --clean-first` 全量重建后，**Release 含窗体直接跑到 0 error C**。
- **结论**：崩因是 **`.build` 增量构建的陈旧对象**。本文件第 344/385 行与交接文档早有同类记录（「增量构建可能产生陈旧对象 → 运行时 0xC0000409 崩溃，clean-first 全量重建可解决」），本轮又踩了一次，且被误判为「release 独崩 = 未初始化/UB」。**新规则：见到 release-only 崩溃，先 `--clean-first` 全量重建再复现，仍崩才考虑 UB。**

## 2. 顺带补齐的抓栈工具（已保留）

本机未装 `cdb`/`windbg`，pdump 之类也不可用，因此改为**进程内**符号化：

- `src/driver/main.cpp`：`C3_CRASH_TRACE=1` 时安装 `SetUnhandledExceptionFilter`，用 `CaptureStackBackTrace` + dbghelp（`SymFromAddr` / `SymGetLineFromAddr64`）打印异常码/地址 + `函数+偏移 (文件:行)` 调用栈；**未设置该环境变量时不安装任何处理器，行为与原先完全一致**。
- `CMakeLists.txt`：`WIN32` 下给 `c3` 目标链接 `dbghelp`。
- 用法：`set C3_CRASH_TRACE=1` + 带 PDB 的构建（`.build-rwdi` / `.build-debug`）。

以后真遇到 UB 崩溃可直接定位，不必依赖外部调试器。

## 3. 含窗体全量回归：1 → 0

纳入窗体后，原先那 7 个「窗体假阳性」（cLogs/cLayer 引用 `FLogs`/`FLayer`）**全部消失**（窗体模块现在参与编译），只剩 1 个真实错误。

### 唯一剩余错误：`FLogs.c(175)` C2440

```vb
' vbman/src/Logs/FLogs.frm:175
Clipboard.SetText Text1.Text
```

```c
/* 生成（错误） */
vb6_Clipboard_SetText(vb6_VariantFromValue(vb6_GetControlText(vb6_hwnd_Text1)  /* ctrl prop read */));
/* vb6_Clipboard_SetText 形参是 BSTR，实参却是 vb6_VARIANT → C2440 */
```

### 根因

- `cQRcode.cls:34` 有 `Public Function SetText(ByVal Content As Variant) As cQRcode`。
- `IndexOrCallExpr` 的 **class-unaware 兜底**（对象非本类、类感知未命中时用 `symTab_.lookupModule(memberName)` 兼容旧行为）命中了这个 external 符号 → `calleeParams = [ByVal Variant]`。
- 于是 Fix 086 / Fix 024P2 的「实参 → Variant 包装」被触发。
- 但 callee 其实早已被 `visit(MemberAccessExpr)` 的 **`Clipboard` 硬编码分支**解析成 RTL 函数 `vb6_Clipboard_SetText`，**VB 侧根本不存在形参表**。

### 修法（092z）

在 class-unaware 兜底前加判定：对象是 **VB6 保留全局对象**（`clipboard` / `screen` / `printer` / `forms` / `debug` / `err` / `app`）时跳过兜底，`calleeParams` 保持为空（实参按原样透传）。这些名字不可能被用户标识符占用，故判定安全。

### 验证

- 含窗体全量 129 条目：`error C` **1 → 0**；
- 无窗体 125 条目：仍为 7（无回归）。

## 4. 新暴露的链接期问题（下一步）

同一次运行在**链接阶段**报出：`LNK2005` 重定义（`FToastDrawer`/`FToastCenter` 的 `m_Theme`/`Sad`/…；`mDelay`/`Tools` 的 `Delay`；`cModbusTransportTCP`/`cWebSocketClient` 的 `vb6_evt_wrap_m_*`）+ `LNK1104: 无法打开文件 msvbvm60.lib`。详见 handoff 第 10 节。

### 4.1 `msvbvm60.lib` 追根（2026-09-11 补充，纠正初次「配置缺口」判读）

- **来源是源码，不是工程配置**：`cgen_decl.cpp:1219` 对每条 VB6 `Declare ... Lib "X"` 都生成 `#pragma comment(lib, "X.lib")`；VBMAN 源码有 **10 个模块 14 处** `Declare ... Lib "msvbvm60"`（`mdTlsThunks.bas`、`cAsyncSocket.cls`、`cTlsSocket.cls`、`mdTlsSodium.bas`、`mdTlsNative.bas`、`ToolsJsonUcs.bas`、`cHttpRequest.cls`、`cHttpDownload.cls`、`cToolsArray.cls`），生成物里遂出现 `#pragma comment(lib, "msvbvm60.lib")`。
- **只涉 3 类符号**：`Alias "VarPtr"`（`ArrPtr`）、`Alias "__vbaObjSetAddref"`、`Alias "#644"`（按**序号**导入，源码名 `SplitLongToBytes`）。
- **x64 补不了这个库**：本机 `SysWOW64\msvbvm60.dll` 存在（32 位），`System32` 下无 64 位版本，SDK / VS 目录里没有任何 `msvbvm60.lib` —— VB6 运行时只有 32 位。故 `--arch x64` 下「补 msvbvm60.lib」不可行，只能改道 RTL。
- 首次判读为「bisect 工程配置缺口、非代码缺陷」是错的：它既源于源码、也需生成器提供处理策略。
