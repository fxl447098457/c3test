# 85 - C3Fix 092y：模块限定调用前缀兜底取工程模块规范名

> 日期：2026-09-11
> 基线：无窗体 125 模块 bisect **8 → 7**（提交 `ec7fa10`）
> 结论：**无窗体 bisect 面完全收敛** —— 剩余 7 个错误全部是 cLogs/cLayer 的窗体假阳性，真实代码缺陷 0、配置缺口 0。

## 现象

`cHttpServerResponse.cls` 440 行：

```vb
Header("Server") = Ver & ServerName & " " & Common.Version()
```

生成的 C：

```c
vb6_cVBMAN_Version(&(void*){0}, 0)
```

报 **C2198**（`int16_t? vb6_cVBMAN_Version(vb6_cls_cVBMAN*, void**, int)` 实参太少）。正确应为：

```c
vb6_Common_Version(&(void*){0}, 0)   /* BSTR vb6_Common_Version(void**, int) */
```

## 排查与根因

### 先推翻交接文档的判读

交接文档（092v 条目）把此错误记为：

> `Common` 是**外部 ActiveX 引用**的模块……且不在 vbman 任何 vbp 内 → 符号表无该模块 → 属配置/缺口。

实际核查 `vbman/src/VBMAN.vbp`：

```
61: Class=cVBMAN; ...\StaticClass\cVBMAN.cls
65: Module=Common; Common\Common4DLL.bas
```

`Common` 就在工程内，并且 `Common4DLL.bas` 定义了 `Public Function Version(Optional HostApp As Object) As String`。**该错误被误判搁置了整整一轮。**

### 真实根因：同名符号 storageKey 冲突 + 先到先得

`Symbol::storageKey()` 对 `Function` 返回的就是 `lowerName`（无后缀）。于是：

| 符号 | storageKey |
|---|---|
| `Common.Version`（模块函数） | `version` |
| `cVBMAN.Version`（类方法） | `version` |
| `Common.Path` | `path` |
| `cVBMAN.Path` | `path` |

driver 注入跨模块公开符号时按 storageKey 去重、**先到先得**（`defineExternal`）。`cVBMAN` 胜出 → 在 `cHttpServerResponse` 的模块作用域里：

- `lookupModule("Version")` 命中 `cVBMAN.Version`；
- 由于 `Common` 的 **两个** 公开成员（`Version`/`Path`）**全部**被同键挤掉，该作用域内**不存在任何** `sourceModule == "Common"` 的 `isExternal` 符号。

于是 Fix 092v 的兜底扫描（遍历 `moduleScope()->symbols()` 找 `sourceModule` 匹配限定符）**必然落空**，`sourceMod` 退回 `memSym->sourceModule`（`"cVBMAN"`）→ 前缀错误 → 少一个 `me` 参数。

> 这也解释了为什么 092v 在 `cVBMAN.cls` 自身内部能正确生成 `vb6_Common_Version(HostApp, 1)`：那里 `memSym` 是本类的 `Version`（非 external），走的是 else 分支「限定名即模块名」；只有**跨模块消费点**才踩到。

## 修法

`src/backend/cgen_expr.cpp`（模块限定调用的前缀判定，092v 块内）增加兜底：

```cpp
// Fix 092y: 兜底 — 限定符本身就是工程内的**标准模块**名时, 直接采用其规范名.
if (modCanon092v.empty()) {
    for (const auto& extMod092y : externalModules_) {
        if (Symbol::toLower(extMod092y) != objL092v) continue;
        Symbol* extSym092y = symTab_.lookup(extMod092y);
        if (extSym092y && extSym092y->kind == SymbolKind::Class) break;  // 类模块不参与
        modCanon092v = extMod092y;
        break;
    }
}
```

- 数据源用现成的 `externalModules_` —— driver 在 `generate()` 里传入「除当前模块外的全部模块名（**规范大小写**）」，代码中已有 3 处 `toLower(extMod)` 比对的既有惯例；
- 用 `symTab_.lookup(extMod)` 是否为 `SymbolKind::Class` 把类模块排除，避免影响 `类名.成员` / 窗体名.成员 的既有语义。

## 验证

- 生成 `vb6_Common_Version(&(void*){0}, 0)`，与签名 `BSTR(void**, int)` 匹配；`cHttpServerResponse.c` 中已无 `cVBMAN_Version`；
- bisect **8 → 7**，C2065 仍 5（无回归）；
- 剩余 7 = cLogs×5 + cLayer×2，全部为窗体假阳性。

## 教训

1. **交接文档的「根因」也需复核**：凡「外部模块 / 配置缺口」类结论，归档前先在 `.vbp` 里 `search_content` 核实；并优先怀疑「同名符号 storageKey 冲突」这类更常见的内部原因。
2. **`storageKey(Function) == lowerName` 是全局命名空间的薄弱点**：任何「模块函数 vs 类方法」同名都会让模块函数在跨模块消费点静默消失。若后续再出现类似「前缀取到别的模块」，先查 storageKey 冲突。
3. **兜底条件要绑在「限定符本身」上**：092v 试图用「作用域内是否存在该模块的 external 符号」间接判断模块身份，在成员被全部挤掉时不成立；直接判断「限定符是否就是工程内模块名」才是稳的。
