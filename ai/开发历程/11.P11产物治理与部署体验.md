## 目标

解决 dist/demos 全量测试（5/6通过）暴露的 5 个问题，让 C3 在用户侧体验真正"开箱即用"。

问题来源：
1. 默认输出目录为 `output/`（相对 CWD），不合直觉——用户期望 .exe 出现在源文件旁边
2. 中间产物（.c/.h/.obj）留在用户项目目录，污染工作区
3. RTL 释放 8 个 .c/.h 源文件再到临时目录编译，速度慢（P11.3，待做）
4. 用户无 vcvarsall 环境时 cl.exe 找不到标准头文件（P11.4，待做）
5. --help 暴露了大量内部调试选项（P11.5，待做）

## 过程

### P11.1: 默认输出目录改为源码所在目录

**原有逻辑：**
```cpp
std::string outputDir = effectiveOpts.outputDir.empty() ? "output" : effectiveOpts.outputDir;
```
所有 .c/.h/.exe/.dll 都写入 CWD 下的 `output/` 子目录。

**新逻辑——三级优先级：**

| 优先级 | 来源 | 说明 |
|--------|------|------|
| 1 | `--output-dir <dir>` | 用户显式指定 |
| 2 | VBP `Path32="xxx"` | VB6 工程文件的输出路径字段 |
| 3 | 源文件所在目录 | 单文件: .bas 父目录; 多文件: "." |

**实现：**
- `driver.hpp`: 新增 `projectPath32_` 成员变量
- `driver.cpp` Change A: VBP 解析阶段保存 `project.outputPath` 到 `projectPath32_`（通过 `project.resolvePath()` 解析相对路径）
- `driver.cpp` Change B: 重写 stage 4+5 的目录决策逻辑，`outputDir = std::filesystem::absolute(outputDir)`

**Path32 字段说明：** VB6 的 .vbp 文件中 `Path32="xxx"` 指定编译输出目录。`VbpParser` 已在 P6 阶段实现了对该字段的解析（`project.outputPath`），但一直未被 driver 使用。

### P11.2: 中间产物移至会话临时目录

**原有流程：**
```
用户项目目录/output/
  ├── hello.h       ← 生成
  ├── hello.c       ← 生成
  ├── hello.obj     ← MSVC /Fo
  ├── hello.exe     ← MSVC /Fe
  └── _c3_msvc_out.txt  ← 临时日志
```
.c/.h/.obj 和临时文件全部污染用户目录。

**新流程：**
```
%TMP%\C3C\{timestamp}\           ← session.sessionDir() (中间产物)
  ├── hello.h                    ← 代码生成
  ├── hello.c                    ← 代码生成
  ├── dll_entry.c                ← ActiveX DLL 入口
  ├── activex_dll.def            ← DLL 导出定义
  ├── activex_dll_typelib.rc     ← TypeLib RC
  ├── activex_dll_typelib.res    ← 编译后资源
  ├── TestAXDLL.tlb              ← TypeLib
  ├── _c3_msvc_out.txt           ← 临时日志
  ├── hello.obj / ...            ← MSVC /Fo
  └── rtl\                       ← RTL 运行时 (session.rtlDir())
      ├── vb6rtl.h / .c
      ├── vb6com.h / .c
      └── ...

用户项目目录/
  └── hello.exe                   ← 唯一最终产物 (MSVC /Fe)
```

**实现细节：**

1. **SessionManager 扩展**: 新增 `sessionDir()` getter，暴露会话根目录（之前只有 `rtlDir()` 返回 `sessionDir_/rtl`）

2. **session.create() 调用提前**: 从 `runLinker()` 移到 `compile()` 的 stage 4 之前，因为代码生成也需要写入中间产物目录

3. **代码生成目标变更**: `runCodeGeneration(effectiveOpts, intermediatesDir)` 而非 `runCodeGeneration(effectiveOpts, outputDir)`

4. **MSVC 驱动新增字段**: `MsvcDriverOptions` 新增 `srcDir`（生成代码的 include 路径）和 `objDir`（.obj 输出目录）

5. **msvc_driver.cpp 三处修改**:
   - `/I{srcDir}`: 让 MSVC 找到生成的 .h 文件
   - `/Fo{objDir}`: .obj 输出到会话临时目录
   - `_c3_msvc_out.txt` 放在 `objDir`（临时），`c3-error.log` 放在用户项目目录（持久）

6. **TypeLib 路径修复**:
   - .tlb 生成在 `intermediatesDir`（和 .c/.h 一起）
   - `runLinker` 中查找 .tlb 也用 `intermediatesDir`
   - RC 文件中 .tlb 路径使用正斜杠（避免反斜杠被 RC 编译器当成转义字符）

7. **cleanup 时机**: 无论成功或失败，都执行 `session.cleanup()` 清除中间产物。失败时先写 `c3-error.log` 再清理。

**writeErrorLog() 函数:**

编译失败时在用户项目目录生成 `c3-error.log`，包含：
- 失败阶段（code-generation / linking）
- 诊断信息（`diag_->toString()`）

注意：MSVC 编译失败时的详细日志由 `msvc_driver.cpp` 自行写入 `c3-error.log` 并输出到 stderr，`writeErrorLog()` 只负责 driver 层面的诊断信息，不重复读取已删除的临时文件。

## 技术难点与解决

### 1. SessionManager.create() 返回值歧义

`create()` 返回 `rtlDir_`（RTL 子目录），不是 session 根目录。P11.2 需要 session 根目录作为中间产物目录。

解决：新增 `sessionDir()` getter，`intermediatesDir` 使用 `session.sessionDir()` 而非 `session.create()` 返回值。

### 2. RC 路径反斜杠转义

RC 文件中 `.tlb` 绝对路径含反斜杠（如 `C:\Users\...`），RC 编译器将 `\a`、`\t` 解释为转义字符，导致 "file not found"。

解决：路径中反斜杠替换为正斜杠后再写入 RC 文件。
```cpp
std::string tlbPathForRc = tlbPath;
for (auto& c : tlbPathForRc) { if (c == '\\') c = '/'; }
rcFile << "1 TYPELIB \"" << tlbPathForRc << "\"\n";
```

### 3. PowerShell 5.1 编辑 C++ 大文件

PS5.1 对 C++ `<<` 运算符、反斜杠字面量、中文匹配等均有解析问题。

解决：
- 编辑内容写入临时 .txt 文件（text-writer_write_text，无 PS 解析问题）
- PS 脚本只做行号定位 + 文件拼接（避免内联 C++ 代码字符串）
- 中文注释行用 ASCII-safe 模式搜索（避免 `-match` 中文字符串失败）

## 决策

1. **输出目录优先级**：`--output-dir` > VBP Path32 > 源文件所在目录。覆盖最常见场景，同时兼容 VB6 原有行为（Path32）。
2. **中间产物 = session 根目录**：代码生成到 `sessionDir()`，RTL 在 `sessionDir()/rtl/` 子目录。层次清晰，cleanup 一次删除。
4. **c3-error.log 双层写入**：编译失败时 msvc_driver 写 MSVC 详细日志，driver 写诊断摘要，各自负责各自阶段。
4. **TypeLib 在 intermediatesDir 生成**：.tlb 是中间产物（最终嵌入 DLL 资源），不应出现在用户目录。如果用户需要 .tlb 文件，可单独导出（未来功能）。
5. **RC 路径用正斜杠**：这是 RC 编译器的标准做法，反斜杠在 RC 文件中有特殊含义。

### P11.6: parseBlockUntil 裸 End 语句 bug 修复

**问题发现过程：**
dist/demos/realVBP 测试 5/6 通过，唯一的失败 工程1.vbp 报错：
`
Form1.frm(30,8): error VB2005: expected 'End Sub' (got NewLine)
Form1.frm(31,1): error VB2002: unexpected token at module level: End
`

起初以为是 frm parser 嵌套 Begin...End 块解析 bug，但经过逐步调试发现：
1. frm parser 的递归解析逻辑完全正确（End 正确配对对应 Begin）
2. lineIdx 正确停在代码段起始位置（第69行 Attribute VB_Name）
3. **真正原因**：VB 代码段中 MQ_Click() 过程包含裸 End 语句（终止程序执行），但 parseBlockUntil({TokenKind::End}) 一遇到 End token 就停止解析块体，不管它是块终止符（End Sub/End Function）还是裸 End 语句

**根因：**
parseBlockUntil 中 cur_.kind == TokenKind::End 判断过于宽泛，没有区分：
- End Sub / End Function / End Property — 块终止符（应该停止）
- End — 裸语句（终止程序执行，不应停止块解析）

**修复：**
在 parseBlockUntil 的循环中，当 End 在 endKinds 列表中且当前 token 是 End 时，增加 isEndBlock() 检查：
- isEndBlock() 返回 true — End 后面跟 Sub/Function/Property 等，是块终止符，停止解析
- isEndBlock() 返回 false — 裸 End 语句，不停止，继续解析为 EndStmt

修改文件：src/parser/parser_stmt.cpp 的 parseBlockUntil 函数

**测试结果：**
- C3 --syntax-only test_end.bas（Private Sub 包含裸 End）— PASS
- realVBP demo 不再报 parse error，进入正常的语义分析阶段
- 71/71 回归测试零失败

**修改文件清单：**

| 文件 | 操作 | 说明 |
|------|------|------|
| src/parser/parser_stmt.cpp | 修改 | parseBlockUntil 增加 isEndBlock() 区分裸 End 与块终止符 |

### P11.7: 默认属性解析

**问题：** VB6 中 `a = Text1` 应读取 Text1 的默认属性 Text，但 c3 生成的代码是 `vb6_BSTR_Assign(&a, Text1)` — Text1 未解析为属性读取。

**根因：** `visit(IdentifierExpr&)` 中默认属性读取代码放在 `foundSym && (Variable || Constant)` 检查之后，该检查对控件变量（Variable + isBuiltin + Object类型）过早 return，导致默认属性代码永远不执行。

**修复：**
1. `cgen.hpp`: 新增 `static const char* getDefaultPropertyName(FrmControlType ctrlType)` 声明
2. `cgen.cpp`: 实现 `getDefaultPropertyName()` — 10种控件默认属性映射（TextBox→Text, Label→Caption, CheckBox→Value 等）
3. `cgen.cpp`: 在 `visit(IdentifierExpr&)` 的 foundSym 变量处理块中，检查 `isBuiltin && type == Object` 时触发默认属性读取，在 early return 之前完成
4. `cgen.cpp`: 在 `visit(AssignmentStmt&)` 中处理目标为控件 IdentifierExpr 时的默认属性写入

**代码生成验证：**
| VB6 代码 | 生成代码 |
|----------|----------|
| `a = Text1` | `vb6_BSTR_Assign(&a, vb6_GetControlText(vb6_hwnd_Text1) /* default prop: .Text */)` |
| `Label1 = a` | `vb6_SetControlText(vb6_hwnd_Label1, a) /* default prop: .Caption */` |
| `b = Check1` | `b = vb6_GetCheckValue(vb6_hwnd_Check1) /* default prop: .Value */` |
| `Check1 = 1` | `vb6_SetCheckValue(vb6_hwnd_Check1, 1) /* default prop: .Value */` |

**修改文件：** src/backend/cgen.hpp, src/backend/cgen.cpp

### P11.3: RTL 预编译 .lib 嵌入（源码保护）

**问题：** RTL .c/.h 源文件以明文 RCDATA 嵌入 c3.exe，用户可用资源编辑器轻松提取完整源码。

**方案：** 将 RTL .c 预编译为 .lib 静态库，替换 RCDATA 中的源码。

**实现：**
1. **预编译脚本** `.temp/build_rtl_libs.bat`: 用 MSVC `/c /MT /O2` 编译 4 个 .c 为 .obj，再用 lib.exe 打包成 3 个 .lib：
   - `vb6rtl.lib` = vb6rtl.obj + vb6com.obj（所有程序）
   - `vb6rtl_dll.lib` = vb6comserver.obj（ActiveX DLL）
   - `vb6rtl_gui.lib` = vb6forms.obj（GUI 程序）
2. **c3rtl.rc**: 从 8 个 RCDATA（4.h + 4.c）改为 7 个（4.h + 3.lib），资源 ID 100-112
3. **rtl_embedded.hpp/cpp**: 更新枚举和提取列表（.h + .lib），不再有 .c
4. **msvc_driver.cpp**: 从 `cl.exe ... vb6rtl.c vb6com.c /link` 改为 `cl.exe ... /link ... vb6rtl.lib`

**关键决策：/MT 静态 CRT**
- 初次用 `/MD`（动态 CRT）编译 .lib，导致 LNK4098（MSVCRT 冲突）和 LNK2019（__imp_ 未解析）
- 改为 `/MT`（静态 CRT），.lib 不依赖 MSVCRT DLL，链接时零冲突零警告

**安全验证：** c3.exe 二进制中不含 `vb6rtl.c -` / `vb6com.c -` / `vb6forms.c -` 等源码特征，仅含 COFF .lib 归档格式。

**修改文件：** src/driver/c3rtl.rc, src/driver/rtl_embedded.hpp/cpp, src/backend/msvc_driver.cpp, src/rtl/lib/*.lib（新增）

### P11.4: MSVC 环境三层自动检测

**问题：** 用户未运行 vcvarsall.bat 时 cl.exe 不在 PATH，编译直接失败。错误消息要求用户手动运行 vcvarsall，体验差。

**方案：** 三层 fallback 自动检测 MSVC 环境：

| 优先级 | 方法 | 覆盖场景 |
|--------|------|----------|
| 1 | `VCINSTALLDIR` 环境变量 | 用户已手动运行 vcvarsall.bat |
| 2 | vswhere.exe（固定路径） | VS2017+ 正常安装 |
| 3 | 注册表 `HKLM\...\SxS\VS7` | VS2015 及更早版本 |

**实现：**
1. `msvc_driver.hpp`: 新增 `findVcvarsallBat()`、`findVsInstallPath()`、`buildVcvarsPrefix()` 静态/const 方法
2. `msvc_driver.cpp`:
   - `findVsInstallPath()`: 运行 vswhere.exe（`%ProgramFiles(x86)%\Microsoft Visual Studio\Installer\vswhere.exe -all -latest -property installationPath`），捕获输出；失败则查注册表
   - `findVcvarsallBat()`: 拼接 `{VS路径}\VC\Auxiliary\Build\vcvarsall.bat`
   - `buildVcvarsPrefix()`: 当 VCINSTALLDIR 未设置时返回 `call "vcvarsall.bat" x64 >nul 2>&1 && `
   - `compileAndLink()`: fullCmd 前面加 vcvarsPrefix
   - `isMsvcAvailable()`: 三层检测更新
3. `driver.cpp`: 错误消息改为 "install Visual Studio 2017+ with C++ workload"

**vswhere 关键发现：** 需加 `-all` 标志，因为 `-latest` 只返回 isComplete=true 的安装。某些安装状态（如待更新）isComplete=false 但 vcvarsall.bat 完全可用。

**验证：** 在 cmd.exe 中清除 VCINSTALLDIR 后运行 C3，成功通过 vswhere 自动找到 VS2022 并编译。

**修改文件：** src/backend/msvc_driver.hpp, src/backend/msvc_driver.cpp, src/driver/driver.cpp

## 决策（本轮）

1. **P11.3 .lib 替代 .c**：源码保护优先，.lib 无法还原 .c 源码，而 .c 可以轻松提取。编译性能提升是额外收益。
2. **/MT 静态 CRT**：避免 MSVCRT DLL 依赖冲突，.lib 使用 /MT 编译，用户代码也用 /MT，链接零冲突。
3. **vswhere -all 标志**：VS 安装可能 isComplete=false 但完全可用，-all 确保检测到所有安装。
4. **通用属性 switch 前匹配**：Left/Top/Width/Height/hWnd 是所有可见控件通用的，放在 switch 前避免每个 case 重复，且 default 分支也能匹配。
