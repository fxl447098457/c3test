# 05. P5集成测试 — 跨模块符号解析

> 日期: 2026-06-26
> 阶段: P5 集成测试
> 状态: 进行中

---

## 目标

实现VB6多模块工程(.vbp)的跨模块符号解析，使模块A调用模块B的Public函数时，生成的C代码能正确链接。

## 过程

### 5.1 问题定位

VBP多模块编译（MainMod.bas + MathUtils.bas）在MSVC链接阶段失败：
- **MathUtils.c** 定义 `vb6_Add` / `vb6_Multiply`（带 `vb6_` 前缀）
- **MainMod.c** 调用 `Add` / `Multiply`（不带前缀）
- 链接器找不到 `Add` / `Multiply` 符号

根因：每个模块有独立的 SymbolTable，语义分析时 MainMod 找不到 MathUtils 的 Public 符号，CCodeGen 的 `visit(IdentifierExpr&)` 调用 `symTab_.lookupModule("Add")` 返回 nullptr，直接用了 `cIdent("Add")` 而不是 `cProcName`。

### 5.2 方案设计

采用"方案C — 最简单路径"：

| 步骤 | 文件 | 变更 |
|------|------|------|
| 1 | `symbol_table.hpp` | Symbol 新增 `isExternal`/`sourceModule` 字段 |
| 2 | `symbol_table.cpp` | 新增 `defineExternal()`/`getPublicSymbols()`/`getExternalModuleNames()` |
| 3 | `driver.hpp/cpp` | 新增 `runCrossModuleResolution()` 阶段 |
| 4 | `cgen.hpp` | `generate()` 签名新增 `externalModules` 参数，新增 `isMultiModule_`/`moduleName_` |
| 5 | `cgen.cpp` | `cProcName()` 支持跨模块前缀 `vb6_<Module>_<Proc>`，`visit(IdentifierExpr&)` 检测外部符号，`generate()` 输出跨模块 `#include` |

### 5.3 实现细节

**Symbol 扩展** (symbol_table.hpp)：
```cpp
bool isExternal = false;       // 定义在其他模块中
std::string sourceModule;      // 源模块基名（如 "MathUtils"）
```

**跨模块链接 pass** (driver.cpp `runCrossModuleResolution`)：
1. 收集每个模块导出的 Public 符号
2. 构建全局查找表 `lowerName → (模块索引, Symbol*)`
3. 对每个模块，将其他模块的 Public 符号注入为外部符号（`isExternal=true, sourceModule=模块名`）
4. 如果本模块已有同名本地定义则跳过（不覆盖）

**CCodeGen 多模块模式**：
- `cProcName(name, public, sourceModule="MathUtils")` → `vb6_MathUtils_Add`
- `cProcName(name, public, sourceModule="")` + `isMultiModule_=true` → `vb6_MainMod_Main`
- `cProcName(name, private, ...)` → `vb6_Main`（Private 不变）
- 单模块项目 `isMultiModule_=false` → 保持 `vb6_Main` 原格式
- `.h` 文件自动 `#include "MathUtils.h"` 等跨模块头文件

**Scope 友元**：`SymbolTable` 需要 `defineExternal` 直接向 `Scope::symbols_` 写入，添加 `friend class SymbolTable`。

## 问题

1. **冗余跨模块 #include**：MathUtils.h 包含了 MainMod.h（MathUtils 并未调用 MainMod 的函数），因为 `runCrossModuleResolution` 把所有其他模块的 Public 符号都注入了。功能无影响（#ifndef guard 保护），但不够精确。后续可优化为只注入被实际引用的符号。

2. **CMakeCache.txt 零宽字符污染**：CMake 运行后 CMakeCache.txt 被注入零宽字符，导致重新配置失败。需要删除 .build 目录重建。已用 text-writer 写入的所有源文件都是干净的。

3. **exe 输出路径**：VBP `ExeName32="TestVBP.exe"` 无路径前缀时，MSVC 在当前工作目录生成 exe，不在 output 目录下。需要改进 runLinker 中的路径处理。

## 决策

1. **跨模块命名格式选择**：`vb6_<Module>_<Proc>` 而非 `vb6_<Proc>`，避免不同模块同名 Public 函数冲突。Private 函数保持 `vb6_<Proc>`（static 限制在本文件内）。

2. **单模块兼容性**：通过 `isMultiModule_` 标志区分，单模块项目保持原有命名格式不改变，确保向后兼容。

3. **无条件注入 vs 按需注入**：选择无条件注入所有 Public 符号（简单但不精确），而非扫描 AST 找出实际引用的标识符（复杂但精确）。后续优化。
