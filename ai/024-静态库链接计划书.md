## 一、价值

今天所有外部 C 函数都经 `Declare ... Lib "user32.dll"` 走**链接期**解析：C3 发 `extern <ret> __stdcall vb6_di_<Export>(...)` + `#define <VB名> vb6_di_<Export>` + `#pragma comment(lib, "<lib>.lib")`（`cgen_decl_api.cpp:97-171`），实现由 RTL 的 `vb6_di_*` 桩提供，桩体是**直接转发**（`vb6_di_win32_stubs.c:55`），不是 `GetProcAddress`。真正的运行期加载只用于四类特例：gdiplus（C++ 头无法直调）、无导入库的 DLL（cryptdlg/hhctrl）、序号导出、msvbvm60 运行时。静态旁路给三样东西：

1. **免注册、免部署**：链进 exe，不随附 DLL；
2. **省掉 `vb6_di_*` 一层跳转**（**不是**"省掉 `GetProcAddress` 查找"——那条路本来就不存在；gdiplus/序号那几类特例除外）。收益量级要诚实：一线直转的函数，省下的是一次 `jmp`；
3. **能直接用 C 生态的算法库**（sqlite、压缩、编解码、纯计算 kernel），且调用约定可 `CDecl`。**这一条才是本特性的主价值**——它是由 0 到 1，前两条只是从 1 到 1.02。

⚠️ 同时必须记住一个反面事实：`vb6_di_*` 那一层**不只是开销，它是 ABI 适配层**——C3 调用点用的原型是 `intptr_t` 加宽过的（`cgen_decl.cpp:90-98` 的 Fix 081e），桩靠**函数指针 cast 到真实原型**让编译器重做编组。静态直连等于把这件活接回自己手里，这正是 §五 L1 想用一张尺寸表手工解决的那件事。§五之三给出的"选项 B"就是为了**不丢这一层**。

## 二、对齐对象与它的语法问题

twinBASIC 的 Static Linking（docs.twinbasic.com/Features/Advanced/Static-Linking）：`.lib`/`.obj` 放进工程的 *Miscellaneous files* 目录，然后

```
Import Library "/Miscellaneous/sqlite3_64.obj" As SQLITE3 Link "stdlib", "kernel32"
Declare PtrSafe Function sqlite3_open CDecl Lib SQLITE3 (ByVal filename As String, ByRef ppDb As LongPtr) As Long
```

其文档自己点名的坑：x86 StdCall 会按参数总字节修饰（`int f(int x, short y)` → `f@6`），所以建议用 `CDecl`。

三处冗余，本文的设计全部去掉：

- **`Import Library` 新语句** → 不需要。`Lib "sqlite3.obj"` 里的串就是文件名。
- **`As NAMESPACE`** → 不需要。命名空间本来就是 `Lib` 串（与 VB6 已有心智一致）。
- **`Link "dep1","dep2"` 依赖列表** → 不需要。未解析符号由链接器报；本项目系统库常量已在 `src/driver/msvc_driver.cpp:229+`（ole32/oleaut32/advapi32/user32/gdi32…）带着。

## 四、核心决策

- **E1 语法 = 一个取值，不是一条语句**：`Lib` 串以 `.lib/.obj`（或 MinGW 后端下 `.a/.o`）结尾 → 静态模式；否则**今天的行为一字不变**。
- **E2 寻址放工程层**：`Package`/vbp 新键 `LibDir=`（可重复）或 CLI `--libdir`；解析基准 = vbp 所在目录（与 `VbpProject::resolvePath()` 同族，绝不引入 cwd 基准）。文件找不到 → 编译期报错并打印搜索过的那几个根。
- **E3 静态分支不得触碰动态分支的名字生成**（本特性的头号护栏）。理由比首版说的更强：动态路查的符号名是 `vb6_di_<Export>`（RTL 里定义的），静态路查的是归档符号——**两边符号空间本就不重叠**，所以"互不影响"是可以低成本买到的，不是靠小心。`tests/` 里现有 `Declare` 相关用例 + 8 文件 `--emit-c` 逐字节护栏必须双跑。
- **E4 自动修饰分两级**（第五节），缺省开启；写了 `Alias "..."` 则**完全按字面**，这是逃生舱，语义与 VB6 一致。
  - ⚠️ **补充实现约束（首版漏）**：`Alias "_foo@12"` 这种值**不能直接当 C 标识符 `extern`**（`@` 非法）。所以"按字面用"必须另有落点，候选两条，T02 必须选一条并实测：① `#pragma comment(linker, "/alternatename:<c3内部名>,_foo@12")`（`@` 在 linker 指令的字符串里是合法的）；② 生成 `.asm` 别名桩。**这条不解决，E4 的逃生舱就是空的。**
- **E5 只承诺纯 C 导出**，不承诺 C++（厂商私有修饰规则，MSVC 与 gcc 两套）。遇未解析符号直接报"本特性不覆盖 C++ 修饰名"，别让人拿 Boost 的 `.lib` 来问。

## 五、实现路线与修饰名

### 5.0 两条路线，**B 优先**

"静态 Declare 怎么落地"有两条路，首版默认了 A，评审后改为**先走 B**：

- **路线 A（直连）**：静态模式下不发 `vb6_di_*`，改为 `extern <ret> <conv> <符号名>(<C3原型>);` + 调用点直呼。省一层跳转，但**丢掉了 `vb6_di_*` 的 ABI 适配**（函数指针 cast 那段），把编组责任收回 C3 自己 → 这正是 L1 尺寸表要手工解决的问题。
- **路线 B（沿用桩，换实现）**：静态模式下**继续用 `vb6_di_*` 命名空间**，只把桩的实现从"转发到 import lib"换成"直接引用归档符号"。
  - 调用点 ABI **一字不改** → E3 的逐字节护栏几乎免费；
  - ABI 适配层（cast）**保留**；
  - 两条路的符号空间天然分离（动态=`vb6_di_<Export>`，静态=归档符号）；
  - 代价：`cgen_decl_api.cpp` 要按 `Lib` 取值分叉决定"是否 emit `#pragma comment(lib,...)`" + 桩体实现模式，可能牵到 `gen_di_stubs.ps1`。

**结论：先按 B 走 T02，A 作为 B 不成立时的退路。** 理由很直接——B 是"新增旁路"（E1 的原意），A 是"改造公共路径"，风险等级不同，而 B 恰好把 L1 整块降级（见下）。

> **⚠️ 实施结论（2026-09-23，T02 已按 A 落地，见 §十二）：本节的路线选择已反过来。**
> 上面给 B 记的那条"代价"（"可能牵到 `gen_di_stubs.ps1`"）实际是**硬依赖**：B 要求为每个工程
> **生成一份桩 `.c`**，而桩体所需的原型信息（`retType`/`callConv`/`params`）只在 `cgen_decl_api.cpp`
> 里算得出来，且 `gen_di_stubs.ps1` 是**构建期**脚本、不在工程编译时运行 → B 要新造"原型注册表 +
> 去重 + 一份新的生成文件"三样东西。而 A 实测**根本没碰公共路径**：它只是 `isStaticDecl` 下的一条
> 平行分支，逐字节护栏 9/9 全同即为证。**A 反而比 B 更像"新增旁路"。**
> 另外 A 顺带消掉了 §五之三-3 担心的 SR8 隐患 —— 没有桩就没有"把 `char**` 当 BSTR 解读"的机会。

### L0 让编译器算修饰名（**主方案**，取代首版 L1 的地位）

x86 stdcall 的 `_name@N` 由谁算？**不要 C3 算，让 MSVC 算。** C3 静态模式下发的 `extern` 声明就是 MSVC 的输入，编译器自己会算出 `_name@N`（x86）或 `name`（x64）。C3 不需要知道 N，只需要：

1. 调用约定（`callingConv`，已有）；
2. **声明的宽度与库的 C 原型等价**。

第 2 条是**同编译器保证同 ABI**的推论：库也是 MSVC 编的（§六 边界 1），同一个编译器对同一份原型算出的修饰名必然相同。于是首版 §五 那三条"必须实测的未知项"**全部消失**——它们之所以是未知项，正是因为"手工算 N"这个方法要求你复刻 C 侧的隐藏行为；换成编译器算，隐藏行为本来就归编译器管：

| 首版未知项                         | 在 L0 下的处置                                                      |
| ----------------------------- | -------------------------------------------------------------- |
| 固定字符串 `String * N` 是否多传隐藏长度参数 | 不关心。C3 声明 `char*` 就按 `char*` 算；库若真多传，那是库的 ABI，C3 无论如何对不上，也不该去对 |
| UDT byval 按 `sizeof` 还是按指针    | MSVC 按真实 `sizeof` 计入，且库那边同规则 → 自动一致                            |
| 结构体返回的隐藏指针是否占槽                | MSVC 自己处理，且库那边同样处理 → 自动一致                                      |

残留风险只剩一条，且是**安全**的：用户 `Declare` 写错签名（如库是 `int f(int,short)`，用户写成 `ByVal x As Long, ByVal y As Long`）→ C3 算出 `_f@8`，库里是 `_f@6` → **未解析符号**。stdcall 把签名的字节数编进了名字，所以签名错 = 链接期报错，不会静默错参（首版 E3 的"失败模式安全"在 L0 下**免费继承**）。

⚠️ 例外只有一处：**CDecl 下无 N**（`_name`），签名写错就是静默的。这是 A/B 两路共有的真风险，与修饰名方案无关，写进 §六。

⚠️ 首版表按"VB6 类型"与按上表算出的 x86 结果**大体一致**（因为 `intptr_t` 在 x86 = 4，且 x86 栈参最小 4 字节槽）——这是**巧合成立**，不是同义。将来谁动了 `mapDeclareType` 的宽度（Fix 081e 那处加宽）就会静默错，所以口径必须写成"C3 生成的 C 原型经 MSVC 修饰"。

### L2 查归档符号表（**保留**，但定位改为"诊断 + 改名建议"）

首版说 L2 是"L1 猜得准 → L2 查得到"的递进优化。更正：L2 不是优化，它是 **L0/L1 算错时的唯一恢复路径**——库是 `_f@6` 而 C3 声明算出 `_f@8` 时，只有归一化匹配能告诉用户"库里其实有 `_f@6`"。两件事耦合，**不能按 §七 拆成 T03/T04 两批排期**。

解析 `.lib` 的 COFF member 符号表，对名字做归一化匹配（忽略前导 `_`、忽略 `@N` 后缀、大小写不敏感）：

- 唯一命中 → **不能静默替换**。因为要落到 C3 这边必须能写出这个名字，而 `_f@6` 含 `@`（见 E4 补充），落点只能是 `#pragma comment(linker,"/alternatename:...")` 或 asm 别名。实现方式与 E4 逃生舱**是同一件事，须一起定**。
- 多义 → **报错并列出候选**（比让用户去开 `dumpbin` 强一个数量级，是本特性最有价值的一条诊断）；
- 零命中 → 原样交链接器，保留原生错误。

实现选**自研只读解析器**（COFF 归档头 + member 符号表，约 200 行），不 shell 调 `dumpbin`：理由见三节末行——`rc.exe` 探测那 50 行已经证明每加一个外部工具都在放大 CI 与 MinGW 分支的麻烦。


### 5.1 L0 与 L2 的取舍（给拍板用）

既然 L2 能查到权威符号名，能否**直接跳过 L0/L1**？不能，但理由要说准：L2 查到 `_f@6` 之后，C3 仍要**让 MSVC 生成**这个符号引用；而写入 C 源码的唯一合法载体是 linker 指令/asm 别名。所以两条路是：

- **倾向 L0**：C3 声明宽度对 → MSVC 算对 → 零额外机制，L2 只用于"算错时告诉用户为什么"；
- **倾向 L2-优先**：完全不管宽度，一律查表取符号名 → 但每个静态 Declare 都要挂一条 linker 指令，且 `#pragma comment(linker,...)` 与 `/alternatename` 在本工程工具链（link.exe 14.29.30159）上的行为**须实测**。

我选 **L0 为主 + L2 为诊断**，因为它不引入未经实测的 linker 机制；L2-优先作为 T04 的备选实验。

## 五之二、系统依赖自动化：**我们没有 `Link` 子句**

tB 要用户写 `Link "stdlib", "kernel32"`，FB 要用户敲 `-l`——那都是把 C 世界的习惯原样搬进 VB6 的门面，也是"普通人哪有办法记得要链哪个系统库、要查半天"的根因。

**但先要划清问题域（首版混了）**：DLL 型 `Declare` 的依赖**早就自动化了**——`cgen_decl_api.cpp:98` 为每个 Declare 发 `#pragma comment(lib, "<lib>.lib")`，用户本来就是一个额外字都不用写。M1/M2/M3 真正要解决的是**另一件事**：静态 `.obj` **内部**引用的系统符号（如 `sqlite3.obj` 里的 `WSAStartup`），用户没写 `Declare`、因此没有 pragma、因此未解析。首版把这两件事混在一条线上讲，会导致 M1 实测设计出错（见下）。

四条，按**更正后的**优先级落地：

- **M1 先实测"什么都不写够不够"——但答案已知，且实验结论不能外推。**  
  首版推测 kernel32 能过是"CRT 的 `/DEFAULTLIB` 指令传递引入"。**推测错了**：`src/rtl/core/di/vb6_di_win32_stubs.c:48` 就写着 `#pragma comment(lib, "kernel32.lib")`。kernel32 不在 `msvc_driver.cpp:229,244,257` 命令行里却能用，是 **RTL 的 pragma 兜的**。  
  → 所以拿夹具工程实测**会"通过"**，但那证明的是"RTL 恰好带了这个 pragma"，**不能外推**成"用户可以不给"。M1 的验证法必须改成：**逐个把 RTL 的 23 个 pragma 去掉/屏蔽，看哪些真的必要**——这才是有效实验。成本仍然 2 分钟，但设计要换。
- **M2 全量塞候选 lib：**&#x590D;**活为主方案。** 首版以"会招来 `LNK4098` 默认库冲突"否掉 M2，**与项目现状矛盾**：
  - RTL 各 stub 已**无条件**带 23 个库（`grep -h 'pragma comment(lib' src/rtl/`）；
  - `msvc_driver.cpp` 每条链接命令行再常驻 7 个（`ole32 oleaut32 uuid advapi32 user32 shell32 gdi32`）；
  - `vb6_di_win32_stubs.c` 甚至无脑塞了明显用不到的 `comdlg32.lib`；
  - stub 注释自陈："*Adding one that is not needed is harmless: a static import lib is only pulled when a symbol from it is referenced.*"  
    也就是说**项目今天已经在跑"全量塞"，且 35+ 用例天天过、没有 `LNK4098` 成灾**。`LNK4098` 只在同一符号被多个库提供时出现，对系统 import lib 几乎不发生（msvcrt 系列除外）。  
    → M2' 形态：把 RTL 全集的 23 个库 + 命令行的 7 个并集作为**默认追加集**，一次到位。比 M3 更快（零额外链接）、更简单（零新机器件）。
- **M3 失败驱动反查 + 自动重链：降级为可选，不做主方案。** 原设计（先正常链一次 → 未解析则查索引补 lib → 重链一次 → 打印处方）技术上成立，但 M2' 覆盖了绝大多数场景，M3 只剩"用户引用的库不在默认集里"这一窄口（第三方 kernel、vulkan 等），而那类恰恰更适合 M4 显式给。**故：M2' 为主，M4 兜底，M3 暂缓**；若 M2' 实测出意外噪声再启用 M3。  
  若将来做 M3，两条更正必须带上：① **档 A 的"资产"不存在**——`vb6_di_lib` 标记由 `cgen_decl_api.cpp:149` 发到**生成的 .h**，消费方是 `gen_di_stubs.ps1:84` 与 `driver_link.cpp:175`，**需一次编译会话（`-SessionDir`）才拿得到，不在仓库里**；仓库里真实可用的是 `vb6_di_<Export>` 函数名 + 各 stub 的 `#pragma` 列表，且**族→库是一对多**（net 族 = `ws2_32`+`iphlpapi`+`comdlg32`），给不出唯一答案 → 档 A 只能产出**候选集**，而这正好又回到 M2' 的思路。② 档 B（扫 SDK `Lib` 建索引）才彻底，但优先级排在 M2' 之后。
- **M4 逃生舱放工程层，不进语言**：`ExtraLib=ws2_32.lib`（vbp）或 `--extra-lib`。理由是依赖属于链接配置、不属于函数签名；写进语句就会像 tB 那样每行 `Declare` 重复一遍。（**M4 的建议**：首版把它列为最后一条，既然 M3 降级，M4 应提升为"与 M2' 同批做"——有了 `ExtraLib`，M2' 的默认集可以保守一点。）

一句话口径（不变）：用户侧最终形态是 `Declare ... Lib "sqlite3.obj"`，**一个额外字都不用写**。

## 五之三、字符串编组归谁管（**首版完全没提，但正好命中它自己的例子**）

§二 举的例子是 `Declare ... Function sqlite3_open (...)`，而 `sqlite3_open` 的 C 原型是 `int sqlite3_open(const char *filename, sqlite3 **ppDb)` —— **`const char*`，ANSI**。所以"字符串参数怎么编组"是静态链接**第一个**会撞上的问题，不是边角。

现状（Fix 187）：`cgen_decl_api.cpp:58-62` 把**每一个** Declare 的 VB 函数名登记进 `knownDeclareAnsi_`，调用点据此（`cgen_expr_call_callee_params.inc:219-226` → `cgen_expr_call_arg_emit.inc:97-110`）对 `ByVal x As String` 生成：

```c
char* _ansi_0 = vb6_BSTR_ToANSI(s);   /* 调用后释放 */
```

三条必须明确的结论：

1. **调用点发的已经是 `char*`，不是 `BSTR`。** 但 `makeParamCType` 对 `As String` 给出的声明类型是 `BSTR`（`mapType`：`Vb6Type::String → "BSTR"`，`cgen_base_type.cpp:42`）。**声明与调用点本来就不一致**（动态路靠 MSVC 只报 `C4047` 警告而容忍）。静态路径新增 `extern` 声明时**必须与调用点口径对齐**——按 `BSTR` 发声明会把这个既有不一致固化进新路径。
2. **静态模式下要沿用 `knownDeclareAnsi_`，不要按库名/后缀猜 ANSI 还是 Unicode。** 保持 Fix 187 的"一律 ANSI"口径，一致性成本最低；`sqlite3_open` 这类 C 库恰好就是要 ANSI。若将来要支持 `sqlite3_open16` 那类宽字符入口，那是一个**独立特性**（需要 `WString` 或显式 `AliasW` 概念），别顺手塞进本特性。
3. **路线 B 下要特别小心**：桩的形参若仍是 `BSTR` 而调用点实参是 `char*`，桩内部再 cast 到真实原型时，是在"把 `char**` 当 `BSTR` 解读"的边缘上跳舞。T02 必须写一个**字符串参数的正例**（用夹具里的 `const char*` 函数），并检查生成码里 `vb6_BSTR_ToANSI` 的临时量与 `ansiTempsToFree_` 释放配对没有回归。

## 六、v1 硬边界

1. **后端 × 格式必须匹配**：MSVC 后端只吃 `.lib/.obj`，MinGW 只吃 `.a/.o`；不匹配由编译器**先诊断拒收**，别丢给 link.exe 吐一堆。
2. 只做 MSVC 后端的 `.lib`。MinGW `.a` 是另一套归档 + bfd 符号表格式，单独批次（S06）。
3. 静态库带资源成员（可撞宿主 `ResFile=`/RT_TYPLIB 同 ID，见 023 八-1）v1 **不检测、不保证**，只写进文档。
4. 与 RTL 无关：RTL 继续源码同批编译（`driver_link.cpp:137-138` 的 P11.3 回退结论），本特性不引任何"预编译 RTL"回潮。
5. **不做"把 C3 工程编成 `.lib` 分发出去"**——那是 023 已拒的二进制发布。
6. **~~不做 M2 的全量塞 lib~~；自动重链上限 1 次**。→ **更正**：M2 已复活为主方案（§五之二），本条作废。保留的约束是"任何自动补 lib 的动作**上限 1 次**"，防止成环或把命令行滚成雪球。
7. **（新增）`CDecl` 是唯一会静默错参的调用约定。** 全特性的"失败模式安全"（§五 L0）建立在 stdcall 把签名字节数编进名字这一点上；`CDecl` 无 N，用户签名写错就是**静默错参**。v1 的处理：文档显著标注 `CDecl` 需用户自担签名正确性，不做额外校验（要做校验需 L2 匹配 + 参数宽度反推，不在 v1）。
8. **（新增，理由已按实测重写）`vb6_VARIANT` 与 Win32 `VARIANT` 不是同一个类型：x86 下尺寸差 8 字节。**  
   实测（**真 MSVC 14.29.30133**，`vcvarsall x64`/`x86`，探针 `.temp/vsz_probe.bat` 且 `#include` 项目真实 `vb6rtl.h`）：
   |                  | tag          | 值槽偏移 | x86    | x64 |
   | ---------------- | ------------ | ---- | ------ | --- |
   | Win32 `VARIANT`  | 2B `VARTYPE` | 8    | **16** | 24  |
   | C3 `vb6_VARIANT` | 4B enum      | 8    | **24** | 24  |
   两者 **tag 与值槽偏移一致**（且 MSVC 实测确认 C3 的 `vb6_vartype` 取值**逐一等于**真实 `VARENUM`：I2=2/I4=3/R8=5/BSTR=8/BOOL=11/UI1=17/ARRAY=0x2000），所以：
   - **x64：尺寸与布局均兼容**（24=24，tag/值槽同位）→ 按指针或按值都可行；
   - **x86：尺寸差 8（24 vs 16）** → **按值传参压 24 字节而 callee 只消费 16 → 栈失衡，真 bug**；**按指针传参则安全**（callee 只读前 16 字节，tag 与值槽都在正确位置）。
   故 v1 的处理不是"布局不兼容一律拒收"，而是：**x86 下拒收 `ByVal <x> As Variant`；`ByRef` 与 x64 放行**。若嫌分支麻烦，可退化为"v1 一律拒收 + 诊断文本说明 x86 的尺寸差"，等有真实用例再按上述细分放宽。

需要一个自制的纯 C `.lib`。要点：

**`DeclareWide` 的实现要点**：整个 ANSI 编组机制**只由 `knownDeclareAnsi_` 这一个集合驱动**
（消费点两处：`cgen_expr_call_callee_params.inc` 的 `isDeclareAnsiCall` 判定、
`cgen_expr_call_arg_emit.inc` 的 `vb6_BSTR_ToANSI` 生成）。所以"禁用转换"的全部实现 =
**不登记**。实测对照：

| 输入 | 生成的调用点代码 |
|---|---|
| `Declare Function lstrlenA Lib "kernel32" (ByVal s As String) As Long` | `char* _ansi_0 = vb6_BSTR_ToANSI(s);` `n = lstrlenA(_ansi_0);` `vb6_FreeANSI(_ansi_0);` |
| `DeclareWide Function lstrlenW Lib "kernel32" (ByVal s As String) As Long` | `n = lstrlenW(s);` ← 直接传 BSTR, 零转换、零临时量 |

`parseDeclaration()` 的 kind 分派 **和** `isDeclarationStart()`（模块级闸门，
`parser_module.cpp:180` 据此决定要不要调 `parseDeclaration`）。

## 十二、实施记录：T02（2026-09-23）—— 静态 Declare **真的链上归档**

### 先纠正一句结论

T01/T01b 交付后曾误以为"静态库做完了"。**没有。** 计划书自己第 325 行就写着"静态 Declare

### x86 实测：L0「装饰名靠编译器算」成立，且失败模式**确为安全**

x86 是这条特性唯一真正吃紧的地方（x64 只有一种调用约定，`__cdecl`/`__stdcall` 同一套 ABI，
约定写错**不报错也不出错**；x86 才会把签名字节数编进名字）。夹具做了**两组隔离的库**
（只剩调用约定这一个变量）：

| x86 用例 | 归档里的符号 | VB6 声明 | 结果 |
|---|---|---|---|
| A | `_sl_add@8` / `_sl_fill@4` / `_sl_strlen@4`（`/Gz` = `__stdcall`） | **默认**（即 `__stdcall`） | ✅ 链接并运行 → `add=203` / `fill=4242` / `strlen=5`；产物 PE 头实测 `0x14c` = **i386** |

| C | 同 B（`__cdecl`） | 显式 `Declare ... CDecl` | ✅ 链接并运行 → `cdecl=708` |

A 证明了 **L0 的核心主张**：C3 一行尺寸表都没写，`_sl_add@8` 里的 `@8` 是 **MSVC 自己**按

"让编译器算"这条路在 x86 上真的走得通。C 给了库里用 `__cdecl` 时的正规出口。

B 一度被读成"`@N` 让签名不一致在链接期暴露 → 失败模式安全"。**这个读法在同日补做 T03 负控后

详见下一节。

**顺带两条要写进文档的方向（T03/T05）**：

1. **归档成员是 `.obj` 粒度的。** 本次夹具三个函数由同一次 `cl /c` 产出 → 落在**同一个成员**里，

   文档要讲清（推荐一功能一 `.obj` 或拆库）。

### T03 负控实测（同日补做）：`@N` 的安全边界比计划假设的窄得多

计划书 T03 的验收判据原文是：

> **故意把某个 `Declare` 的 `ByVal Long` 写成 `ByVal Integer`（或反之）→ 必须报未解析符号、
> 而非静默错参**（证明 stdcall 的失败模式安全确实成立）

照此实测，**这条判据本身就是它自己警告过的"自洽假绿"**。

| 用例 | C3 生成的声明（`--emit-c` 实见） | x86（`/Gz` = stdcall 库） | x64 |
|---|---|---|---|
| 正例 `(ByVal a As Long, ByVal b As Long)` | `extern intptr_t __stdcall sl_add(intptr_t a, intptr_t b);` | ✅ `add=203` | ✅ `add=203`（连跑 3 次稳定） |
| **负控 A：宽度错** `(ByVal a As Integer, ByVal b As Long)` | `extern intptr_t __stdcall sl_add(int16_t a, intptr_t b);` | ❌ **链接通过、零诊断、实得 203** —— `int16_t` 在 x86 栈上提升为 4 字节，`@N` 仍是 `@8`，与归档成员名相同 | ❌ **链接通过、算错值**：连跑 5 次得 `1874591947 / -364904245 / 270008523 / 1190658251 / -67370805` —— **每次都不一样** |
| **负控 B：元数错** `(ByVal a As Long)`（调用点同步改成 1 参） | `extern intptr_t __stdcall sl_add(intptr_t a);` | ✅ `LNK2019: 无法解析的外部符号 _sl_add@4`（`_vb6_Main` 中引用） | ❌ **也静默**：链接通过，运行得 `-321915124 / -1213203828 / 1039138060`（连跑 3 次各不相同） |

于是完整矩阵是这样（**这是本轮最重要的一张表**）：

| 错误形态 | x86（`--arch x86`） | x64（默认） |
|---|---|---|
| 参数**元数**不一致 | ✅ `LNK2019 _name@4`（**响**） | ❌ 静默 → 非确定垃圾值 |
| 参数**宽度**不一致（同槽位类） | ❌ 静默（**且可能恰好算对**） | ❌ 静默 → 非确定垃圾值 |
| **调用约定**不一致 | ✅ `LNK2019 _name@N`（**响**） | ➖ 无意义（同一套 ABI，本来就不会错） |

**一句话：x86 有两条护栏（元数、调用约定），x64 一条都没有。** 默认的 x64 构建里，
`Declare` 签名与库 C 原型不一致**不会产生任何编译期或链接期信号**。

三点结论（**修正 §五 L1 与 §九 SR1 的假设**）：

1. **`@N` 的保护只覆盖两件事**：①元数变化；②改变**栈槽字节数**的类型变化（x86 如 `Long`↔`Double`）。
   **同一槽位类内部的宽度差它看不见** —— x86 上 `Integer` 与 `Long` 提升后同为 4 字节槽，`@N` 相等，
   链接器眼中两个符号根本是同一个。故"宽度不一致 → 链接期暴露"**不成立**。
2. **x64 没有任何装饰名，因此这一层保护在 x64 上恒等于零 —— 连元数错都静默**（实测见上表）。
   且 x64 的失配形态**比"静默错参"更坏**：声明的 `int16_t` 只写 `cx`，而 callee 读整个 `ecx` → 高位是
   **调用点残留的垃圾**，实测**每次运行值都不同**。这是"不可复现、不可察觉、连断言都写不出来"的一档。
   （本条与 x86 上"恰好无害"形成对照：x86 那次能得 203 是**巧合**，不是保证。）
   由此，**默认的 x64 构建是本次静态库功能里最没有护栏的一块** —— 而它恰好是主路径。
3. **L2（T04）同样救不了宽度差**：符号名一致 → 无候选可报。COFF 对 **C** 归档不携带参数类型
   （类型安全链接是 C++ 修饰名才有的能力）。所以 **SR1 的唯一缓解手段是文档约束，不是工具诊断**。

**T03 判据据此改写**：

- ✅ **保留（已实测）**：元数不一致 → 必须 `LNK2019`。这是真正可用的安全网。
- ⚠️ **删除**：宽度不一致 → **不会有任何诊断**。x86 静默（且可能恰好算对，更具欺骗性）、
  x64 静默且非确定。改为落进用户文档：**要求库作者 `__stdcall`（x86）+ 逐参精确对齐**，
  并在 `C3_COMPILE_OPTIONS.md` 显著标注「x64 无护栏」。

> 值得一提：这条假绿恰好命中了 §七 自己立下的纪律 ——"负控必须能证明签名/宽度不一致会报错，
> **否则用例是自洽假绿**（同 022 的 ReDim 步长陷阱）"。纪律写对了，但 T03 写的**具体形态**不是那个
> 能报错的形态。教训：负控的**形态**必须实测筛过，光有"必须有负控"的原则不够。

### E4 落点实验 + 实施（2026-09-24；注意与批次表的 T04b=M1'/M2' 默认库集实验**不是**一回事）
