# ai/032 — VB.NET 风格的运算符扩展与四档无符号/窄整型

> 目的：把一批 **VB.NET 有、VB6 没有** 的写法和类型做进 C3，且**不破坏任何存量 VB6 语义**。
> 本文件记录口径与取舍，供后续维护/复核。行为本身由
> `.temp/tools/feat_probe.py`(语法 36 条) 与 `.temp/tools/feat_sem_check.py`(语义 48 条)
> 以及 `tests/run_tests.ps1` 全量门禁背书。

## 1. 新增的语法

| 类别 | 语法 | 落脚点 |
|---|---|---|
| 移位 | `a << n` / `a >> n` | 词法 `Shl/Shr` → `BinaryOp::Shl/Shr` → RTL `vb6_Shl/Shr/ShrU` |
| 复合赋值 | `+= -= *= /= \= ^= &= <<= >>= Mod=` | 词法 10 个独立 token → **解析期脱糖**成 `target = target op value` |
| 引用比较 | `a IsNot b` | 解析期脱糖成 `Not (a Is b)` |
| 三元 | `If(cond, a, b)` | 解析期产 `IndexOrCallExpr("If")` → 发**裸 C 三目**（真短路） |
| 类型 | `SByte` / `UInteger` / `ULong` / `ULongLong` | `Vb6Type::SByte/UInteger/ULong(既有)/ULongLong` |
| 转换函数 | `CSByte` / `CUInt` / `CULng` / `CULngLng` | `builtin_funcs.inc` 登记 + RTL `vb6_CSByte/CUInt/CULng/CULngLng` |

### 1.1 位宽口径：阶梯对齐 8/16/32/64

`U<x>` 恒等于「`<x>` 的无符号版」，与既有 `Vb6Type::ULong = 19 → uint32_t` 完全吻合：

| VB 类型 | C 类型 | 位宽 | 对照 |
|---|---|---|---|
| `SByte` | `int8_t` | 8 | — |
| `UInteger` | `uint16_t` | 16 | `Integer` = 16 位（C3 沿用 VB6 口径） |
| `ULong` | `uint32_t` | 32 | `Long` = 32 位 |
| `ULongLong` | `uint64_t` | 64 | `LongLong` = 64 位 |

`ULong` 枚举值**早已存在**（`mapType`→`uint32_t`、`typeSize`→4、typelib→`VT_UI4`），
但词法器没有 `ulong` 关键字、也不在 `isIntegral` 里 —— 属"半截活"，本次补齐。

### 1.2 绑定力（插入 `bpTable_` 的推导，不是拍脑袋）

VB6 既有优先级：`Or(2,3) < Xor(3,4) < And(4,5) < Eqv/Imp(6,7) < 比较(8,9) < &(10,11)
< 加减(12,13) < Mod(14,15) < \(16,17) < 乘除(18,19) < ^(21,20) < Like/Is(22,23)`

- `Shl/Shr = (9,10)` —— 夹在比较(8) 与 `&`(10) 之间。两侧夹逼：`1 << 2 + 3` 必须是 32
  （算术高于移位）而 `1 << 1 = 2` 为真（移位高于比较）。
- `IsNot = (22,23)` —— 与 `Is` 完全一致（它就是 `Is` 的否定形）。
- 10 个复合赋值 token **不登记任何绑定力** —— Pratt 中缀循环拿到 `{0,0}` 自然停住，
  再在语句层收编。

### 1.3 三处必须小心的既有冲突

1. **`&` 后缀 vs `&=`**：`lexer.cpp` 的 `scanIdentifierOrKeyword` 里，`&` 后跟非字母
   数字（含 `=`）就被并进标识符 —— 所以 `x& = 5` 的 `&` **到不了**运算符分支，而
   `x &= 5`（带空白）走 `scanOperator`。两者天然不冲突，已用对照用例 C7 钉住。
2. **`<<`/`>>` vs `<`/`<=`/`<>`**：`<` 分支先 `match('<')`（再判 `=`）出 `Shl/ShlEq`，
   之后才判 `<>`/`<=`/`<`；`>` 分支对称。对照用例 C5 钉住 `<` 家族。
3. **`Mod=` 不做空白容忍**：`x Mod= 2` 之间的 `Mod=` 必须紧贴。刻意不容忍
   `x Mod = 2`，因为与 `If x Mod 2 = 0` 形状太近，误吞的代价远大于省一次空格。

## 2. 五处"做法"上的取舍（都是刻意的）

### 2.1 复合赋值：解析期脱糖，而不是新增赋值节点

`parseLabelOrAssignmentOrCall` / `parseLetStmt` 在 `if (match(TokenKind::Equals))`
**之前**拦一道复合赋值，用 `ASTCloner` 深拷左值，产出
`AssignmentStmt(loc, target, BinaryExpr(op, clone(target), value))`。

- 收益：语义层/发码层**零改动**；`arr(i) += 7`、`udt.a += 41` 自动可走。
  已用探针 A9/A10 验证。
- 代价：左值被求值两次（VB.NET 里是"求值一次、写回一次"）。对 `arr(i) += 1` 这类
  常见形状（下标是无副作用表达式）无差异；对有副作用的左值（如 `f() += 1`）会差异。
  **记为本扩展的已知语义近似**。
- `&=` 映射到 `BinaryOp::Concat`，**不是** `Add` —— 字符串连接语义。
- **`Set` 不收复合赋值**（`parseSetStmt` 刻意不接）：Set 是对象引用赋值，
  VB.NET 里同样非法。

### 2.2 `IsNot`：解析期脱糖成 `Not (a Is b)`

理由：`exprYieldsVbBoolean` 认 `BinaryOp::Is` 为布尔，于是 `Not` 走**逻辑**取反，
拿到正确的布尔语义，下游（`CStr`/`And`/装箱）零改动。
不能用 `<>` 顶替 —— `Is` 是**引用**比较，`=`/`<>` 是**值**比较。

### 2.3 `If(c,t,f)`：发裸 C 三目，类型自算

- 短路是真的（C `?:`），探针 `if_short_circuit`（`If(d<>0, 100/d, 42)` 在 d=0 时得 42）
  就是对 IIf 急切求值的对照判据（IIf 那条报 ERROR11）。**副产品**：`If` 比 `IIf` 更安全。
- `addBuiltinFunc("If", Variant)` 只是让语义层知道"这个名字存在"，**真结果类型由
  `inferExprType` 自算**（同型取该型 / 都数值取 promote / 任一支 String 取 String /
  否则 Variant）。两处口径必须一致，所以 `isPolymorphicBuiltin` 的 denylist
  （`iif/choose/switch`）也必须加上 `"if"` —— 否则 `CStr(If(...))` 会走
  `vb6_CStr(vb6_VariantFromValue(<BSTR>))` → C2440。
- **已知不支持形状**：C 没有"序号化三目"，`If(True, f(), 0)` 可能同时调用 `f()`。
  VB6 常见用法（下标表达式、除法保护）不受影响，约定为病态形状不支持。

### 2.4 移位：不直接发 C 的 `<< >>`，改发 RTL inline

C 的移位在三处与 VB.NET 语义不同，其中两处是 **UB**：

1. **计数屏蔽**：VB.NET 把计数屏蔽到操作数位宽内；C 对"计数 ≥ 位宽"是 UB。
   `vb6_Shl/Shr/ShrU` 统一按 **63** 取模（取 63 而不是按左操作数位宽，见第 3 条）。
2. **有符号左移溢出**（`&H80000000 << 1`）在 C 里是 UB。按 `uint64_t` 位模式左移，
   位模式确定，再由 cgen 截断回目标类型 —— 结果与 VB.NET 的 wrap 一致。
3. **结果类型抬到至少 32 位**：VB.NET 的 `Integer` 是 32 位，C3 的 `Integer` 是 16 位。
   照搬会让 `1 << 20` 被截成 0。所以窄整型（SByte/Byte/UInteger/Integer/Boolean/Long）
   一律抬到 `int32_t`，`ULong→uint32_t`、`LongLong→int64_t`、`ULongLong→uint64_t`、
   `LongPtr→intptr_t`。这也是"计数按 63 取模"的原因。
4. **右移的有符号性**：VB.NET 对有符号整型是**算术**右移，对无符号整型
   （Byte/UInteger/ULong/ULongLong）是**逻辑**右移。C 对有符号数是实现定义，
   所以分成 `vb6_Shr` / `vb6_ShrU` 两支，由 cgen 按左操作数的有符号性选。

### 2.5 新类型：不新造 `VT_UI1/UI2/UI4`，Variant 装箱复用既有最小 VT

| 类型 | 装箱 | 理由 |
|---|---|---|
| `SByte` | `VT_I2`（int16_t 承载） | 能无损装下 |
| `UInteger` | `VT_I4`（int32_t 承载） | 能无损装下 |
| `ULong` | 既有路径（`VT_I4`…） | 枚举早已存在 |
| `ULongLong` | `VT_I8`（int64_t 承载） | 能无损装下（> 2^63 例外） |

代价：`VarType()` 对这些值答**有符号档**。收益：值不丢 + 全部走既有已测分支 +
RTL 装箱路径一行不改。

## 3. 一等类型化的关键：`knownNarrowIntVars_`

**根因**：`symTab_` 只有模块作用域，**局部变量/形参/返回槽在它里面不可达**。
这四档的 C 型（`int8_t/uint16_t/uint32_t/uint64_t`）又都不在既有的
`int32_t | int16_t | VBABOOL` 那一支里，于是 `inferExprType` 一律答 Variant。
后果（实测）：

- `CStr(u)`（u As ULong）→ `vb6_CStr(vb6_VariantFromValue(u))` →
  `_Generic` 的 `unsigned int: vb6_VariantLong` 把 `&HFFFFFFFF` 打成 **-1**；
- `Debug.Print u` → `vb6_DebugWriteLong((int32_t)(u))` → 同样 **-1**。

**做法**：新增一张 `name → Vb6Type` 的表 `knownNarrowIntVars_`（仿 `knownByteVars_` /
`knownBoolVars_` / `knownIntVars_` 的并存登记口径），在
局部 `Dim`/局部 `Const`/形参/返回槽 四处登记；消费点在 `inferExprType` /
`isDefinitelyVariantExpr` / CStr 分派 / Debug.Print 分派。
**类型映射只写一份**：`CCodeGen::isNarrowIntVbType` + `narrowIntTypeOfCType`
（`cgen_util_type.cpp`），登记点与消费点都调它 —— 免得"同一个决定抄两遍"
（本仓反复量到的那一族）。

模块级变量**不进**这张表：它们在 `symTab_` 里可达，且本表随过程入口 `clear()`。
CStr 分派另留一条 `inferExprType` 兜底，覆盖模块级/表达式两种落点。

### 3.1 无符号输出：`vb6_CStrULong` / `vb6_CStrULongLong`

不复用 `vb6_CStrLong/LongLong`：那两条是有符号口径（`%d`/`%lld`），2^31 以上打成负数。
与 Fix 084m 另开 `vb6_CStrLongLong` 同一处理由（`vb6_Format` 不认 VT_I8）。
`SByte`/`UInteger` 的值域 ⊆ `int32_t`，有符号与无符号十进制**同字面**（`-128`/`65535`），
故仍复用 `vb6_CStrLong`。

### 3.2 无符号 `\` 与 `Mod`：另开四条 helper

`vb6_IntDiv` / `vb6_Num_Mod` 的形参都是 `int32_t`，无符号操作数会先被按有符号解释 ——
实测 `&H80000000 As ULong \ 2` 得 **3221225472**（应为 1073741824），
因为 `(int32_t)&H80000000 = -2147483648`。故新增
`vb6_IntDivULong` / `vb6_Num_ModULong` / `vb6_IntDivULongLong` / `vb6_Num_ModULongLong`
（除零同为错误 11）。cgen 侧判据：**任一侧**是无符号档就取更宽的那一档；结果类型由
`inferExprType` 用**同一份判据**答出（否则 `2 \ u` 会被 promote 判成 Long）。

### 3.3 位运算 `& | ^ Eqv Imp`：按档收口，不再一律 `(int32_t)`

原路径把两侧硬转 `(int32_t)`。实测 `u3 = (1 << 40) Or 255` 得 **255** ——
`(int32_t)(2^40) = 0`，高 32 位整段丢掉。改为：任一侧 `ULongLong` → `uint64_t`；
否则任一侧 `ULong` → `uint32_t`；否则保持既有的 LongPtr 字面量→`intptr_t`、
其余→`int32_t`（Fix 082 口径不动）。

### 3.4 `promote` 的 rank 表：一处既有缺陷 + 一个**踩过的坑**

`LongLong` 以前**不在** `promote` 的 rank 表里，落 `default: 0` 档 —— 于是
`LongLong + Long` 被判成 32 位 Long，**高位静默丢失**。本次一并补到 6 档
（与 Currency 同档）。这是本次唯一的**既有行为改动**，由全量门禁背书。

但"按位宽补档"这个做法本身有坑，第一次就踩了，记录下来：

**坑：`promote` 是"取 rank 大者"，而 rank 是按位宽的 —— 于是 64 位整型排到了
`Single(4)/Double(5)/Currency(6)` 之上。** 后果不是算术算错（`+` 直接发裸 C
`(a + b)`，C 自己会把 `int64 + double` 提成 double），而是**结果类型被问错**：
上层 `CStr` 按 `inferExprType` 选入口，一旦答整型就发 `vb6_CStrLongLong/…`，
把 `5.5` 打成 `5`。

修法是两处，缺一不可：

1. **`promote` 里加"浮点/货币/Decimal 侧必胜，与位宽无关"**，在 `rank` 比较之前
   返回。对改动前的类型表这是**恒等变换**（浮点/货币档 4~7 本来就高于所有整型档
   1~3，走原来的比较也是它们胜），所以既有行为零变化。
2. **`LongPtr` 刻意不进这张表**（继续落 `default: 0`）。它的宽度是**目标相关**的
   （x86 4 字节 / x64 8 字节），而 `TypeSystem` 这一层**拿不到目标架构** ——
   只有后端的 `targetArch_`，且 `typeSize(LongPtr)` 本身也还在用宿主
   `sizeof(void*)`（既有隐患 Fix 081e）。给它写死任何一档都会错：写 6 之后
   `LongPtr + Double` 被判成 LongPtr，`CStr(p + 1.5)` 出 4（x86 与 x64 两个目标
   **都是** 4，因为档位是宿主侧算的，与目标无关）；写 3 又会在 x64 上低估。
   正确的修法要先把架构信息贯通到语义层，不在本次范围。
   （顺带说明：C3.exe 自身是 **x64 宿主**，所以 `sizeof(void*)` 在编译器里恒为 8，
   想用宿主宽度推目标宽度是行不通的 —— 这正是最初写错的原因。）

**负控实测**（把 LongLong/ULongLong/LongPtr 一律登记 6 档、并去掉上面第 1 条，
编 `tests/test_vbnet_ext.bas`）：

| 表达式 | 坏版 | 修后 | 说明 |
|---|---|---|---|
| `CStr(u3 + 1.5)`（ULongLong） | `5` | `5.5` | `vb6_CStrULongLong` 截断 |
| `CStr(u3 + CCur(1.5))` | `5` | `5.5` | Currency 侧同样被吞 |
| `CStr(p + 1.5)`（LongPtr） | `4` | `4.5` | 登记 6 档所致 |
| `CStr(p * 2.5)` | `7` | `7.5` | 同上 |
| `CStr(ll + 1.5)`（LongLong） | `5.5` | `5.5` | **没**截断：LongLong 在 CStr 那侧没有整型分支，走 Variant 路 |

最后一行正是"为什么判据必须落在真算出来的值上"：同一个 rank 错误，会不会真丢值
取决于下游发码有没有对应分支。**"语法通过 ≠ 取值正确"，也不能靠读代码判断有没有丢值。**

## 4. 转换函数 `CSByte / CUInt / CULng / CULngLng`

- 口径与 `CInt/CLng/CByte` 一致：收 `double`，由调用点的 `_Generic`/`NumVal`
  分诊 `BSTR`/`Variant`；沿用 `vb6_OvfChk` 的 **VB6 语义：越界是 Error 6，不是静默截断**
  （`CByte(300)` 那条先例）。`CULngLng` 的上界（2^64-1）装得下 double 的整数域，
  故只挡负数。
- **大小写不敏感**：表键用小写 `csbyte/cuint/culng/culnglng`，与 `cint/clng` 同路，
  所以 `culng(7)` 也能用（探针 `conv_case`）。
- 登记**不加 `calleeParams`** —— 同 `CStr/CInt/CLng/CByte`，让 cgen 的 callee-rewrite
  独立工作（加了会被 Fix 024/029 的实参包装抢先，C2440）。
- 宽度不同的两个邻档一并考虑过：`CShort`（= CInt）、`CUShort`（= CUInt 的 16 位无符号）
  本次未加 —— 用户点名的是那四个。`CUShort` 若要补，照 `CUInt` 抄一遍即可。

## 6. 已知边界（明确记为"不支持/近似"）

1. `f() += 1` 这类**左值有副作用**的复合赋值会求值两次（见 2.1）。
2. `If(True, f(), 0)` 可能同时调用 `f()`（C 无序号化三目，见 2.3）。
3. `VarType()` 对 SByte/UInteger/ULongLong 答**有符号**档（见 2.5）。
4. 有符号与无符号混算时取"任一侧无符号即按无符号"（VB6 无无符号类型，
   没有先例可循；`promote` 里明确记为"等宽即最高位宽胜出"的最简口径）。
5. `Eqv`/`Imp` 在无符号档已按位宽收口，但这两个运算符本身极罕见，
   探针未覆盖其 64 位路径。
6. 类模块**字段**（非局部）为这四档时未进 `knownNarrowIntVars_`（该表随过程入口
   clear，字段应走 symTab）；如遇实际用例再补 `classNarrowIntMembers_`。
7. `LongPtr` **不在 `promote` 的 rank 表里**（见 3.4）：所以 `LongPtr + Long` 的
   结果类型仍是 `Long`。x86 上两者同宽、取值不受影响；x64 上这个组合会窄化 ——
   属**既有**问题（本次之前就是 0 档），要修得先把目标架构贯通到 `TypeSystem`。
