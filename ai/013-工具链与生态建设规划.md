# 013 - 工具链与生态建设规划

> 日期: 2026-06-26
> 状态: 规划中
> 前置: VB6编译器核心（P0-P6）完成，P7窗体控件可选

---

## 一、愿景

c3 不只是一个命令行编译器，而是一套完整的 VB6 开发工具链。从写代码、查错误、补全、调试到编译运行，全流程覆盖。最终形态：

```
c3 编译器 + LSP + DAP + Formatter + Linter + 反编译器 + 包管理器 + VS Code 插件 + 窗体设计器
= VB6 的现代化开发环境
```

对标成熟生态：Rust 有 rustc + rust-analyzer + cargo + rustfmt + clippy，Go 有 go + gopls + gofmt + go vet，c3 也需要同等完整度。

## 三、P0: LSP 语言服务器

### 3.1 LSP 协议映射

c3 编译器已有基础设施，LSP 本质是对现有能力的封装暴露：

| c3 已有能力 | LSP 映射 | 协议方法 |
|-------------|---------|---------|
| 词法分析 (Lexer) | 语义 token 高亮 | textDocument/semanticTokens/full |
| 语法分析 (Parser) | 文档大纲、代码折叠 | textDocument/documentSymbol |
| 语义分析 (Semantics) | 错误诊断 | textDocument/publishDiagnostics |
| 符号表 | 补全、悬停、跳转定义 | textDocument/completion, textDocument/hover, textDocument/definition |
| 符号引用 | 查找所有引用 | textDocument/references |
| 重命名支持 | 符号重命名 | textDocument/rename |

### 3.2 架构方案

```
VS Code 扩展  ←──stdin/stdout──→  c3-lsp.exe  ←──调用──→  c3.exe（增量分析）
```

- c3-lsp 独立进程，通过 stdin/stdout 与 VS Code 通信（LSP 标准传输）
- 增量分析：文件变更时仅重新分析受影响模块，复用 c3 的词法/语法/语义管线
- c3 本身不改动架构，c3-lsp 作为薄封装层

### 3.3 预计工期

| 阶段 | 内容 | 工期 |
|------|------|------|
| LSP-S1 | LSP 通信框架（JSON-RPC + 生命周期） | 1 周 |
| LSP-S2 | 诊断暴露（语义分析 → publishDiagnostics） | 1 周 |
| LSP-S3 | 补全 + 悬停（符号表 → completion/hover） | 2 周 |
| LSP-S4 | 跳转定义 + 引用查找 | 1 周 |
| LSP-S5 | 语义 token + 文档大纲 | 1 周 |

### 3.4 关键决策

1. **语言**：用 C++ 实现（复用 c3-core 静态库），不引入 Go/Node 依赖
2. **增量策略**：文件级增量（修改文件重新分析），不做更细粒度
3. **多文件支持**：VBP 工程级感知，跨模块符号解析

## 四、P1: DAP 调试适配器

### 4.1 调试信息生成

c3 生成 C 代码后由 MSVC 编译，核心问题是 **VB6 源码行号 ↔ 运行时地址** 的映射：

```
VB6 源码 hello.bas:15  →  生成 hello.c:42  →  MSVC PDB → 地址 0x00401030
```

方案：在代码生成阶段输出 **行号映射文件** `xxx.debug.map`：

```json
{
  "source": "hello.bas",
  "mappings": [
    { "vb6_line": 15, "c_line": 42, "c_file": "hello.c" },
    { "vb6_line": 16, "c_line": 45, "c_file": "hello.c" }
  ]
}
```

### 4.2 调试器架构

```
VS Code  ←──DAP──→  c3-dap.exe  ←──读取──→  .debug.map + PDB
                                  ←──控制──→  被调试进程（via Windows Debug API）
```

### 4.3 功能范围

| 功能 | 阶段 | 说明 |
|------|------|------|
| 断点设置 | DAP-S1 | VB6 行号 → C 行号 → 地址断点 |
| 启动/继续/停止 | DAP-S1 | 进程生命周期控制 |
| 单步执行 | DAP-S2 | step over / step into / step out |
| 变量查看 | DAP-S3 | 读取局部变量、全局变量、Watch 表达式 |
| 调用栈 | DAP-S3 | VB6 函数名映射（去 C 生成前缀） |

### 4.4 预计工期

| 阶段 | 内容 | 工期 |
|------|------|------|
| DAP-S1 | DAP 通信框架 + 断点 + 进程控制 | 2 周 |
| DAP-S2 | 单步执行 + 行号映射 | 2 周 |
| DAP-S3 | 变量查看 + 调用栈 | 2 周 |

## 六、P1: 代码格式化器 (c3-fmt)

### 6.1 定位

现代开发体验的标配。没有格式化器，团队协作时风格不统一，代码审查被格式争论淹没。Rust 有 rustfmt，Go 有 gofmt——c3 也要有 c3-fmt。

### 6.2 功能范围

| 功能 | 说明 |
|------|------|
| 缩进统一 | Tab 或空格（默认4空格），可配置 |
| 关键字大小写 | VB6 不区分大小写，但统一风格有助阅读（默认首字母大写） |
| 空行规则 | Sub/Function 间空行、逻辑段间空行 |
| 对齐 | Dim 声明对齐、参数对齐（可选） |
| 行宽控制 | 超长行自动断行（VB6 有行续行符 _） |
| End If 合并 | 单行 If 可选合并为 If...Then...End If 单行形式 |

### 6.3 调用方式

```
c3 fmt                  格式化当前目录所有 .bas/.cls/.frm
c3 fmt hello.bas        格式化指定文件
c3 fmt --check          检查是否有格式问题（CI 用）
c3 fmt --diff           显示格式差异而不修改
```

### 6.4 预计工期：2 周

## 七、P1: 静态分析 / Linter (c3-lint)

### 7.1 定位

VB6 陷阱极多（见 009 文档第五章），自动检出价值巨大。clippy 对 Rust、eslint 对 JS 的生态贡献不可估量——c3-lint 对 c3 同理。

### 7.2 规则分类

| 类别 | 示例规则 | 严重级别 |
|------|---------|---------|
| **正确性** | Variant 未初始化就使用、On Error 后未检查 Err、Integer 溢出风险 | Error |
| **安全性** | Shell 执行未转义参数、文件路径拼接未校验 | Error |
| **性能** | 循环内字符串拼接（应用 StringBuilder 思路）、Variant 能改强类型 | Warning |
| **风格** | 未使用的变量/参数、过长过程（>200行）、深层嵌套（>4层） | Info |
| **VB6 陷阱** | 默认属性隐式调用、And/Or 位/逻辑歧义、IIf 双求值 | Warning |
| **迁移建议** | 不兼容 x64 的 API 调用、依赖 32 位指针假设 | Warning |

### 7.3 调用方式

```
c3 lint                  检查当前目录所有文件
c3 lint hello.bas        检查指定文件
c3 lint --fix            自动修复可修复的问题
c3 lint --config .c3lintrc   使用配置文件（启用/禁用规则）
```

### 7.4 与 LSP 的关系

c3-lint 的诊断结果通过 LSP 暴露到编辑器，VS Code 中直接看到黄色波浪线和快速修复建议。**c3-lint 是 c3-lsp 诊断功能的扩展，不是独立平行系统。**

### 7.5 预计工期

| 阶段 | 内容 | 工期 |
|------|------|------|
| LINT-S1 | 框架 + 规则注册 + 报告输出 | 1 周 |
| LINT-S2 | 正确性 + 安全性规则（20+） | 2 周 |
| LINT-S3 | VB6 陷阱规则（10+） | 1 周 |
| LINT-S4 | 性能 + 风格规则（15+） | 1 周 |
| LINT-S5 | --fix 自动修复 + LSP 集成 | 1 周 |

## 八、P1: 项目脚手架 (c3-init) + AST 浏览器 (c3-ast-dump)

### 8.1 c3-init: 项目脚手架

降低入门门槛，新用户一行命令创建可编译的项目：

```
c3 init myapp                创建标准 EXE 项目
c3 init mylib --type=dll     创建 ActiveX DLL 项目
c3 init myscript --type=vbs  创建 VBS 脚本项目
```

生成的项目结构：

```
myapp/
├── myapp.vbp          工程文件
├── Module1.bas        主模块（含 Sub Main）
└── README.md          项目说明
```

工期：1 周

### 8.2 c3-ast-dump: AST/IR 可视化

开发和调试 c3 本身的工具，也面向高级用户理解编译器行为：

```
c3 ast-dump hello.bas         输出 AST 树（文本格式）
c3 ast-dump hello.bas --json  输出 JSON（供可视化工具消费）
c3 ast-dump hello.bas --ir    输出语义 IR
c3 ast-dump hello.bas --web   启动本地 Web 服务，浏览器中交互查看
```

工期：1 周

## 十、P2: 反编译器 (c3-decompile)

### 10.1 定位

**迁移场景的杀手级功能。** 大量旧 VB6 项目丢失源码，只剩 EXE/DLL。反编译器让这些项目起死回生——这比任何其他工具更能吸引用户。

### 10.2 技术方案

```
VB6 EXE/DLL (PE + MSVBVM60 依赖)
    ↓ PE 解析
    ↓ 识别 VB6 特有结构（PROJECTINFO, EVENTTABLE, OBJECTINFO）
    ↓ 反汇编（x86/x64 → 中间表示）
    ↓ 模式匹配（识别 VB6 编译器生成的代码模式）
    ↓ 还原 VB6 源码
.bas / .cls / .frm 文件
```

### 10.3 难度分级

| 目标 | 可行性 | 说明 |
|------|--------|------|
| P-Code 反编译 | 高 | VB6 默认编译为 P-Code（字节码），有成熟研究 |
| 原生代码反编译 | 中 | native compile 需要逆向 x86，但 VB6 编译器模式固定 |
| .frx 资源还原 | 高 | 二进制结构简单，图片/图标可提取 |
| 变量名还原 | 低 | 符号信息在 Release 中通常被剥离 |

### 10.4 调用方式

```
c3 decompile app.exe                 反编译为 VB6 源码
c3 decompile app.exe --output=src/   指定输出目录
c3 decompile app.exe --pcode-only    仅反编译 P-Code 部分
c3 decompile app.exe --resources     仅提取 .frx 资源
```

### 10.5 预计工期：6-8 周

### 10.6 商业价值

反编译器可以作为**专业版付费功能**——"丢失源码的旧项目还原"是企业最愿意掏钱的需求之一。也可以作为社区版功能（引流），专业版增加更高质量的原生代码反编译。

## 十一、P2: 迁移助手 (c3-migrate)

### 11.1 定位

与反编译器配合，形成完整的迁移工作流：旧 EXE → 反编译 → 识别问题 → 自动修复 → c3 编译 → 现代化项目。

### 11.2 功能范围

| 功能 | 说明 |
|------|------|
| 兼容性检查 | 扫描代码中 c3 不支持的语法/控件/API，生成报告 |
| API 映射 | 32位 → 64位 API 自动替换（Long → LongPtr, VarPtr → VarPtr_Auto） |
| 字符串现代化 | VB6 ANSI 字符串 → c3 Unicode 字符串建议 |
| OCX 替代建议 | 识别旧 OCX，建议开源/现代替代品 |
| 自动转换 | 对确定安全的转换自动执行（--fix） |

### 11.3 调用方式

```
c3 migrate check .            检查当前项目兼容性
c3 migrate fix .              自动修复可修复的问题
c3 migrate report . --html    生成 HTML 迁移报告
```

### 11.4 预计工期：3-4 周

## 十二、P2: 包管理器 (c3-pm)

### 12.1 定位

VB6 生态最大的问题之一是**没有包管理**。代码复用靠复制粘贴或手工引用 OCX/DLL。c3-pm 解决这个问题，让 VB6 代码可以像 npm/cargo 一样共享和复用。

### 12.2 设计

**清单文件** `c3.pkg`（每个 VBP 工程根目录）：

```toml
[package]
name = "my-app"
version = "1.0.0"

[dependencies]
vb6-json = "2.3"         # 从 c3 注册中心拉取
vb6-utils = { path = "../utils" }  # 本地路径
win-http = { git = "https://github.com/xxx/win-http" }  # Git 仓库
```

**命令**：

```
c3 pkg install            安装所有依赖
c3 pkg add vb6-json       添加依赖
c3 pkg update             更新依赖
c3 pkg publish            发布到注册中心
c3 pkg search json        搜索包
```

### 12.3 技术要点

- 依赖内容：.bas 源码模块、.cls 类模块、类型库（.tlb）、COM 引用
- 安装位置：工程内 `vendor/` 目录（Go 风格，不搞全局缓存）
- 注册中心：最小 MVP 用 GitHub 仓库 + JSON 索引，后期可独立服务
- 版本解析：语义版本（SemVer），不搞复杂解析

### 12.4 预计工期：4-5 周

### 12.5 生态意义

## 十三、P2: 代码保护 / 混淆器 (c3-protect)

### 13.1 定位

VBA 代码保护的专业版付费核心功能。VBA 宏源码默认可被任何人查看和修改，这是企业核心算法暴露的风险。c3-protect 将 VBA/VB6 源码编译为不可逆的二进制，同时可选混淆增加逆向难度。

### 13.2 保护层次

| 层次 | 技术 | 逆向难度 | 性能影响 |
|------|------|---------|---------|
| L1 编译保护 | 源码 → 原生机器码，剥离所有符号 | 中 | 无 |
| L2 符号混淆 | 函数名/变量名 → 无意义字符串 | 中高 | 无 |
| L3 控制流扁平 | 将顺序逻辑打散为 switch-case 状态机 | 高 | 5-15% |
| L4 字符串加密 | 字符串常量运行时解密 | 高 | 微 |
| L5 反调试 | 检测调试器附加，自我保护 | 中 | 微 |

### 13.3 调用方式

```
c3 protect macro.bas --level=1           编译保护（默认）
c3 protect macro.bas --level=3           符号混淆 + 控制流扁平
c3 protect macro.bas --level=5           全部保护
c3 protect macro.bas --output=protected.dll  输出 DLL
```

### 13.4 预计工期：4-6 周

### 13.5 商业定位

**专业版核心付费功能**。VBA 保护是企业最明确的付费痛点——Excel 宏里嵌了核心算法，竞争对手打开 .xlsm 就能看到源码。c3-protect 把这个恐惧变成收入。

## 十四、P2: REPL 交互式控制台 (c3-repl)

### 14.1 定位

快速实验和即时求值。写 VB6 代码最痛苦的是改一行就要编译运行整个项目，REPL 让你即时看到结果。

### 14.2 设计

```
c3 repl
> Print 2 ^ 10

> :quit
```

### 14.3 技术方案

- 复用 c3 RTL 做求值（JIT 编译单表达式 → 执行 → 返回结果）
- 或者更简单：表达式 → C 代码 → 编译 → 执行 → 捕获输出

## 十五、P2: WebUI 窗体设计器

### 15.1 定位

VB6 的核心体验是拖控件画界面。没有窗体设计器，c3 只能服务纯逻辑/类库场景。WebUI 窗体设计器是 **真正的差异化功能**——市场上没有好的 VB6 窗体在线设计器。

### 15.2 技术方案

```
Monaco Editor (代码编辑)
    +
可视化画布 (拖拽布局)
    ↕  双向同步
.frm 文件 (VB6 窗体定义)
```

- 前端：React/Vue3 + 可视化拖拽框架（react-dnd / vue-draggable）

### 15.3 与 c3 的协作

- c3 已有 .frm 文本格式解析能力（VBP 解析器可扩展）
- WebUI 设计器输出 .frm，c3 编译 .frm 中的代码

## 十六、P3: 原生窗体设计器 + 性能分析器

### 16.1 原生窗体设计器

WebUI 验证可行且用户量足够后，开发原生 Win32 窗体设计器。

技术候选：

| 方案 | 优势 | 劣势 |
|------|------|------|
| twinBASIC | 开发体验好、64位原生 | 闭源、依赖twinBASIC运行时 |
| C++ + Win32 | 性能最优 | 开发周期长 |
| Go + Walk | 开发较快 | 非原生控件 |
| Electron + 原生模块 | 复用WebUI代码 | 体积大 |

倾向 **twinBASIC** 或 **C++ + Win32**，取决于 WebUI 阶段的市场反馈。

触发条件：
- WebUI 窗体设计器日活 > 100
- 用户反馈性能不足或体验不够原生
- 企业客户有明确需求

### 16.2 性能分析器 (c3-profile)

运行时性能瓶颈定位，专业版付费功能。

功能：

| 功能 | 说明 |
|------|------|
| 函数耗时 | 每个函数的执行时间和占比 |
| 调用频次 | 函数被调用次数 |
| 热点路径 | 最耗时的调用链 |
| 内存分配 | BSTR/SAFEARRAY 分配统计 |

技术方案：在代码生成阶段插入计时插桩（--profile），运行后输出报告。

预计工期：3 周

## 十七、P2: 构建系统集成 (c3-build)

### 17.1 定位

CI/CD 和团队协作的刚需。Makefile 对 VB6 项目不友好，c3-build 提供声明式构建定义。

### 17.2 设计

**构建文件** `c3build.toml`：

```toml
[project]
name = "my-app"
type = "exe"          # exe / dll / vbs

[build]
optimize = true
debug = false
define = ["NDEBUG"]

[tasks.build]
command = "c3 build ."
output = "bin/my-app.exe"

[tasks.test]
command = "c3 test ."

[tasks.clean]
command = "del /s bin\\*.exe bin\\*.obj"
```

### 17.3 调用方式

```
c3 build                执行默认构建
c3 build --release      Release 模式
c3 build --watch        增量构建 + 文件监听
c3 run task test        执行命名任务
```

## 二十一、商业价值

### 21.1 分层定价模型

| 层级 | 内容 | 定价 | 目的 |
|------|------|------|------|
| 社区版 | c3 + LSP + DAP + Formatter + Linter + VS Code 基础插件 + REPL | 免费 | 用户量、口碑、生态 |
| 专业版 | + c3-protect + c3-decompile + WebUI 窗体设计器 + c3-profile | 699-999 元/年 或 1999 买断 | 个人开发者收入 |
| 企业版 | + 原生窗体设计器 + c3-migrate 高级功能 + 批量授权 + 技术支持 + 定制 | 4999+ 元 | B 端收入 |

### 21.2 核心判断

1. **社区版必须完整可用**——编译、补全、调试、格式化、Lint 都能跑，不是残废版，否则没人用
2. **付费切入点选 VBA 保护 + 反编译器 + 窗体设计器**——"怕"（代码被看/源码丢失）和"想"（画界面）是最强的付费驱动力
3. **公测期完全免费**——积累用户和口碑，正式版再引入分层
4. **LSP/VS Code 插件/Formatter/Linter 永远免费**——这是用户量入口，收费等于自断流量

### 21.3 收入预期

- 乐观：5000 用户 × 5% 付费转化 × 800 元/年 = 20 万/年
- 中性：3000 用户 × 3% 付费转化 × 800 元/年 = 7.2 万/年
- 保守：1000 用户 × 2% 付费转化 × 800 元/年 = 1.6 万/年

主要收入来自 VBA 保护功能（企业痛点）、反编译器（源码复原刚需）和窗体设计器（可见价值），编译器本体免费。
