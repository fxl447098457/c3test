# 010-VBA代码编译支持方案

> 日期：2026-06-24
> 状态：构思阶段
> 结论：VBA 代码 → 提取 → 转换/适配 → VB6 编译 → exe/dll

---

## 一、目标

让 c3 能够编译 VBA 代码，最终产出独立的 exe 或 dll，不再依赖 Office 宿主运行。

这意味着：

- Excel 宏、Access 模块、Word VBA 等，可以编译为独立可执行文件
- 用户不再需要安装 Office 就能运行这些逻辑
- VBA 代码获得 x64 / Unicode / 多线程能力

---

## 二、VBA 与 VB6 的关系

VBA 和 VB6 共享约 95% 的语言内核：

| 维度 | VB6 | VBA | 差异程度 |
|------|-----|-----|---------|
| 词法/语法 | 相同 | 相同 | 极低 |
| 基本类型 | 相同 | 相同 | 无 |
| 控制流 | 相同 | 相同 | 无 |
| 错误处理 | 相同 | 相同 | 无 |
| 类模块 | 相同 | 相同 | 无 |
| 模块级关键字 | 部分不同 | 部分不同 | 低（如 VBA 有 `WithEvents` 在类中用法不同） |
| 宿主对象模型 | 无（自有 RTL） | Excel/Word/Access 对象 | 高 |
| 窗体 | .frm 窗体 | UserForm | 中 |
| 声明方式 | 相同 | 相同 | 无 |
| API 调用 | Declare | Declare | 无 |

**核心结论**：VBA 的语法层和 VB6 几乎完全一致，差异集中在**宿主对象模型**（Application、Workbooks、Range 等）。

## 三、总体架构

```
Office 文件 (.xlsm / .docm / .accdb / ...)
        │
        ▼
  ┌─────────────┐
  │ VBA 提取器   │  从 OLE 结构中提取 VBA 源码
  └──────┬──────┘
         │  VBA 源码（内存/磁盘）
         ▼
  ┌─────────────┐
  │ VBA→VB6 适配 │  语法微调 + 对象模型转换
  └──────┬──────┘
         │  等效 VB6 源码
         ▼
  ┌─────────────┐
  │  c3 编译器   │  正常编译流程
  └──────┬──────┘
         │
         ▼
    exe / dll
```

## 四、VBA 提取

### 4.1 Office 文件结构

Office 文件（.xlsm/.docm 等）本质是 OLE Compound Document（ZIP 包在 2007+ 格式中），VBA 代码存储在 `vbaProject.bin` 中。

```
.xlsm (ZIP)
└── xl/
    └── vbaProject.bin     ← OLE Compound Document
        ├── VBA/
        │   ├── Module1     ← VBA 源码（压缩存储）
        │   ├── Sheet1      ← 文档级代码
        │   ├── ThisWorkbook
        │   └── UserForm1
        ├── PROJECT         ← 项目元信息
        └── PROJECTwm       ← 项目元信息备份
```

### 4.2 提取策略

| 策略 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 磁盘文件系统 | 提取到临时目录，按 .vbp 组织 | 文件可检视调试 | 需要清理临时文件 |
| 内存虚拟文件系统 | 提取到内存中的 VFS | 无磁盘 IO，干净 | 调试不便 |

两种都支持，c3 已有的 `SourceManager` 可以适配虚拟文件系统接口。

### 4.3 提取器的归属

VBA 提取器可以作为一个独立工具 `c3-vba-extract`，也可以作为 c3 的子命令 `c3 --extract-vba`。建议后者，用户体验更简单。

## 五、VBA 对象模型处理（最核心的问题）

VBA 代码中大量使用宿主特有的对象，如：

```vba
' Excel VBA 典型代码
Sub ProcessData()
    Dim ws As Worksheet
    Set ws = ThisWorkbook.Worksheets(1)
    
    Dim lastRow As Long
    lastRow = ws.Cells(ws.Rows.Count, 1).End(xlUp).Row
    
    Dim rng As Range
    Set rng = ws.Range("A1:A" & lastRow)
    
    rng.Value = Application.Transpose(ProcessArray(rng.Value))
    
    ThisWorkbook.Save
    Application.Quit
End Sub
```

`Worksheet`、`Range`、`ThisWorkbook`、`Application` — 这些都不是 VB6 的东西，它们是 Excel 暴露的 COM 对象。

### 5.1 方案A：自建 VBA RTL（硬路）

构建一套纯 C++ 实现的对象模型，模拟 Excel/Word/Access 的行为：

```
VBA RTL
├── Excel RTL
│   ├── Application    → 自建实现
│   ├── Workbook       → 自建实现
│   ├── Worksheet      → 自建实现
│   ├── Range          → 自建实现
│   └── ...
├── Word RTL
│   ├── Document       → 自建实现
│   └── ...
└── Access RTL
    ├── CurrentDb      → 自建实现
    └── ...
```

**优点**：不依赖 Office 安装，产物可独立运行
**缺点**：工作量极大（单 Excel 对象模型就有数百个接口），且行为兼容性难以保证

### 5.2 方案B：转为 COM 对象调用（推荐，肯定行）

将 VBA 宿主对象全部转为 Office COM 对象的调用，运行时需要 Office 安装：

```vb
' VBA 原始代码
Dim ws As Worksheet
Set ws = ThisWorkbook.Worksheets(1)

' 转换后等效代码
Dim ws As Object    ' → COM IDispatch
Set ws = g_ExcelApp.Workbooks(1).Worksheets(1)
' g_ExcelApp 是 c3 运行时通过 COM 启动的 Excel 实例
```

**转换映射关系**：

| VBA 宿主对象 | 转换为 | 运行时实现 |
|-------------|--------|-----------|
| `Application` | `g_ExcelApp`（全局 COM 对象） | `CoCreateInstance("Excel.Application")` |
| `ThisWorkbook` | `g_ExcelApp.Workbooks(1)` | 通过 COM 获取 |
| `ActiveSheet` | `g_ExcelApp.ActiveSheet` | 通过 COM 获取 |
| `Range("A1")` | `ws.Range("A1")` | COM 调用 |
| `Selection` | `g_ExcelApp.Selection` | COM 调用 |
| `Workbooks` | `g_ExcelApp.Workbooks` | COM 集合对象 |
| `Worksheets` | `wb.Worksheets` | COM 集合对象 |

**所有 VBA 宿主对象本质上就是 COM 对象**，VBA 引擎内部也是通过 `IDispatch` 调用它们的。我们只是去掉 VBA 引擎这层中间人，让编译后的代码直接 COM 调用。

**优点**：
- 行为 100% 兼容（调的就是同一个 Excel，结果一定一样）
- 工作量可控（写 COM 启动器 + 类型库导入即可）
- 肯定行，没有技术风险

**缺点**：
- 运行时需要安装对应 Office
- 进程外 COM 调用有性能开销
- 但这正是 VBA 本来的工作方式，用户不会有感知

### 5.3 方案C：渐进式（最终推荐）

先走方案B快速落地，再逐步把高频对象自建实现，逐步减少对 Office 的依赖：

```
阶段1：方案B — 全部转 COM 对象调用（必须装 Office）
  ✓ 最快可用，行为 100% 兼容

阶段2：高频对象自建 — Range/Cells 等直接操作 xlsx 文件库
  ✓ 纯数据处理的 Excel VBA 可脱离 Office 运行
  ✗ 复杂格式/图表仍需 COM 回退

阶段3：完整 VBA RTL — 覆盖更多对象模型
  ✓ 覆盖面越来越广
  ✗ 工作量巨大，长期工程
```

## 六、VBA→VB6 语法适配

大部分 VBA 代码无需修改即可被 c3 编译，少量需要适配：

| VBA 特性 | 适配方式 | 难度 |
|----------|---------|------|
| `UserForm` | 转为 VB6 `Form`（布局兼容） | 中 |
| `WithEvents` 在文档类中 | 保留，VB6 也支持 | 低 |
| `RaiseEvent` | 保留，VB6 也支持 | 无 |
| `Implements` | 保留，VB6 也支持 | 无 |
| `Enum` 在文档模块中 | 提取到独立 .bas 模块 | 低 |
| `Document_Open` 等事件 | 映射为 `Sub Main()` 调用 | 低 |
| `Application` 隐式引用 | 显式替换为 `g_ExcelApp` | 低 |
| VBA 项目引用（MSForms 等） | 转为 COM 类型库引用 | 中 |

### 6.1 c3 的处理方式

c3 可以在驱动层做 VBA 模式判断：

```
c3 --vba source.xlsm           # 自动提取 + 适配 + 编译
c3 --vba source.xlsm --extract # 仅提取，输出 .bas/.cls 文件供检视
c3 --vba source.xlsm --dry-run # 提取 + 适配，输出 VB6 等效代码，不编译
```

`--dry-run` 非常重要，让用户可以先看转换结果，确认无误再编译。

## 七、产物形态

VBA 代码编译后的产物：

| 产物类型 | 场景 | 说明 |
|----------|------|------|
| exe | 独立运行的批量处理工具 | 命令行调 Excel COM 做数据处理 |
| exe (带窗体) | 带界面的 Office 扩展工具 | 替代 VBA UserForm |
| dll (ActiveX) | 供其他程序调用的组件 | VBA 逻辑封装为 DLL |
| COM Add-in | 替代 VSTO 的轻量方案 | 注册为 Office 插件 |

- 与 006（MSVC 路线）：VBA 编译同样走 C 代码生成 + MSVC，无额外后端需求

## 九、优先级判断

VBA 支持在 c3 整体规划中的位置：

```
P0: VB6 核心编译能力（纯逻辑 + 类模块）         ← 当前
P1: VB6 运行时 + COM 支持                       ← 下一阶段
P2: VB6 窗体代码编译                            ← 之后的阶段
P3: VBA 提取 + 方案B（COM 对象转换）             ← VB6 编译器成熟后
P4: VBA 方案C（部分对象自建 RTL）                ← 长期演进
```

VBA 支持不需要现在做，但架构上要预留：`SourceManager` 支持虚拟文件系统、驱动层预留 VBA 模式入口。
