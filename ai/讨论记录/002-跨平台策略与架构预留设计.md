# 002 - 跨平台策略与架构预留设计

> 日期: 2026-06-24
> 状态: 已定方案
> 前置: 001-VB6编译器方案评估与路线图

---

## 一、核心原则

**架构预留，MVP不投入。**

编译器在架构层面保证跨平台不是事后补丁，而是先天约束；但MVP阶段只在Windows上验证，不投入任何跨平台开发资源。

---

## 二、两个层面，两种命运

| 层面 | 编译器本身 | 运行时（RTL） |
|------|-----------|-------------|
| 跨平台 | 天然支持 | 依赖平台 |
| 原因 | 词法→语法→语义→AST→IR全是纯逻辑，与OS无关 | COM/窗体/控件/Win32 DLL调用等全是Windows特有 |
| 后端 | LLVM天然支持多目标triple | 需要逐平台实现运行时 |

编译器加个 `--target x86_64-linux-gnu` 就能生成Linux机器码，这是LLVM白送的。真正要干活的是运行时。

---

## 三、跨平台定位：只对"新项目"，不对"旧项目"

### 传统VB6项目 = Windows Only，不跨平台

传统VB6工程的标志：
- 使用COM组件（CreateObject、ActiveX DLL/OCX引用）
- 使用.frm窗体+VB6内置控件
- 调用Win32 API（Declare声明kernel32/user32/gdi32）
- 依赖注册表、WMI、Shell等Windows专有对象

这些项目的跨平台**既不现实也不必要**——VB6用户100%在Windows上，迁移到Linux/macOS意味着推翻整个生态，不如换语言。

### 新项目 = 跨平台候选

新项目的定义（三个条件同时满足）：

| 条件 | 说明 |
|------|------|
| **无COM** | 不使用CreateObject/GetObject，不引用ActiveX组件，不使用Implements IDispatch |
| **GUI使用WebView套壳WebUI** | 窗体不再是CreateWindowEx+Win32控件，而是WebView2/WebKit宿主 + HTML/CSS/JS前端，VB6代码通过宿主桥接与WebUI交互 |
| **不直接调用Win32 API** | 不使用Declare声明Windows专有DLL，只使用编译器提供的跨平台标准库 |

### 新旧项目的编译器行为

```
vb6c my_project.vbp                          ← 默认: Windows原生
vb6c my_project.vbp --target win-x64         ← 显式指定Windows x64
vb6c my_project.vbp --target linux-x64       ← 跨平台编译(必须是"新项目")
vb6c my_project.vbp --target macos-arm64     ← 跨平台编译(必须是"新项目")

# 如果旧项目尝试跨平台编译:
vb6c old_project.vbp --target linux-x64
→ 错误: 项目使用了COM组件(msxml6.dll)，不支持跨平台编译
→ 提示: 请使用 --target win-x64 或移除COM依赖
```

编译器在语义分析阶段可以检测出项目是否满足"新项目"条件——只要引用了COM TypeLib或使用了CreateObject，就自动打上 `requires_windows` 标记。

## 四、GUI跨平台方案：WebView套壳 + 宿主交互

### 架构

```
┌─────────────────────────────────────────────────┐
│                 VB6 业务逻辑层                    │
│    (编译出的原生代码，跨平台可执行)                │
├─────────────────────────────────────────────────┤
│              宿主交互桥接层 (Host Bridge)         │
│    - VB6 → WebUI: 调用JS函数、设置DOM属性        │
│    - WebUI → VB6: 事件回调、用户输入通知          │
├──────────────────┬──────────────────────────────┤
│  WebView宿主      │      VB6标准库               │
│  Win: WebView2   │    (跨平台核心子集)            │
│  Mac: WKWebView  │    - BSTR/VARIANT/SAFEARRAY  │
│  Linux: WebKitGTK│    - 文件I/O (POSIX)          │
│                  │    - 数学/字符串/日期           │
│                  │    - 网络 (libcurl)            │
├──────────────────┴──────────────────────────────┤
│              操作系统                             │
│   Win32 / Linux / macOS                          │
└─────────────────────────────────────────────────┘
```

### WebView宿主层各平台实现

| 平台 | WebView引擎 | API | 状态 |
|------|-----------|-----|------|
| Windows 10+ | WebView2 (Chromium Edge) | ICoreWebView2 | MVP实现 |
| macOS 10.15+ | WKWebView (Safari) | WKWebView / WKScriptMessageHandler | 后期 |
| Linux | WebKitGTK | webkit_web_view / JSCore | 后期 |

### 宿主交互接口设计

```vb
' === VB6侧使用方式（新语法/新对象，不影响旧项目兼容性）===

' 1. 创建WebView窗口
Dim wb As New WebViewHost
wb.Show                            ' 弹出WebView窗口
wb.Navigate "index.html"           ' 加载HTML页面

' 2. VB6调用JS函数
Dim result As String
result = wb.EvaluateJS("calcSum(1, 2)")  ' 同步调用JS

' 3. JS调用VB6（注册回调）
wb.RegisterCallback "onButtonClick", Me  ' 将VB6对象暴露给JS

' 4. JS→VB6事件
' JS侧: window.host.invoke("onButtonClick", {name: "ok"})
' VB6侧: 自动路由到 Public Sub onButtonClick(params As Object)

' 5. 直接操作DOM（可选高级接口）
wb.SetElementValue "output", CStr(result)
```

```javascript
// === JS侧 ===

// 调用VB6宿主方法
window.host.invoke("onDataReady", { rows: 100 });

// 接收VB6推送的数据
window.host.onMessage = function(data) {
    document.getElementById("output").textContent = data;
};

// VB6注册的回调可直接调用
window.host.callbacks.onButtonClick({ action: "submit" });
```

### 关键约束

这种WebView GUI模式与VB6传统.frm窗体是**两种不同的UI范式**，**不兼容**：

| 对比 | 传统VB6窗体 | WebView套壳 |
|------|-----------|------------|
| 控件 | VB6内置控件(TextBox等) | HTML元素(input/div等) |
| 事件 | Form_Click/Text1_Change | JS事件→宿主桥接 |
| 设计器 | VB6窗体设计器(.frm) | 任意Web前端工具 |
| 数据绑定 | VB6 Data控件 | JS框架双向绑定 |
| 外观 | Windows原生控件样式 | CSS自由定制 |
| 兼容性 | 旧项目可编译 | 新项目专用 |

## 五、RTL分层架构

### 设计原则

RTL严格分为三层，边界清晰，跨平台时只需替换平台层：

```
┌─────────────────────────────────────────┐
│  1. RTL Core (跨平台，C标准库+POSIX)     │  ← 所有平台共享
│     - BSTR字符串 (自实现，不依赖SysAlloc) │
│     - VARIANT结构体 (自实现)             │
│     - SAFEARRAY数组 (自实现)             │
│     - 文件I/O (fopen/fread/fwrite)       │
│     - 数学函数 (cmath)                   │
│     - 字符串函数 (Left/Mid/InStr等)      │
│     - 日期时间 (time.h / chrono)         │
│     - 错误处理 (setjmp/longjmp)          │
│     - 动态数组 (Redim/Preserve)          │
│     - 类型转换函数 (CInt/CStr/CDate等)   │
├─────────────────────────────────────────┤
│  2. RTL Platform (平台专用)              │  ← 每个平台独立实现
│     ─── Windows ───                      │
│     │ - COM (CoCreateInstance/IDispatch) │
│     │ - 注册表 (RegOpenKey/RegQueryValue)│
│     │ - 窗体 (CreateWindowEx/消息循环)   │
│     │ - 控件 (VB6内置控件集)             │
│     │ - Declare DLL调用 (LoadLibrary)    │
│     │ - OLE/ActiveX                      │
│     │ - Shell/App对象                    │
│     ─── Linux ───                        │
│     │ - WebView宿主 (WebKitGTK)          │
│     │ - POSIX文件系统                     │
│     │ - D-Bus (替代注册表)               │
│     ─── macOS ───                        │
│       - WebView宿主 (WKWebView)          │
│       - Cocoa桥接                        │
│       - NSUserDefaults (替代注册表)       │
├─────────────────────────────────────────┤
│  3. RTL Bridge (渐进式原生平替)          │  ← 按需提供
│     - HTTP客户端 (libcurl, 替代WinHTTP)   │
│     - JSON解析 (替换ScriptControl)        │
│     - SQLite (替代DAO/ADO)               │
│     - 正则表达式 (替代VBScript.RegExp)    │
│     - 压缩/加密 (替代第三方COM组件)       │
│     - WebView宿主交互                     │
└─────────────────────────────────────────┘
```

### 跨平台编译时的RTL链接

```
Windows传统项目:   exe + rtl_core.lib + rtl_win32.lib + vb6rtl.dll
Windows新项目:     exe + rtl_core.lib + rtl_win32.lib + rtl_bridge.lib
Linux新项目:       exe + rtl_core.lib + rtl_linux.lib + rtl_bridge.lib
macOS新项目:       exe + rtl_core.lib + rtl_macos.lib + rtl_bridge.lib
```

## 六、COM抽象接口设计

### 问题

COM是Windows独有组件模型，但VB6编译器必须在语义分析阶段理解COM——类型库导入、IDispatch调用、事件连接点等。这些逻辑不能写死为"调CoCreateInstance"，否则将来无法替换。

### 方案：IComInterop 抽象接口

```cpp
// com_interop.hpp — 抽象COM互操作接口

class IComInterop {
public:
    virtual ~IComInterop() = default;

    // 对象创建
    virtual HRESULT CreateInstance(
        const CLSID& clsid,
        const IID& iid,
        void** ppv) = 0;

    // 后期绑定调用
    virtual HRESULT InvokeMethod(
        void* pDisp,
        DISPID dispid,
        VARIANT* args,
        int argCount,
        VARIANT* result) = 0;

    // 属性读写
    virtual HRESULT GetProperty(
        void* pDisp,
        DISPID dispid,
        VARIANT* result) = 0;

    virtual HRESULT PutProperty(
        void* pDisp,
        DISPID dispid,
        VARIANT* value) = 0;

    // 事件连接
    virtual HRESULT Advise(
        void* pSource,
        void* pSink,
        const IID& iid,
        DWORD* pCookie) = 0;

    virtual HRESULT Unadvise(
        void* pSource,
        const IID& iid,
        DWORD cookie) = 0;

    // 类型库
    virtual HRESULT LoadTypeLib(
        const char* path,
        void** ppTypeLib) = 0;

    // 引用计数
    virtual ULONG AddRef(void* pUnk) = 0;
    virtual ULONG Release(void* pUnk) = 0;
};
```

### 各平台实现

| 平台 | 实现类 | 行为 |
|------|--------|------|
| **Windows (传统项目)** | `Win32ComInterop` | 调用真实COM：CoCreateInstance、IDispatch::Invoke等 |
| **Windows (新项目)** | `Win32ComInterop` | 同上，但编译器会阻止新项目使用COM |
| **Linux/macOS** | `StubComInterop` | 所有方法返回 E_PLATFORMNOTSUPPORTED，运行时抛出"此平台不支持COM" |

### 编译期检查

编译器在语义分析阶段就知道一个项目是否使用了COM，不需要等到运行时才发现：

```cpp
// 项目依赖标记
struct ProjectRequirements {
    bool uses_com;           // CreateObject/GetObject/ActiveX引用
    bool uses_win32_declare; // Declare Lib "kernel32" 等
    bool uses_vb6_forms;     // .frm窗体
    bool uses_webview_gui;   // WebViewHost对象 (新GUI)
};

// 编译器检查
if (target_platform != WINDOWS) {
    if (req.uses_com)
        error("项目使用了COM组件，不支持跨平台编译");
    if (req.uses_win32_declare)
        error("项目使用了Win32 API声明，不支持跨平台编译");
    if (req.uses_vb6_forms)
        error("项目使用了VB6窗体，跨平台请使用WebViewHost");
}
```

## 七、渐进式原生平替：Bridge层按需提供

传统VB6项目大量使用COM组件来弥补标准库的不足（JSON、HTTP、XML、压缩等）。新项目跨平台时，这些功能不应消失，而是由编译器的Bridge层提供**原生平替**。

### 平替策略

| VB6常见COM依赖 | Bridge层平替 | 实现方式 | 跨平台 |
|----------------|-------------|---------|--------|
| MSXML2.DOMDocument | 内置XML解析 | tinyxml2 / pugixml | 是 |
| ScriptControl (Eval) | 内置表达式引擎 | 自实现或嵌入QuickJS | 是 |
| VBScript.RegExp | 内置正则 | PCRE2 / RE2 | 是 |
| WinHTTP / XMLHTTP | 内置HTTP客户端 | libcurl | 是 |
| ADODB / DAO | 内置数据库 | SQLite3 | 是 |
| Scripting.FileSystemObject | 内置文件系统 | C++17 fs + POSIX | 是 |
| Shell.Application | 不平替 | 需用原生API | 否 |
| WScript.Network | 不平替 | 需用原生API | 否 |

### 使用方式

新项目中不需要CreateObject，直接用编译器内置对象：

```vb
' === 旧项目 (COM，Windows Only) ===
Dim http As Object
Set http = CreateObject("MSXML2.XMLHTTP")
http.Open "GET", "https://api.example.com", False
http.send

' === 新项目 (内置，跨平台) ===
Dim http As New HttpClient       ' 编译器内置，非COM
http.Open "GET", "https://api.example.com"
Dim response As String
response = http.Send()

' 或者更简洁:
Dim json As String
json = HttpClient.Get("https://api.example.com/data")
```

Bridge对象的特点：
- **语法上**是VB6的New + 属性/方法调用，和使用COM对象一样自然
- **编译时**编译器知道这些是内置类型，不走IDispatch后期绑定，走直接方法调用
- **运行时**是C++原生实现，无COM注册、无DLL部署

## 八、.frm窗体的解析/生成分离

即使是Windows传统项目，也要把.frm的解析和代码生成分离，保证架构整洁：

```
.frm文件
    │
    ▼
┌──────────────────┐
│  .frm解析器       │  ← 平台无关，生成窗体描述AST
│  (参考AvaloniaVB6 │     包含控件类型/属性/事件/布局
│   的Deserializer) │     不包含任何Win32 API调用
└───────┬──────────┘
        │  窗体描述AST (平台无关)
        ▼
┌──────────────────┐
│  代码生成策略分发  │
├──────────────────┤
│ Win32后端:        │  → 生成CreateWindowEx + WndProc + 消息循环
│ WebView后端:      │  → 生成HTML模板 + 宿主桥接代码
│ (将来可扩展)      │  → 例如Qt后端: 生成QWidget代码
└──────────────────┘
```

这种分离意味着：
- 解析.frm的逻辑只写一次
- Windows原生窗体和WebView套壳是两种不同的代码生成策略
- 将来加Qt/GTK后端不需要改解析器

## 九、编译器目标平台选项设计

```
vb6c [options] <project.vbp>

目标平台选项:
  --target <triple>        目标平台三元组
                           win-x86      Windows 32位 (默认)
                           win-x64      Windows 64位
                           win-arm64    Windows ARM64
                           linux-x64    Linux x64 (新项目)
                           linux-arm64  Linux ARM64 (新项目)
                           macos-x64    macOS Intel (新项目)
                           macos-arm64  macOS Apple Silicon (新项目)

  --gui <mode>             GUI模式
                           native       Win32原生控件 (默认，仅Windows)
                           webview      WebView套壳WebUI (跨平台)
                           none         无GUI (控制台/库)

  --bridge <list>          启用的Bridge模块
                           http,json,xml,regex,sqlite,...
                           all          启用全部Bridge (默认)
                           none         不启用Bridge

  --compat <level>         兼容性检查级别
                           strict       严格：跨平台禁止任何Windows依赖
                           warn         警告：跨平台时Windows依赖给出警告
                           relaxed      宽松：允许Windows依赖，运行时可能报错
```

### 典型使用场景

```bash
# 传统VB6项目，Windows原生编译
vb6c legacy_app.vbp

# 新项目，Windows + WebView
vb6c new_app.vbp --target win-x64 --gui webview

# 新项目，Linux + WebView
vb6c new_app.vbp --target linux-x64 --gui webview --bridge http,json,sqlite

# 纯逻辑库，跨平台
vb6c math_lib.vbp --target linux-x64 --gui none

# 传统项目强行跨平台 → 报错
vb6c legacy_app.vbp --target linux-x64
# ERROR: 项目引用了COM组件 "MSXML2.DOMDocument.6.0" (msxml6.dll)
# ERROR: 项目使用了Declare声明 "kernel32.dll"
# 提示: 此项目包含Windows专有依赖，请使用 --target win-x64 或移除上述依赖
```

## 十、MVP阶段 vs 后期阶段的边界

| 模块 | MVP (阶段1-2) | 后期 (阶段3+) |
|------|---------------|--------------|
| RTL Core (跨平台) | 实现，但只验证Windows | 补POSIX实现，验证Linux/macOS |
| RTL Win32 (COM/窗体) | 阶段2逐步实现 | 完善 |
| RTL Linux/macOS | 不实现 | 实现WebKitGTK/WKWebView |
| WebView宿主 (Windows) | 不实现 | 实现WebView2套壳 |
| Bridge模块 | 不实现 | 逐个按需实现 |
| --target选项 | 只支持win-x86/win-x64 | 扩展linux/macos |
| 跨平台兼容性检查 | 不实现 | 实现语义分析阶段检测 |
| .frm解析/生成分离 | 不做分离(阶段3初期) | 重构为分离架构 |

**关键约束：MVP阶段所有代码都必须放在正确的抽象层里，即使当前只有Windows实现。**

比如BSTR的实现，MVP阶段可以调Windows的SysAllocString，但接口必须包在 `IStringAllocator` 里——将来换Linux时只写一个malloc实现，不动上层代码。

## 十一、总结

```
跨平台策略全景

传统VB6项目 ──→ Windows Only ──→ 原生PE+COM+Win32控件 ──→ 不跨平台，永远不跨

新项目 ──→ 跨平台候选 ──→ RTL Core + WebView GUI + Bridge层 ──→ Win/Linux/macOS

两者共享 ──→ 同一套编译器前端 ──→ 同一套AST/IR ──→ 同一套LLVM后端

差异仅在 ──→ 链接的RTL层不同 ──→ 代码生成策略不同 ──→ Bridge模块不同
```

核心设计约束：
1. **RTL三层分离**：Core(跨平台) / Platform(平台专用) / Bridge(渐进平替)
2. **COM抽象接口**：IComInterop，Windows真实实现，Linux/macOS空壳拒绝
3. **GUI策略分离**：.frm解析与代码生成分离，原生/WebView/将来Qt都是不同生成策略
4. **编译期检测**：语义分析阶段判定项目是否可跨平台，提前报错而非运行时崩
5. **Bridge渐进提供**：HTTP/JSON/SQLite/Regex等按需实现，新项目用New创建而非CreateObject
