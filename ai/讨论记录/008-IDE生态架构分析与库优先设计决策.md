# 008-IDE生态架构分析与库优先设计决策

> 日期：2026-06-24
> 状态：分析完成，待落地
> 结论：**同一项目，库优先架构**。c3.exe 只是薄 CLI 驱动，所有核心逻辑下沉为可复用库

---

## 一、核心问题：独立项目 vs 同一项目？

### 选项A：独立项目

```
vb6c3/          编译器
vb6c3-lsp/      语言服务器
vb6c3-dap/      调试适配器
vb6c3-vscode/   VS Code 扩展
```

- 每个项目各自构建、各自版本
- 编译器内部逻辑（AST、符号表、类型系统）需要通过某种 IPC 暴露
- 版本同步噩梦：编译器加了新语法，LSP 项目要单独对接

### 选项B：同一项目，库优先 ✅

```
vb6c3/
├── src/
│   ├── core/          核心库（词法/语法/语义/类型/符号）
│   ├── backend/       后端（cgen / llvm）
│   ├── lsp/           语言服务器
│   ├── dap/           调试适配器
│   ├── driver/        CLI 入口（c3.exe 的 main）
│   └── rtl/           运行时
├── extensions/
│   └── vscode/        VS Code 扩展
└── CMakeLists.txt
```

- 所有模块共享同一份核心库代码，零拷贝
- 编译器前端改动自动对 LSP/DAP 生效
- 一个 CMake 构建，一个版本号

**业界先例**：

| 项目 | 做法 |
|------|------|
| Rust | rustc 是库，rust-analyzer 独立但共享语义模型 |
| Clang | libclang 库，IDE 插件直接调用 |
| TypeScript | tsserver 语言服务，tsc 编译器，同一仓库 |
| Go | gopls 语言服务器，同一仓库 |
| Zig | zls 语言服务器，同一仓库 |

**结论：同一项目，库优先**。这是主流做法，且最适合我们的小团队规模。

---

## 二、架构设计：库优先（Library-First）

### 核心原则

**c3.exe 是薄壳，所有实质逻辑在库中。**

```
                    ┌─────────────┐
                    │   c3.exe    │  CLI 驱动（30 行 main）
                    └──────┬──────┘
                           │ 调用
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        ┌──────────┐ ┌──────────┐ ┌──────────┐
        │ vb6c3-core  │ │ vb6c3-lsp │ │ vb6c3-dap │
        │ (STATIC LIB) │ │ (EXECUTABLE)│ │(EXECUTABLE)│
        └──────────┘ └──────────┘ └──────────┘
         词法/语法/语义     LSP 协议       DAP 协议
         类型/符号/诊断     补全/悬停/跳转   断点/变量/调用栈
```

### 库的划分

| 库 | 内容 | 消费者 |
|----|------|--------|
| `vb6c3-core` | 词法器、语法器、AST、语义分析、符号表、类型系统、诊断 | c3.exe, LSP, DAP, 测试 |
| `vb6c3-cgen` | C 代码生成器 | c3.exe |
| `vb6c3-lsp` | Language Server Protocol 实现 | c3-lsp.exe / stdio |
| `vb6c3-dap` | Debug Adapter Protocol 实现 | c3-dap.exe / stdio |
| `vb6c3-rtl3-core` | 运行时核心（字符串/变体/数组/错误） | 用户程序链接 |
| `vb6c3-rtl3-win32` | 运行时 Win32（COM/注册表/窗体） | 用户程序链接 |

## 三、各能力详细分析

### 3.1 Language Server（语言服务器）

**协议**：LSP (Language Server Protocol)，微软提出，已成为事实标准

**c3 需要提供的 LSP 能力**：

| LSP 方法 | 依赖的编译器能力 | 优先级 |
|----------|-----------------|--------|
| `textDocument/completion` | 符号表 + 类型系统 | P0 |
| `textDocument/hover` | 语义分析 + 类型信息 | P0 |
| `textDocument/gotoDefinition` | 符号表 + 源码位置映射 | P0 |
| `textDocument/diagnostics` | 词法/语法/语义分析的诊断 | P0 |
| `textDocument/documentSymbol` | AST + 符号表 | P1 |
| `textDocument/references` | 符号表 | P1 |
| `textDocument/rename` | AST + 符号表 | P2 |
| `textDocument/formatting` | AST（格式化器） | P2 |
| `textDocument/codeAction` | 语义分析 + 诊断 | P3 |
| `textDocument/foldingRange` | AST | P3 |

**关键设计**：增量解析。LSP 要求毫秒级响应，每次按键不能全文重解析。

- 方案A：**全文重解析**（先做这个，VB6 文件通常 < 5000 行，够快）
- 方案B：**增量词法 + 语法树**（后期优化，类似 rust-analyzer 的 CST）

**实现路线**：

```
阶段1: c3-lsp --stdio，支持诊断 + 补全 + 悬停 + 跳转定义
阶段2: 增量解析优化，文档符号，引用查找
阶段3: 重命名，格式化，代码操作
```

### 3.2 Debug Adapter（调试适配器）

**协议**：DAP (Debug Adapter Protocol)，微软提出，VS Code / VS 等通用

**为什么需要**：VB6 原生调试器是 IDE 内置的，c3 编译出的程序需要新的调试方案。

**c3 的调试信息流**：

```
VB6 源码 → c3.exe → C 代码（带 #line 指令）→ cl.exe /Zi → PDB
                                                        ↑
                                        编译器在 C 代码中嵌入 #line 映射：
                                        #line 42 "C:\project\form1.frm"
```

**关键：`#line` 指令**。在生成的 C 代码中标注每行对应的 VB6 源码位置，MSVC 编译时会把映射关系写入 PDB，调试器就能在 VB6 源码层面断点和单步。

**c3-dap 需要提供的 DAP 能力**：

| DAP 能力 | 实现 | 优先级 |
|----------|------|--------|
| 断点设置 | 通过 PDB 的 #line 映射 | P0 |
| 变量查看 | PDB 符号 + 运行时类型信息 | P0 |
| 单步执行 | 源码级 #line 映射 | P0 |
| 调用栈 | PDB | P0 |
| 条件断点 | MSVC 调试引擎支持 | P1 |
| Watch 表达式 | 需要 VB6 表达式求值器 | P2 |
| 编辑并继续 | 极其复杂，后期考虑 | P3 |

**实现路线**：

```
阶段1: 利用 #line + PDB，即可通过 VS Code 的 C++ 调试器调试 VB6 源码（零开发量！）
阶段2: 实现 c3-dap，提供 VB6 级变量查看（变体类型展平、BSTR 显示）
阶段3: VB6 表达式求值器（Watch 窗口支持 VB6 语法）
```

**阶段1 是白嫖**——只要 C 代码生成器正确输出 `#line` 指令，VS Code 的 C++ 调试器就能直接在 .frm/.bas/.cls 源码上断点，无需写任何 DAP 代码。

### 3.3 项目系统（Project System）

VB6 的项目文件是 `.vbp`，包含源文件列表、引用、组件等。

**c3 需要解析**：

```
Type=Exe                                    → 项目类型
Reference=*\G{...}#1.0#0#...\xxx.dll        → COM 引用
Object={...};{...};#1.0#0;xxx.ocx           → ActiveX 控件
Form=Form1.frm                              → 窗体文件
Module=Module1;Module1.bas                  → 标准模块
Class=Class1;Class1.cls                     → 类模块
```

**c3 项目系统职责**：

- 解析 .vbp 文件，提取源文件列表和依赖
- 解析 .vbw 工作区文件（多项目）
- 管理引用关系（COM 类型库、ActiveX）
- 为 LSP 提供项目级符号索引
- 为编译器提供完整的编译单元

**建议**：作为 `vb6c3-core` 的一部分，因为 LSP 和编译器都强依赖它。

### 3.4 VS Code 扩展

**职责**：

- 语法高亮（TextMate 语法文件，纯声明式，简单）
- 启动 c3-lsp（stdio 通信）
- 启动 c3-dap（调试会话）
- 项目模板（新建 .vbp 项目）
- 代码片段

**技术栈**：TypeScript + VS Code Extension API

**和编译器的关系**：扩展本身不含任何编译器逻辑，纯粹是 LSP/DAP 的客户端壳子。可以放在 `extensions/vscode/` 目录下，但构建独立（npm/yo code）。

### 3.5 独立 IDE

**不推荐现阶段做**，理由：

- 工作量巨大（编辑器、项目管理、调试UI、窗体设计器……）
- VS Code + 扩展能覆盖 90% 需求
- 窗体设计器是唯一 VS Code 搞不定的，但这可以后面做 Web 版设计器

**如果未来做窗体设计器**，建议是 Web 技术栈（Vue3/React）的独立应用，通过 LSP/DAP 与 c3 通信，而非嵌入 IDE。

### 3.6 其他可发散的能力

| 能力 | 说明 | 依赖 |
|------|------|------|
| **REPL/交互式** | 逐行执行 VB6 代码，适合教学和调试 | 需要解释器或 JIT（LLVM ORC） |
| **格式化器** | 自动美化 VB6 代码风格 | AST |
| **代码分析/Lint** | 检测死代码、未使用变量、潜在错误 | 语义分析 |
| **文档生成** | 从注释生成 API 文档 | 语义分析 + 注释 |
| **代码迁移助手** | VB6 → VB.NET / C# 的自动化迁移建议 | 语义分析 + 类型系统 |
| **反编译器** | 从 COM DLL / OCX 还原 VB6 接口定义 | PE 解析 + 类型库 |
| **包管理器** | VB6 组件的版本化分发（类似 npm/nuget） | 项目系统 + 注册表 |
| **测试框架** | VB6 单元测试框架 | 运行时 + 诊断 |
| **性能分析器** | 函数级耗时统计 | PDB + 运行时插桩 |
| **窗体序列化** | .frm 文件的解析和生成，为窗体设计器服务 | 项目系统 |

## 四、架构影响总结：当前决策对未来能力的影响

| 当前架构决策 | 对 LSP 的影响 | 对 DAP 的影响 | 对 IDE 的影响 |
|-------------|--------------|--------------|--------------|
| **库优先** | LSP 直接链接 core 库，零拷贝 | DAP 直接链接 core 库 | 灵活，任何客户端都能用 |
| **命名空间 vb6c3** | LSP/DAP 同一命名空间 | 同左 | 品牌统一 |
| **C 后端 + #line** | 无影响 | **调试信息白嫖 PDB** | VS Code 开箱即调试 |
| **后端可插拔** | 无影响 | 后端切换不影响调试 | 未来 LLVM 可提供 JIT（REPL） |

## 五、现阶段要做的事（为未来铺路）

### 必须做（否则后期大改）

1. **core 逻辑全部放库，不放 main()** — c3.exe 的 main 只做参数解析 + 调用库
2. **所有诊断信息携带源码位置** — `SourceLocation` 是 LSP 的基石
3. **符号表支持查询接口** — 按名称查、按位置查、按类型查
4. **C 代码生成器输出 `#line` 指令** — 调试信息的零成本方案
5. **支持逐文件解析** — 不要强制整个项目才能编译单个文件（LSP 需要单文件模式）

### 暂不做（现阶段不需要）

- LSP/DAP 服务器实现
- VS Code 扩展
- 增量解析
- 窗体设计器
- REPL

## 六、CMake 目标结构（远景）

```cmake
# 核心库（词法/语法/语义/类型/符号/诊断/项目系统）
add_library(vb6c3-core STATIC ...)

# 后端
add_library(vb6c3-cgen STATIC ...)     # C 代码生成
add_library(vb6c3-llvm STATIC ...)     # LLVM 后端（未来）

# 运行时
add_library(vb6c3-rtl3-core STATIC ...)
add_library(vb6c3-rtl3-win32 STATIC ...)

# 编译器 CLI
add_executable(c3 ...)                  # 链接 core + cgen
target_link_libraries(c3 PRIVATE vb6c3-core vb6c3-cgen)

# 语言服务器
add_executable(c3-lsp ...)              # 链接 core
target_link_libraries(c3-lsp PRIVATE vb6c3-core)

# 调试适配器
add_executable(c3-dap ...)              # 链接 core
target_link_libraries(c3-dap PRIVATE vb6c3-core)
```

所有可执行文件共享同一个 `vb6c3-core`，一次改动，处处生效。
